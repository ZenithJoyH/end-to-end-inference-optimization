## 1\. 开发综述与按需阅读

### 1\.1 职责边界与仓库结构

请根据计算契约选择目标仓库：`FlagGems` 仅提供符合 ATen schema/overload 的算子能力；vLLM 融合算子及 vLLM 专用数据布局或状态契约的数值计算由 `FlagGems-vllm` 提供。不得因融合逻辑可复用就将其作为非 ATen 融合 API 新增到 FlagGems。SGLang 专用计算仍归其专用算子库，仅在任务已涉及时适用。请求调度和框架级资源生命周期管理应保留在框架侧。开发时应优先复用已有的公开 API，确不满足时再考虑扩展或新增实现（详见 A1、A3）。

合理的依赖流向应当是：**调用方通过公开入口及现有的后端选择机制进入 wrapper/kernel；独立参考实现、单元测试和 benchmark 则共同用于验证这条生产路径。** 生产代码严禁反向依赖测试代码。关于目录结构与接入细则，请参见 A2、B1、E1。

|层次与代码落点|核心职责|对应细则|
|---|---|---|
|包的公开导出、注册与配置|明确 API 签名、变体及支持范围，打通真实的后端选择路径|B1、B2|
|`src/<package>/ops/`（FlagGems 为 ATen 算子；vLLM 融合算子进入 FlagGems-vllm）|存放 host wrapper、kernel 及算子内部 helper；各仓库准确路径见 A2|A2、B3、C1|
|`src/<package>/runtime/backend/_<vendor>/`|存放厂商特化实现与专属调优配置；专用算子库的新增厂商实现放入其下的 `ops/`|A2、A4、D6|
|仓库现有的独立参考入口（SGLang 使用 `reference/`）|提供独立于被测算子的正确性基准（Golden Reference）|B6、E1|
|`tests/` 与 `benchmark/`|负责契约、数值精度、真实后端命中情况及性能的全面验证|E2、E3、F1、F2|

各仓库的算子注册需遵循各自现有的机制：`FlagGems` 仅接入真实 ATen schema/overload，不新增非 ATen 融合 API；`FlagGems-vllm` 需维护公开导出、配置文件和后端注册；`FlagGems-sglang` 则使用模块的 `__all__` 和 registrar。具体要求见 B2、B5、B6，切勿跨仓库生搬硬套。

### 1\.2 标准开发与交付流程

1. **确认归属与可复用性。** 核对当前主线代码、公开入口及各厂商副本，确定代码实现和配置的准确落点（见 A1、A2、A3、A4）。

2. **明确契约并完成接入。** 先厘清输入输出、支持范围和副作用，再编写实现、导出接口并完成注册；编译、launch 和调优统一沿用仓库现有基础设施（见 B1、B2、B3、C1、C3）。

3. **完成独立验证。** 验证目标后端确实被命中、参考实现保持独立且支持范围覆盖完整；若涉及状态更新、可选能力、图执行（CUDA Graph 等）或 autotune，需按对应条款补充验证（见 D1、D3、D5、E1、E2、E3、E4）。

4. **按项目标准交付。** 算子实现和性能优化需提供对应的 benchmark 数据，并说明关键性能回归及未覆盖的测试范围；若仅修改文档、日志或注册元数据，可根据实际影响面和仓库 CI 门禁选择性执行检查（交付要求见 F1、F2、F3、F4）。

## 2\. 关键条款

本节完整保留 A1–F6 的条款编号与约束级别。第 1 节综述仅作导航之用，具体的适用条件与执行标准均以本节条款为准。

### A\. 仓库归属与代码位置

#### A1【必须】按计算契约确定代码归属

|功能内容|归属仓库或层次|
|---|---|
|符合真实 ATen schema/overload 的算子能力|`FlagGems`|
|vLLM 融合算子，以及依赖 vLLM 数据布局、状态格式或调用契约的专用数值计算|`FlagGems-vllm`|
|强依赖 SGLang 数据布局、状态格式或融合调用契约的数值计算|`FlagGems-sglang`|
|模型结构定义、权重加载、请求/token 映射、调度逻辑及 workspace 生命周期管理|对应的框架插件层|

归属判断应基于实际的读写语义与职责边界，而非文件名、编程语言或是否使用了 Triton。例如：请求/token/slot 等调度映射即便在 GPU 上生成，依然属于框架层职责；反之，基于模型分数的 Top\-k、数值 gather/scatter 属于算子范畴，不能仅因输出为索引就将其归为框架 metadata 操作。通用的 view/reshape 等独立张量操作同样可以归入算子库。算子只负责接收明确的 buffer、索引和参数并完成计算，不应接管请求调度；关于资源所有权的界定见 D2。

#### A2【必须】通用实现、厂商特化与参考实现分层落位

|仓库|通用实现目录|厂商特化目录|独立参考与测试目录|
|---|---|---|---|
|FlagGems|`src/flag_gems/ops/`（仅 ATen 算子；不新增非 ATen 融合入口）|`src/flag_gems/runtime/backend/_<vendor>/`|`tests/`、`benchmark/`|
|FlagGems\-vllm|`src/flaggems_vllm/ops/`|`src/flaggems_vllm/runtime/backend/_<vendor>/ops/`|`tests/`、`benchmark/`|
|FlagGems\-sglang|`src/flaggems_sglang/ops/`|`src/flaggems_sglang/runtime/backend/_<vendor>/ops/`|`src/flaggems_sglang/reference/`、`tests/`|

通用实现层应只包含跨后端的公共语义及必要的能力分支；厂商专属的调优配置和特化实现必须放入对应的厂商目录，并通过仓库现有的后端分发机制调用。厂商目录命名需与设备检测及后端配置保持一致，严禁将参考实现（Reference）伪装成厂商优化代码放入后端目录。

#### A3【必须】新增实现前先盘点现有能力

动手开发前，请先检查通用算子库、框架专用算子库及目标后端是否已存在可用入口，并逐项比对 dtype、内存布局、mask、量化参数、状态写入逻辑及报错语义。如果现有 kernel 已满足计算契约、仅仅缺少对应的调用入口，应在算子库中补充一层薄 API 封装，严禁将同一个 kernel 复制粘贴到框架层。

所有新增的数值计算实现均须按上述边界落位；对于历史上已存在于框架内部的实现或特殊后端代码，无需在无关任务中强制迁移。如确需迁移，必须严格保持原有的计算语义、执行顺序和调用契约不变。

#### A4【应该】保持各厂商副本的公共语义同步

修改通用算子时，应全局检索是否存在同名的厂商特化副本，并逐一评估是否需要同步修复；同步时需保留各后端必要的硬件特化逻辑，切勿把仅适用于单一后端的配置机械复制到其他后端。若某厂商后端仅做纯转发而无实质特化，不应为其单独新建一份厂商实现副本。

### B\. 公开接口、注册与构建

#### B1【必须】打通从公开入口到目标 kernel 的完整调用链

新增或修改算子时，必须全链路核对函数签名、公开导出、配置文件、算子注册、后端分发及测试选择器。严禁只提交孤立的实现文件；必须通过仓库规定的公开入口，验证目标实现能够被真实调用。

#### B2【必须】严格按目标仓库的注册机制接入

- **【项目特例：FlagGems】** 根据实际支持的 ATen schema 和 overload，同步更新 `conf/operators.yaml`、`_FULL_CONFIG` 及相关导出列表，各变体需分别核对。FlagGems 不新增非 ATen 融合 API；vLLM 融合算子按 FlagGems-vllm 的公开导出与配置路径接入，严禁将非 ATen 标准的融合算子强行注册为 ATen overload。

- **【项目特例：FlagGems\-vllm】** 按照现有的公开导出规则、`conf/operators.yaml`、后端注册机制及测试 marker 完成接入，确保框架在运行时能正确路由到目标后端。

- **【项目特例：FlagGems\-sglang】** 在算子模块的 `__all__` 中导出真实算子，并按现有的 registrar 和配置机制完成接入；独立参考实现统一通过仓库的 `get_reference()` 机制获取。

算子的公开名称、变体、配置项与测试选择器应当彼此对应；特殊命名例外以目标仓库的既有实现为准。

#### B3【必须】复用项目现有的编译、启动和调优基础设施

严禁绕过项目既有的编译器封装或 launcher，严禁直接修改已安装第三方依赖的源码，也不得用原生 PyTorch 算子冒充目标设备 kernel，或在生产路径中塞入隐式的 PyTorch fallback。Host wrapper 应专注于参数校验、metadata 准备、内存分配和 kernel launch；纯元数据操作与独立参考实现则按仓库既定约定处理。

#### B4【应该】将公共基础设施改动与单个算子改动解耦评估

不要为了迁就单个算子而随意修改公共测试框架、benchmark 基类或构建工具链。如果公共设施确需调整，必须在说明中阐述必要性与影响面，并对所有受影响的调用方进行回归验证。

#### B5【必须】【项目特例：FlagGems】确保 ATen 注册名、重载与元数据严格对齐

对于每一个支持的 ATen 重载（overload）和变体，均需核对其 schema 名称、`conf/operators.yaml` 中的 id 与属性字段、`_FULL_CONFIG` 中的注册 key、公开导出名称以及测试选择器；注册 key 必须使用真实的 ATen 算子名（包含必要的前导下划线和点分 overload 后缀）。元数据需按当前 schema 规范填写，确保 id 唯一并按仓库规则排序，且每次提交只修改与当前算子相关的条目。

融合算子不得作为 ATen overload 混入 `_FULL_CONFIG`。公开 API 名称、yaml id 和 ATen 注册 key 不强求字面完全一致，但必须各自符合对应的命名规范。测试时必须验证注册分发链路真实命中，不能仅用直接调用算子函数的方式替代注册表分发测试。

#### B6【必须】【项目特例：FlagGems\-sglang】将参考实现与生产算子实现彻底隔离

算子实现模块及其 `__all__` 列表中，不得定义或导出 `reference`、`solution` 作为算子别名；所有参考实现必须统一存放在 `src/flaggems_sglang/reference/` 目录下。当存在独立参考实现时，测试代码应通过 `get_reference()` 获取基准结果，严禁将目标 kernel 自身作为测试对比的参考基准。

### C\. 算子语义与数据契约

#### C1【必须】编码前明确输入、输出及支持范围契约

ATen 替换算子的行为以对应的 ATen schema 和 overload 为准；框架专用算子则以目标框架对应版本的实际调用契约为准。实现前需明确所有参数含义、默认值、返回值结构、合法输入范围、算子变体以及明确不支持的参数组合；新增的参数校验逻辑不得误杀上游原本合法的输入场景。

#### C2【必须】严格按各张量自身的内存布局和所在设备进行访问

仔细核对张量的 shape、dtype、device、stride、storage offset、广播语义及输出布局；每一个输入、输出和中间缓冲区都必须使用其自身的 stride 进行寻址，只有当接口契约明确要求 `contiguous` 时，才允许假定内存连续。在多设备环境下 launch kernel 时，必须确保目标设备正确，必要时使用 device guard 显式切换上下文。

#### C3【必须】完整兑现状态更新、原地操作和输出 buffer 的契约

清晰界定哪些输入张量会被原地修改（in\-place）、哪些输出与输入共享底层 storage，以及 cache/state 的准确读写时机与禁写保护区。实现带 `out=` 参数的算子时，需正确处理调用方传入的 buffer、dtype、内存布局和张量别名（aliasing）问题；实现 view 类操作时，必须保留共享底层 storage 的语义。

#### C4【必须】逐项落实所有影响结果的业务参数与数值细节

对于接口接收的 mask、causal 标记、scale、bias、滑动窗口、索引等参数，必须在计算中真实生效，严禁“表面接收参数、内部静默忽略”。严格对齐类型提升（type promotion）、累加精度、整数表示范围、舍入模式及中间结果的物化顺序；量化算子必须真实消费 scale、zero point 和 packed 权重数据。对于 NaN、Inf、负零（`-0.0`）和数值极值，均需按参考契约正确处理。

#### C5【必须】按契约妥善处理空输入与不支持的边界场景

针对具体算子，需明确界定空 batch、空序列（零长度）及零维张量输入下的输出形式与 state 写入行为；注意区分语义（例如 `has_initial_state=False` 仅代表无初始状态，绝不等于空输入，不得据此直接跳过非空计算）。遇到不支持的输入组合或硬件能力缺失时，必须在产生任何内存写入或状态副作用之前明确抛出异常。

#### C6【必须】保障索引计算与内存读写的边界安全

索引变量的数据类型（如 `int32` vs `int64`）必须足以覆盖算子声明支持的最大数据规模；使用 masked load 时，必须为被屏蔽的位置指定合理的填充值（`other`）；任何可能越界的内存写入（store）都必须加上 mask 保护。请务必仔细核算超大张量、尾部非对齐 tile 以及各个独立缓冲区的实际寻址范围。

#### C7【必须】非法输入的报错语义需与目标契约保持一致

完整覆盖越界索引、非法维度、无效参数组合以及 device/dtype 不匹配等异常路径。触发错误时，应按照目标接口约定的异常类型和时机抛出报错，严禁通过取模、截断或 clamp 等方式将非法输入“静默消化”。此外，对用户输入的参数校验必须使用显式的条件判断并抛出异常，不得使用可能被 Python 优化模式（`-O`）抹除的 `assert` 语句。

#### C8【必须】【项目特例：FlagGems】独立实现并测试每一个 ATen 变体

严格按照目标 schema，分别实现并测试默认返回版本、in\-place 版本（`_` 后缀）、`out=` 版本、scalar 重载以及 backward 等实际声明支持的变体；严禁仅写一个普通输出接口，就去顶替具有不同副作用契约的其他变体。其中，`out=` 变体需按上游规范处理 buffer resize、dtype/device 校验、stride、storage offset，并原样返回传入的 buffer 引用；in\-place 变体则需按契约妥善处理张量别名与内存重叠（memory overlap）问题。

### D\. 运行时、性能与图执行

#### D1【必须】严禁在算子开始执行后捕获异常并跨后端重试

所有可选硬件能力或依赖必须在算子正式执行前完成探测；若探测发现能力不可用，应根据既有策略提前切换到同样满足契约的备选路径，或者直接报错退出。一旦计算、原地写入、状态更新或异步 kernel launch 已经启动，任何运行时异常都必须直接向上抛出，严禁在捕获异常后重新调度到另一个后端重试（以免破坏现场或造成双重副作用）。

#### D2【必须】明确声明 buffer、stream 与图执行的生命周期要求

清晰界定输入、输出、state 及 workspace 的别名约束、并发安全性与生命周期归属。跨请求的持久状态、长期驻留的 cache，以及跨调用复用或用于图执行的 workspace，其生命周期统一由框架/调用方管理；算子的 host wrapper 仅可根据接口契约分配常规输出张量和单次调用内部的临时缓冲区。在支持图捕获（Graph Capture）的路径中，严禁执行捕获期非法的操作（如动态流同步、CPU\-GPU 阻塞拷贝等）；固定内存地址、跨 stream 复用及并发同步均由调用方显式管理并建立必要的流依赖。

#### D3【必须】Autotune 过程严禁污染真实输入数据或外部状态

进行算子调优时，必须使用仓库提供的标准 autotune 与状态恢复机制；若被调优的 kernel 包含原地修改（in\-place）、特定输出覆写或 state 更新，必须在每次候选配置试跑后还原受影响的输入、输出及 state 数据。候选配置列表、tuning key 以及适用的 shape 范围需与目标后端的真实硬件能力相匹配；对于不适合动态 autotune 的场景，应明确指定固定的启发式配置。

#### D4【应该】消除热路径（Hot Path）上的不必要开销

在算子执行热路径上，应极力避免 host 端同步等待、设备端数据回读（Device\-to\-Host copy）、冗余的小 kernel 启动以及逐元素的 Python 解释器循环。同时需要注意，任何性能优化手段都不得擅自改变契约规定的数值计算顺序、输出 dtype 或状态写入行为。

#### D5【必须】可选加速特性不得污染基线实现与常规测试

对于依赖特定硬件或第三方库的可选加速特性，必须在执行前检查其运行环境及必需的 API 是否完备；若探测失败，需及时清理可能干扰编译、依赖扫描或缓存 key 生成的无效符号。测试时应将可选加速路径与默认基线路径分开验证，切勿让可选特性的 `skip` 跳过条件误伤正常的基线测试用例。可选特性与编译器的兼容性边界，应严格按目标后端及依赖库的实际支持范围进行处理。

#### D6【应该】【项目特例：FlagGems】厂商专属调优配置应归入对应 vendor 目录

厂商特化的调优参数应遵循仓库规范，统一放入对应后端的调优配置目录中，并通过既有的调优入口加载。如确有充分理由在代码中硬编码固定参数，需在注释或说明中写明适用条件，并充分验证受影响的典型 shape；严禁将针对某一款特定加速卡调出的专属策略直接写死在通用代码路径中。

### E\. 正确性测试

#### E1【必须】测试参考基准（Reference）必须独立于被测实现

构造测试真值（Expected Value）时，应优先调用对应的上游原生算子或仓库内置的独立参考实现；若需自行编写参考逻辑，严禁在其中直接或间接调用被测算子，也不得复用生产路径中可能存在缺陷的公共计算模块。测试脚本当然可以导入被测算子入口，但用于生成预期对比结果的参考计算链路必须保持绝对独立，`reference` 或 `solution` 绝不能指向被测算子自身。

#### E2【必须】全面覆盖声明的支持范围、边界条件与代码分支

测试用例需覆盖具有代表性的典型 shape、所有声明支持的 dtype、非连续内存布局（non\-contiguous）以及非零 storage offset，并按需覆盖多卡/多设备场景。同时，必须确保算子内部的每一条实质性代码分支、空输入、数值边界、非法输入报错、不支持的参数组合、各算子变体、指定输出 buffer、原地修改语义，以及 state 中“不应被触碰的区域”均得到有效验证。

#### E3【必须】测试需明确证明目标后端实现被真实命中

测试文件的组织方式与 pytest marker 标注需符合仓库规范，并能通过仓库标准的测试选择器被正确收集。测试断言必须通过公开调用入口或注册分发链路，证实目标后端的 kernel 确实被路由并执行；仅验证外层 wrapper 有返回值或服务能够正常启动，不足以证明目标 kernel 真正生效。

#### E4【必须】图执行测试必须验证“新输入产生新结果”

当算子涉及图执行（如 CUDA Graph）时，测试必须走完真实的图捕获（capture）与重放（replay）全流程：在 replay 前需更新输入张量的数据，并对独立的输出缓冲区预先填充哨兵值（sentinel values）。对于包含原地修改、张量别名或 state 更新的路径，在对比前必须重置输入数据与初始状态，确保独立参考计算与图 replay 从完全一致的初始状态出发，再比对二者的最终结果——以此排除“捕获了空图”或“直接复用了上一轮旧结果”导致的假阳性通过。此外，测试需覆盖本次改动所涉及的全部状态演进与并发场景。

#### E5【必须】正视并修复代码缺陷，严禁通过削弱测试来掩盖问题

当测试失败时，如果是测试用例本身或参考实现有误，允许修正测试或参考代码；但严禁在缺乏充分数值理论依据的情况下，随意放宽误差容忍度（tolerance）、删减关键断言或直接跳过原本声明支持的场景。精度容差应严格依据数据类型（dtype）、浮点运算顺序及仓库统一标准来设定，且数值边界处的必要检查必须予以保留。

#### E6【必须】测试输入需覆盖真实定义域，并在测试后还原全局状态

测试数据的生成应完整覆盖上游算子允许的负数、零、定义域边界点以及特殊浮点值（NaN/Inf），不得为了迁就不稳定的实现而人为收窄随机数范围、刻意避开难算的数值区间。若测试用例在执行过程中修改了全局配置、随机数种子或设备状态，必须在 teardown 阶段将其彻底还原。如确有客观原因需要跳过（skip/xfail）某些用例，必须在代码中注释说明原因、影响范围及后续跟进的 Issue/追踪项。此外，单测的数据规模应合理控制，确保符合仓库 CI 的运行耗时限制。

#### E7【必须】【项目特例：FlagGems】精度测试应显式调用公开算子接口

在编写精度单元测试时，应按仓库约定直接显式调用 `flag_gems.<op>` 接口来验证算子实现，并逐一覆盖所有已注册的算子变体；新增的单元精度测试不得仅使用 `use_gems()` 上下文管理器包装来替代直接函数调用。至于算子注册表是否真正挂载生效，应另行通过符合当前仓库门禁要求的集成/分发测试来验证——切勿因为直接调用 `flag_gems.<op>` 测试通过，就想当然地认为 PyTorch dispatch 分发链路也已正常命中。

### F\. Benchmark 与交付

#### F1【必须】性能基线（Baseline）与目标路径必须采用相同的测量口径

性能测试需统一使用仓库提供的 benchmark 框架，针对目标硬件平台、真实业务 workload、支持的 dtype 及代表性 shape 建立性能基线。测试前需确认 baseline 与目标路径各自真实执行了预期的算子实现，并在同一设备、相同的流同步策略、一致的 warmup 轮数以及相同的图捕获/重放条件下进行对比；在多卡通信/并行场景下，还需确保各 rank 之间的同步对齐以及迭代次数一致。

#### F2【必须】性能评估结论需覆盖核心 workload 并如实反映性能回归

性能报告需完整呈现 baseline 耗时、目标算子延迟及加速比，并清楚注明测试设备型号、关键依赖版本、代码 commit、测试 shape、dtype，以及任何执行失败或暂未覆盖的场景。性能验收按目标仓库当前的准入门槛和适用范围执行；若核心场景存在性能不达标或负优化，应继续深挖优化或按项目既定评审流程处理，切忌拿单一 shape 下的最好数字当作全场景通用的性能结论。

#### F3【必须】交付物需完整齐套，并如实说明测试验证范围

代码提交时，需一并配齐算子实现、公开导出、注册配置、单元测试及必要的 benchmark 脚本；同时确认下游框架实际调用的是公开可获取的入口，且依赖版本已妥善锁定。提交前请本地运行相关的代码格式化、正确性单测、构建检查及目标硬件测试，并在 PR 说明中如实列出已知失败项与受限于环境未能验证的部分；严禁将临时调试脚本、本地跑出的中间产物或无关改动混入提交中。

#### F4【必须】严格遵守项目的日志、版权声明与代码格式规范

运行时日志必须统一使用项目内置的 `logger`，严禁使用 `print` 语句替代；所有源码、代码注释及日志输出均须使用英文编写。新增文件或改编自第三方的代码文件，必须按照目标仓库的现行规定添加版权头（License Header）及来源声明，自动生成的代码也需按仓库规范明确标注。提交代码前，必须通过仓库配置的 formatter、linter 及 pre\-commit 钩子检查。

#### F5【必须】【项目特例：FlagGems】在算子入口处规范记录算子及变体日志

公开算子入口处需使用 `logger.debug("GEMS <OP>")` 记录调用日志（不同算子变体需带上对应的变体后缀）；若进入特定厂商后端实现，则统一使用 `GEMS_<VENDOR>` 作为日志前缀。请严格遵循仓库既定的 logger 命名规范，确保通过运行时日志即可清晰辨别当前调用的算子变体以及实际命中的厂商后端。

#### F6【必须】【项目特例：FlagGems\-vllm】在厂商实现入口的首行记录后端命中日志

在厂商特化实现的公开入口函数中，第一条可执行语句必须为 `logger.debug("GEMS_<VENDOR> <OP>")`（若函数带有 docstring，则紧随 docstring 之后编写）。厂商名称和算子名称需严格按仓库命名规范填写，以便在调试和验证时能够直观确认实际命中的后端代码路径。
