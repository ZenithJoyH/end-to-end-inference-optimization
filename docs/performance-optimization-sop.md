# 端到端推理性能优化 SOP

## 文档状态

- 版本：`0.60`
- 状态：已包含本项目实际案例与导入案例；导入案例的性能数字尚未在本项目复测
- 最后更新：2026-11-16
- 维护方式：由已完成或明确失败的实际优化案例持续修订

本 SOP 是工作入口，不是固定真理。它只保留能够提高诊断效率、实验可比性、正确性或交付质量的步骤。不同模型、平台和业务 workload 可以有不同分支，但任何删减都需要说明原因。

## 1. 使用方式

每个优化任务开始前：

1. 阅读本 SOP。
2. 在[案例索引](cases/README.md)按平台、模型和问题找到相似案例，再从摘要链接核对引擎、workload 和证据。
3. 只复用与当前 shape、dtype、执行模式和软件 revision 相符的经验。
4. 按[模型产物契约](model-artifact-contract.md)建立实验主记录，用[案例模板](cases/TEMPLATE.md)创建简短摘要，并在案例索引添加一行入口。

任务结束时：

1. 在模型主记录记全实验、失败和回退，将结论、适用边界及关键证据链接写回案例摘要。
2. 判断本次结果是偶发现象、环境内可复现经验，还是具备迁移价值的模式。
3. 只有证据改变了后续决策时才修改 SOP。
4. 核对索引中的案例入口。案例主题或入口变化时编辑原行；修订 SOP 时才写 SOP 变更记录。

workload 可比性、指标决策、schema 与最终报告字段统一见 [实验契约](experiment-contract.md)，每次任务同时记录执行规则版本和验收范围。

### 执行职责与阶段分配

所有阶段遵循 [AGENTS.md 第 5.5 节](../AGENTS.md#55-主-agent-协调与-dsh-headless-执行)：主 Agent 负责目标与契约、任务规划、优先级、资源协调、观察、证据复核和验收；除该节明确例外外，具体分析、实现和测试必须委派。远端默认使用对应目标机器的 `dsh headless`，按[恢复流程](agent-execution.md#dsh-恢复与回退)回退到内置子 Agent；纯本地任务在本地委派。只读、任务较小或执行器故障均不单独构成主 Agent 接管理由。

每个阶段执行前在既有阶段或实验记录中分配工作单元、执行者、输入、产物、依赖、预算及验收标准，结束时记录交付、失败、未完成项、主 Agent 直接执行例外及验收结果。下文的“调用 Skill”“执行”“修改”和命令示例描述方法步骤，不扩大主 Agent 直接执行范围。主 Agent 使用规划复盘 Skill 作决策；其中需要新增的源码/trace 分析、统计或实验仍须委派。按 D0 在已授权且资源独立时自动并行有价值方向，冲突部分串行；分工不改变容器隔离、安全门禁和原生验收要求，也不新增业务账本。

正式精度 runner 位于 [`test/Accuracy_test/`](../test/Accuracy_test/README.md)；参数化工具、结果门禁、性能工具和验收模板见 [`evaluation/`](../evaluation/README.md)。

端到端优化中的正确性和精度步骤统一由 [推理精度评测技能](../skills/inference-accuracy-evaluation/SKILL.md) 编排。SOP 定义触发时机和门禁，Skill 根据 `baseline-sanity`、`minimal-regression`、`formal-gate`、`gate-check` 模式调用现有工具，不维护第二套 runner；进度通知遵循该 Skill：短任务前台反馈，需后台跟进或用户已要求定时通知时使用 heartbeat，并保留已有通知偏好。

正式分数低于预冻结阈值、必要的最小回归失败或评测证据无效时，调用独立的 [推理精度问题定位技能](../skills/inference-accuracy-diagnosis/SKILL.md)。超时、空输出、截断、重复或格式异常可按需诊断，但不单独使精度失败或中断性能优化。

端到端优化中的无 profiler 性能测量统一由 [推理性能评测技能](../skills/inference-performance-evaluation/SKILL.md) 编排，按 `baseline`、`targeted`、`checkpoint`、`formal` 模式调用现有 benchmark 和比较工具。Trace 采集与热点归因由独立的 [推理 Profiling 技能](../skills/inference-profiling/SKILL.md) 编排，按 `capture`、`analyze`、`reprofile` 模式调用 profiler 工具；两者不维护第二套 runner，也不混用计时结论。

多轮实验后的证据归纳和下一轮方向重排由 [推理优化规划复盘技能](../skills/inference-optimization-planning/SKILL.md) 执行。它消费已有实验与各评测 Skill 的结果，不自行补造测量；默认每 2–3 个实验触发一次，遇到组合交互、热点迁移、结论冲突、连续失败或高成本决策时提前触发。

## 2. 证据等级

经验采用以下等级，避免把单次实验过早泛化：

| 等级 | 含义 | 可用于 |
|---|---|---|
| `observation` | 单个案例中的现象，尚未稳定复现或因果未闭合 | 提醒和后续假设 |
| `reproduced` | 同一环境重复出现，A/B 与回退能复现实验方向 | 当前模型/平台决策 |
| `transferred` | 在不同 workload、模型或硬件条件下复现，且适用边界明确 | SOP 推荐路径 |
| `invariant` | 由正确性、安全或测量有效性决定，不依赖具体性能结果 | SOP 强制门禁 |

单个成功案例默认不得高于 `reproduced`。公开资料、理论推导和源码分析可以增强机制解释，但不能代替目标环境实测。

## 3. 阶段 A：定义目标与冻结环境

### A0. 读取已完成的模型适配交付（按需）

当用户指定基于“新模型适配”项目中已经完成适配的某个模型开展性能优化时，只读访问 `/Users/baai/Documents/ChatGPT/新模型适配`，仅检索该模型相关案例、配置和交付记录。提取模型/served name、权重路径、平台与 Host、源适配容器及镜像、启动参数、引擎与 Plugin/FlagGems-vllm/FlagGems revision、挂载、graph 配置、已有精度/性能结论和已知问题。

在当前案例记录上游来源绝对路径、读取时间、文件 revision/SHA 和事实摘要。上游记录用于缩短交接，不直接证明当前环境仍相同；进入容器复刻前重新核对目标机器、容器和服务。不得修改、回写、同步或执行上游项目的流程脚本，也不在当前配置中建立必须依赖上游目录长期存在的链接。用户没有指定具体模型时不扫描整个上游项目。

### A1. 定义验收契约

记录：

- 主指标：例如 P99 TTFT、P99 TPOT、输出吞吐或峰值显存。
- 守护指标：正确性、失败率、尾延迟、显存、功耗或成本。
- 目标 workload：长度分布、并发、请求数、到达模式、endpoint 和数据集。
- 通过门槛：绝对 SLO、相对改善和允许波动。
- 修改边界：允许修改的配置、Plugin、backend、算子和禁止项。
- 工程约束：Plugin 以可提交上游 PR 的设计为目标，明确共享调用方、非目标模型/平台、默认行为与可选依赖影响。
- 远程工作目录：用户可选提供目标 Host 上的绝对路径；记录规范化路径、权限/空间检查及本案例专属子目录。

没有明确通过门槛时，可以完成测量和比较，但结论只能是“改善/回退/未证实”，不能写“达标”。

源码修改范围：用户已授权直接修改当前目标模型推理环境内的 `vllm-plugin-FL`、`FlagGems-vllm` 与 `FlagGems`，覆盖框架逻辑、vLLM 专用/融合算子、通用算子接入、当前算子实现和调优配置。热点来自代码生成时，也可修改、重建并安装该优化容器的私有 FlagTree，实验方法见 C4。vLLM 源码仍默认只读；权重、tokenizer、基础镜像和共享系统配置不因这项授权而开放修改。

修改前核对实际导入路径、安装方式、目标源码副本、revision 和工作区状态，保留已有改动。分别保存各仓库的补丁和回退方法，记录必要的构建/安装及目标服务重载步骤，并验证实际加载和执行路径。若副本被其他服务共享，先隔离影响或取得相应授权，不影响无关工作负载。

#### 远程工作目录

预计在目标机器产生脚本、inspect、日志、profile、benchmark/精度原始结果或临时补丁时，可以让用户提供一个远程工作目录。该目录必须属于当前目标 Host，并解析为明确的绝对路径；不接受 `~`、未解析环境变量、通配符、`/`、home 根目录、模型权重根目录或共享源码根目录作为直接任务目录。

在其下创建唯一的 `<case-id>/` 子目录，并在案例契约中记录 `remote_work_root`、`remote_case_dir`、owner/权限、可用空间和符号链接解析结果。所有新文件使用不覆盖的名称；不清理既有内容。建议按实际需要保存 `commands/`、`manifests/`、`logs/`、`profiles/`、`results/`、`patches/`，不批量创建空目录。项目内只保留可复现配置、摘要、远程绝对路径与 SHA，大体积原始产物留在远端。

远程工作目录不是容器隔离机制。若它不是源适配容器的既有挂载，不得给优化容器增加该目录挂载；Host 侧控制文件和容器产物可通过不改变挂载清单的 runtime 文件传输衔接，并记录源/目标路径与校验。删除或整体归档远程工作目录必须单独确认影响范围。

### A2. 复刻独立优化容器

每次性能优化都从用户指定的已适配容器新建一个专用优化容器。源适配容器只用于读取客观配置和确认适配状态，不直接承载 baseline、profiling、源码修改或 candidate 测试。

执行顺序：

1. 保存源容器的只读 inspect，解析镜像引用与 ID/digest、writable layer 中是否存在必要适配改动、entrypoint/command、working directory、user、关键环境变量、设备、IPC、共享内存、ulimit、网络和资源限制。
2. 确认新容器继承的是有效适配状态。适配结果位于挂载目录时复用原镜像和启动配置；必要改动位于 writable layer 时，先形成可识别、可回退的不可变镜像或等价快照并验证内容，不能使用适配前镜像代替。
3. 规范化源容器的所有目录型 bind mount 和 named volume，字段至少包括 `Type`、`Source`、`Destination`、读写模式、传播属性和适用的 subpath。
4. 用相同目录映射创建优化容器。bind mount 的宿主机源路径和容器目标路径必须分别完全相同；named volume 必须复用同一 volume 及目标路径；访问模式和传播选项不得漂移。
5. 新容器使用独立且不冲突的容器名、宿主机端口和日志路径。容器内端口、设备拓扑及其他影响性能的配置保持一致；必要差异显式记录，不能混入未标注的 baseline。
6. 启动后从优化容器重新提取挂载清单，执行机器可读 diff。只有 `image_lineage=verified` 且 `mount_parity=passed` 才能进入服务预检和 baseline。

目录映射一致是硬门禁：不得用文件复制、符号链接或不同的宿主机路径绕过。若发现缺失、额外挂载、Source/Destination 变化、读写模式或传播属性变化，先修复复刻配置，不运行性能测试。

独立容器不等于独立数据。相同挂载会让 Plugin、FlagGems、模型和缓存目录对源容器或其他使用者可见。源码修改前必须记录挂载目录的 revision、已有改动、共享使用者、补丁和回退方法；同时确认源容器不会与优化容器争抢目标设备、端口或宿主机资源。默认保留且不修改、停止、重启或删除源适配容器。

共享源码的私有副本、实际导入路径验证和回退分支见 [容器隔离流程](container-isolation.md)。通过 `scripts/verify-container-mounts.py` 生成机器可读比较；该工具不自动证明镜像谱系。远端检查入口必须显式指定 inventory Host；新方法先单机验证，之后按 D0 在已授权且资源独立的范围并行，冲突操作串行。

### A3. 冻结可比环境

记录 Host、设备数量与拓扑、功耗状态、容器镜像、权重和 tokenizer、推理引擎、Plugin、FlagGems-vllm、FlagGems、驱动/runtime、dtype、量化、并行策略、graph、cache 配置和完整启动参数。

用于性能测试的 vLLM 服务必须对 baseline、candidate 和 revert 显式使用：

```bash
vllm serve <model> <其余冻结参数> \
  --no-enable-prefix-caching
```

`--no-enable-prefix-caching` 关闭 prefix caching；不要求增加 `--no-enable-log-requests`。先核对目标版本 CLI 确实支持 prefix cache 参数；不支持时停止并记录差异，不静默删除。启动后从完整进程参数、服务日志或等价 runtime 证据确认实际状态，并在 service manifest 中记录 `enable_prefix_caching=false`、`performance_context.prefix_cache_state=disabled`。缺少任一侧证据时不能进入正式比较。

只有用户明确要求研究 prefix cache 时，才在独立实验契约和新基线中改变缓存状态，并记录 cache preparation、前缀复用比例和命中证据。该结果不与默认关闭缓存的基线归因为其他优化收益。历史案例保留其原始缓存语义，不按新规则追认或改写。

任何一项变化都必须进入实验变量或触发新基线，不能作为未记录的背景变化。

配置声明与实际行为分别取证：graph 记录请求/实际模式、capture sizes、backend 和命中；并行记录设备总数、副本数及各 rank 分组；KV 记录有效预算、驻留负载与抢占/重算。先核对目标版本的 CLI、指标及平台能力，不能将 CUDA 文档中的默认值直接用于 PPU 或其他平台。

### A4. 正确性和服务预检

- 调用精度评测 Skill 的 `baseline-sanity` 模式，将结果绑定到当前优化容器和服务身份。
- 验证连接、设备、容器、进程、端口和 `/v1/models`。
- 固定请求执行单请求 smoke test。
- 执行小批量和 8 并发 sanity，并检查实际输出。
- 记录超时、空回复、截断、机械重复、乱码和服务错误。

预检失败时先处理运行时或正确性问题，不开始正式性能调优。

### A5. 建立真实执行路径证据

对 Plugin patch、backend dispatch、graph 特化和算子替换，至少记录一种运行时命中证据：

- profiler 中的目标 kernel symbol 与调用次数；
- backend/dispatch 的可控计数器或一次性日志；
- graph capture/replay 覆盖情况；
- 能区分目标路径和 fallback 的 A/B 开关。

源码中存在分支、环境变量已设置或 microbenchmark 能运行，都不能证明服务实际命中。若发现 no-op、reference fallback、CPU 同步或语义错误，应使依赖该路径的旧性能结果失效并重建基线。

## 4. 阶段 B：建立可信基线

### B1. 分离启动、预热和稳态

分别记录：

- 冷启动：模型加载、编译、graph capture、首请求。
- 预热：allocator、cache、JIT/compile 稳定过程。
- 测量：预热后的有限批次或持续负载；只有满足约定稳态条件时才称为稳态。

测量前冻结预热覆盖的 shape、观察窗口、完成判据和最大预算，例如编译/capture 已完成，连续窗口的主指标与资源波动进入约定范围。固定轮数只能说明执行了预热，不能自动证明稳定；预算内未稳定则记录未证实，不无限等待或选择最好窗口。时间窗口与完成请求数窗口可按 workload 选择，具体时长和容差由任务决定。[测量窗口参考](https://docs.nvidia.com/deeplearning/triton-inference-server/user-guide/docs/perf_analyzer/docs/measurements_metrics.html)

默认优化和验收对象是稳态，不是冷启动、服务首请求、首批次或进入稳态前的首轮。首轮异常用于判断编译、
graph capture、allocator、cache、客户端建连或预热契约是否充分；除非用户明确把冷启动列为独立目标，不能
据此优先优化只影响启动阶段的路径。正式结果只在预冻结稳态准入通过后开始采集，并聚合该阶段的全部测量轮，
同时保留全部逐轮值和
波动。不得看到结果后临时删除较慢的第一个测量轮：若预热后的第一个测量轮仍表现出过渡态，本次证据为
`incomplete`，应先调整预热预算或稳态判据，再对 baseline、candidate、revert 使用同一新契约重跑。

编译/JIT、allocator 和业务 prefix cache 分开记录。默认性能测试已通过服务启动参数关闭 prefix cache，仍需证明实际状态为 disabled；不同 seed 不能替代该证据。显式研究 prefix cache 时才记录共享前缀比例、请求顺序、cache preparation 和每组开始前的队列排空条件。精度评测必须显式开启 prefix cache 并取证；之后切换为关闭缓存的性能服务，按 [performance-bind](../evaluation/accuracy/README.md#精度开启缓存与性能关闭缓存) 核验配置切换、当前运行回归和精度绑定，再按性能契约完成预热与稳态准入。不能直接复用开启缓存实例的 gate。cache 清理仅作用于任务服务，不影响共享目录或其他服务。

### B2. 验证客户端没有成为瓶颈

- 核对实际发送请求数、成功数、并发和到达模式。
- 检查客户端 CPU、网络和连接池。
- 确认 tokenizer 或数据生成是否计入计时范围。
- 固定 endpoint、EOS 和采样策略。
- 区分计划到达、实际发出和完成速率，记录客户端并发限制、等待队列及是否计入延迟。客户端限流可能隐藏服务过载。

客户端饱和时，服务吞吐数字只是客户端上限。

在[实验契约](experiment-contract.md)中选择有限批次、持续并发或到达率扫描；单波请求不能证明持续服务容量。业务容量结论需展示负载扫描、队列趋势、失败和同时满足约定 SLO 的 goodput。vLLM 的 request rate 与 max concurrency 分别约束到达和执行，同时设置时实际发出速率可能低于设定值。[vLLM v0.24.0 benchmark 参数](https://docs.vllm.ai/en/v0.24.0/cli/bench/serve/)

### B3. 收集端到端基线

调用推理性能评测 Skill 的 `baseline` 模式，冻结当前场景、测量契约、服务身份和产物位置。不要求任务开始时先跑完全部场景 baseline；新场景可在进入自身优化闭环时才建立 baseline。

区分两类基线：

- `scenario-entry baseline`：新场景开始优化前的当前已保留代码状态，用于该场景本轮的增量对比。如已包含前序场景优化，记录 `baseline_parent_candidate`。
- `anchor baseline`：未优化原路径在该场景上的基线，用于最终累计收益。可以延后采集，但在最终 full 结论前必须与候选使用同契约补齐。

至少保存请求吞吐、输入/输出/总 token 吞吐、TTFT、TPOT、ITL、端到端延迟的 P50/P95/P99、失败/超时、峰值与稳态显存、设备利用率/功耗和服务错误。记录主机 CPU、内存、网络情况及多卡通信占比和负载不均衡；不可用指标标为 null，不从单点采样推导峰值或能耗。

工具没有提供某项指标时保持缺失，不从平均值推造百分位。

公共工具已提供参数化计划、客户端能力预检和失败记录。测量前通过 `--comparison-contract` 绑定比较阈值；收齐各角色的独立运行后，由 `compare_performance.py` 重验原始产物与条件，输出通过、失败或证据不足。工具只覆盖实际实现的负载范围，不能以一次返回 passed 代替完整任务范围；命令、支持指标及限制统一见[性能入口](../evaluation/performance/README.md)。

按实验契约定义计时边界、请求/token/流式 chunk 的统计单位及跨轮汇总口径。主指标或必要守护指标缺失时只能保留诊断结果，不能通过正式性能验收；精度 gate 通过只代表允许开始候选性能测量。

#### 基线过慢时的恢复分支

baseline 启动前记录本次诊断时间预算和停止条件。某场景在预算内仍无法完成时，这本身是原路径性能很差、值得优先处理的操作信号，不必无限等待完整结果：安全停止本次 benchmark 客户端，保留实际运行时长、已发出/完成/失败请求数、最后进度、部分日志和服务状态，并把该次尝试记为 `deferred-too-slow/incomplete`。诊断预算不是该场景的延迟或吞吐值，不能由它虚构目标 baseline、精确加速比或 passed/failed 性能结论。

随后选择一种 baseline-recovery 策略：

1. **缩减测量（`reduced-measurement`）**：减少请求数、并发、输入长度或输出长度，建立有稳定 ID 且映射到原目标场景的 milestone；用完全一致的缩减 workload 测 baseline/candidate，获得明确的吞吐和延迟数据。
2. **静态优先（`static-first`）**：针对实际加载的 Plugin、FlagGems-vllm、FlagGems 和配置检查调用链、dispatch/回退、算法复杂度、目标 shape、冗余计算、内存搬运、同步、graph、KV、调度与通信组织，并进行单变量、可回退调优。
3. **混合（`hybrid`）**：用缩减测量提供方向和数值反馈，同时通过静态分析解释机制并选择下一项改动。

缩减场景的数字只支持该 milestone，不能冒充原目标 baseline，也不能跨不同输入、输出、并发或请求数计算精确加速比。满足以下任一条件时退出恢复阶段：候选能在记录预算内完成 milestone；静态候选已耗尽，需要目标场景证据；或用户要求恢复整体测量。之后按晋级条件重新调用性能评测 Skill，逐步补做对应目标场景和正式矩阵。若原路径 anchor 仍无法完成，只能报告带 workload 和时间预算的有界结论，不能报告精确累计加速比。

## 5. 阶段 C：定位瓶颈

按以下顺序逐层收敛：

1. 请求与网络：到达、排队、连接、流式返回。
2. 调度与批处理：continuous batching、batch occupancy、prefill/decode 干扰。
3. 推理阶段：tokenizer、prefill、decode、采样、detokenize。
4. 内存与执行：KV cache、prefix cache、分配、同步、graph break、数据搬运。
5. 并行与通信：TP/PP/EP/DP、collective、跨机网络和负载均衡。
6. 算子与 Kernel：dispatch、fallback、launch、访存、occupancy、融合和精度。

对每个当前目标场景，先建立三个相互关联但不可混算的阶段视图：

- **Prefill**：prompt 排队与准入、chunked prefill、输入 token 处理、Prefill batch/shape、首 token 前的通信与 kernel；主要观察 TTFT、input-token 吞吐和服务内部 Prefill 事件。
- **Decode**：首 token 后的自回归循环、KV 读写、Decode batch/shape、采样与逐 token 通信；主要观察 TPOT、ITL、output-token 吞吐和服务内部 Decode 事件。
- **Mixed**：Prefill 与 Decode 共存时的调度、抢占、KV 压力、batch 变化、阶段干扰、排队和完整请求表现。

TTFT 包含排队、调度、网络等开销，TPOT/ITL 也可能包含调度、采样、流式传输或 chunk 口径，因此它们是低开销阶段代理而不是纯设备时间。低开销证据足以确定方向时不强制采 trace；阶段贡献或 CPU、通信、rank 负载归因不足且影响下一项决策时，按需调用 Profiling Skill。需要阶段切分时按事件、iteration/token 边界或服务内标记取证；无法可靠切分时将阶段归因标记为 `unknown/incomplete`，不能把整段时间任意分摊。

调用推理 Profiling Skill 时，已有足以回答当前问题的有效诊断证据直接用 `analyze`；只有缺少决策相关证据时才用 `capture` 在既定预算内补足。证据可以是 trace、CPU/系统/通信报告或 native counter，各自核验身份、范围、时间及有效性，不为 CPU 问题强制采设备 trace。保留改动后，只有热点迁移判断仍缺新采证据且具备可比旧证据/采集条件时才用 `reprofile`；已有数据足够则 `analyze`，无可比旧证据则最小 `capture` 并说明比较边界，不能仅因保留改动就重采。Profiler 运行单独记录，不与无 profiler 的正式性能结果直接比较，所得假设必须回到性能评测 Skill 的 `targeted` 或 `checkpoint` 模式验证。

候选优化按目标指标上预计可兑现的净收益区间排序，再比较证据、成本和风险；不是按 kernel 累计时间或低利用率直接排序：

```text
目标与热点筛选 → 关键路径/资源竞争 → 可消除成本与完整调用新增成本
→ 主指标净收益区间 → 置信度、实现/验证成本与风险 → 下一项证伪实验
```

计算方法和适用边界统一见 C2 及 Roofline 的[热点筛选与净收益排序](../skills/inference-roofline-analysis/references/roofline.md#热点筛选与净收益排序)。实际 shape 覆盖只计一次，时间不能与无量纲风险直接相减；没有足够依据时用区间或待测，不造精确分数。

优先排查与有效工作量无关却随容量或调用次数增长的成本，例如整 cache clone、逐请求 launch、CPU 同步、重复 Prefill、无效 padding/重排和未使用中间结果。

需要区分计算、HBM 带宽与执行效率限制时，按 C5 将 Roofline 证据接入候选排名。若瓶颈收敛到具体算子，使用 `skills/key-operator-opt/SKILL.md`，并把算子收益重新映射到端到端指标。

已有有效材料可按需交给[离线分析工具](analysis-tooling-integration.md)：trace 分层/导航与 overlap/fusion 候选交回 Profiling；上游 PR 检索交回关键算子候选选择；显存/KV 分账和 shape/FLOPs 估算交回 Roofline 或框架工作点判断。工具只产生带输入 SHA、假设和缺口的诊断 sidecar，仍按 C2 排名并回到无 profiler 实测。缺少可验证边界、组布局或实际 shape 时保留 unknown，不为使用工具新增采集或门禁。

### C0. 系统瓶颈分诊与取证

先按症状选择下表相关行，再按 C0.5 选择最低成本方法与工具；这不是要求每个任务运行全部诊断。现有 B1/B2、A5、C1–C5 保持各自职责，主 Agent 按 [AGENTS.md 第 5.5 节](../AGENTS.md#55-主-agent-协调与-dsh-headless-执行)委派具体诊断。归因边界见 Profiling 的[系统瓶颈诊断](../skills/inference-profiling/references/system-bottlenecks.md)，命令模板、工具限制与具体产物见[系统诊断工具步骤](../skills/inference-profiling/references/system-diagnosis-tools.md)；复用当前有效材料，只补影响下一项决策的缺口。

#### C0.1 CPU 热点与主机等待

1. **绑定角色和窗口。** 从当前服务映射 Host/容器 PID、线程与 API、tokenizer、scheduler、worker、采样/detokenize 等角色；只采当前任务相关进程。对照同一稳态窗口的请求事件和设备提交/执行空隙，记录单线程/单核与进程总 CPU、有效 CPU 预算，避免多核平均掩盖串行线程饱和。
2. **先判运行还是等待。** 用当前环境已支持且权限允许的采样，区分 on-CPU 热栈与 off-CPU 的锁/IPC、I/O、调度等待和设备同步；函数墙钟耗时不能直接当 CPU 自耗时，Python 栈也不能代替原生运行时归因。确认热栈是否延迟下一轮提交或输出返回，设备空洞本身不能证明 CPU 算力不足。
3. **检查资源而非只看平均。** 对照实际可用核、quota/cpuset、窗口内节流增量、线程过量及上下文切换、NUMA/设备/网卡邻近性、缺页和内存压力。区分工作太多、预算不足、放置不当与正常等待设备；工具/权限不支持时留缺口，不自动安装、提权或修改系统参数。
4. **只证伪一个机制。** 例如固定 workload 只减少一个冗余 metadata 循环、调整一项线程数，或在已分配资源内改变任务私有启动的核/NUMA 放置。记录预期缩短的热栈/等待与设备空隙；若局部 CPU 下降而关键路径不变，机制尚未兑现。按既有正确性、graph 和无 profiler Mixed 流程验证，并守护另一阶段和尾延迟。

#### C0.2 通信与 collective 等待

1. **建立可比时间线。** 绑定通信库实际版本/backend、TP/PP/EP/DP 组、逻辑 rank、进程/设备、collective 序号或其他可验证关联、消息 shape/dtype/字节数及阶段/迭代。跨进程/设备/Host 核对时钟域、对齐方法及误差界，不能直接相减未经校准的时间戳；误差足以改变先后判断时仅作局部分析并标记 unknown。
2. **区分晚到与传输。** 关联各 rank 的上游计算/主机提交、设备依赖就绪、通信开始和完成。host API 耗时、排队时间与设备 collective 持续时间分列；最早到的 rank 等其他 rank，不等于链路慢。即使到达已对齐，剩余区间仍可能含协议、进展和资源竞争，不能直接命名为纯网络时间。慢到者按 C0.1/C0.3 追溯。
3. **检查有证据的限制。** 按消息量/频次区分小消息延迟与大消息带宽假设，核对拓扑、实际高速/回退路径、设备/网卡邻近性和错误/拥塞信号；检查通信与计算依赖、真实重叠及共享计算/HBM 竞争。通信累计时长不能与计算简单相加，也不能把全部重叠区间当作已隐藏。
4. **按需原生探针。** 已有服务证据不能区分链路和组织开销时，由执行者在已授权且资源独占的窗口跑同组、同 dtype/消息范围的原生通信探针，记录工具语义、预热与同步。探针不得与服务争资源；独立峰值带宽不能替代服务证据。目标工具不可用时返回缺口，不跨厂商回退或改共享驱动/网络配置。
5. **限域回验。** 固定其余条件，单独验证一项通信组织/已支持 backend 配置，并包含 pack、copy、同步、临时内存及重叠变化。拓扑/卡数/并行组改变时按 A3 建可比基线。经适用正确性、graph 与无 profiler Mixed 回验后才保留；collective 变短而关键路径未改善不算端到端收益。

#### C0.3 rank、stage 与副本负载不均衡

1. **定义比较对象。** 保存逻辑 rank 到实际进程/设备及 TP/PP/EP/DP 组的映射，按同阶段、同迭代/微批和可比角色统计多步分布；全服务跨 rank 平均利用率和单点快照均不够。PP 的不同 stage 不要求相同算子，独立 DP 副本不强行对齐无对应关系的 collective。
2. **同时看工作量和时间。** TP 记录实际 token/head/shard shape；PP 记录 stage 层/算子组成、微批和流水线气泡；EP/MoE 记录各专家/rank 接收 token、padding、dispatch/combine 及 all-to-all 收发量；DP 记录到达率、输入/输出/KV 长度、活跃 token 与队列。请求条数相同并不代表工作量相同，padding 后工作量与有效 token 分列。
3. **找决定完成时间的慢者。** 同窗口分列各 rank/stage 的计算、通信、copy、主机空隙和等待，定位最慢者及下游等待；同步时序遵守 C0.2 的对齐边界。可报告同角色工作量/耗时的 max、median 和 max/median 等描述值，分母为零或样本不足时记不可用，不把比值设为通用通过阈值或直接加总重叠时长。
4. **区分三类根因。** 工作量偏斜且单位工作耗时相近，优先验证分片/路由/阶段划分；工作量可比而某 rank 持续慢，回查其 CPU 预算、NUMA、设备状态、backend/graph/shape 与通信路径；工作量与局部执行均可比但等待高，回查同步依赖、流水线和阶段干扰。按 token 归一化也需注意 KV 长度、shape 与算子差异，不能仅凭每 token 耗时断言硬件异常。
5. **限域单变量回验。** 在当前授权内选择一项已有路由/调度配置、任务私有放置或受支持并行布局实验，验证预计缩短的最慢 rank/stage 与整体完成时间；不通过改专家语义或丢弃 token 制造均衡。并行拓扑变更记录新基线，数据布局/通信变更按 D6 高风险回归。最终以无 profiler 的 Mixed、另一阶段守护及尾部请求验证，不把“rank 更均匀”本身当作成功。

这三类诊断共用当前优化点的 evidence、hypothesis 和 next-action：记录选中分支、原始产物路径/SHA、角色/分组/阶段覆盖、时间对齐误差、支持与反对证据、未知项、单变量与停止条件。采样方法和扰动分列；CPU/系统原生报告不要求伪造设备 trace。仅有一张卡或一种采集能力时缩小结论边界，不因补齐清单重复采集、不新增必填 schema、评测模式或独立验收门禁。

#### C0.4 系统诊断自动衔接规划复盘

主 Agent 在新场景首次选方向、每次 C2 排名/D8 复盘、收到诊断或性能结果、保留改动后出现热点迁移时，自动检查下列信号。无需用户点名 Skill，也不等待凑满 2–3 个实验；信号只触发对应分支的决策检查，不等于确认根因或必须新采集。相同信号或结论再次出现但未改变决策前提时，沿用已有决定及停止/重开条件，不另起复盘或采集循环。

| 已发现且可能改变下一项选择的信号 | 自动分支与当前要回答的问题 |
|---|---|
| 关键线程高 CPU、提交/输出空隙、周期限流，或慢 rank 上游主机等待 | 按 C0.1 与 Profiling 的 CPU 分支，区分 on-CPU 工作、runnable 延迟、off-CPU/设备等待；证据已经充分时直接进入相应候选比较 |
| collective 占关键路径、扩卡收益差、跨机/通信抖动 | 按 C0.2 与通信分支，区分参与者晚到、通信服务/传输和重叠争抢；晚到证据指向主机或工作量时将未完成问题限域转入相应分支 |
| 最慢 rank/stage 持续或变化、EP 专家偏斜、DP 副本队列/工作量差异 | 按 C0.3 与负载分支，区分工作量分配、可比工作执行慢和依赖等待；按真实 TP/PP/EP/DP 角色比较 |

先按 C5 的共享证据表核验当前候选/服务绑定，复用有效分析，分析已有报告，合并在途任务；缺口确会改变排序时，按 C0.5 自动选择最低成本方法、工具与所需产物，再限预算派发，不让用户逐项选择采集工具。不可用、已耗尽或旧绑定失效时保留边界与重开条件。三类分支均可直接使用 CPU/系统/通信/工作量证据，不以 Roofline 或设备 trace 为前置条件；只有计算/HBM 等判断确实影响选择时才另按 C5 触发 Roofline。

派发时在当前规划/优化点的既有记录中写清决策问题、分支、候选身份、待证伪机制、执行者、总预算和原规划返回点；依赖新证据的决定等待回收，独立且已有证据支持的候选仍可推进。子任务交付只回原点，不自行重启规划或整轮采集。晚到→CPU/负载等转向由主 Agent 关联原问题、合并未完成范围并沿用预算，不因换分支重置停止条件。

回收后在同一 C2 候选表与 D8 决策中明确消费结果：支持机制的证据更新关键路径贡献、可消除等待/工作量、覆盖和置信度；反对机制或显示成本转移时降级/淘汰相应候选；unknown 或证据不可用时降低置信度，按价值选择有边界的替代证伪或暂缓，不把 unknown 当通过或零成本。与已有算子候选统一比较完整调用新增 copy/pack/通信/排队等成本和主指标净收益区间，记录采纳/降级/暂缓及首个单变量实验、停止条件、另一阶段与 Mixed 守护。诊断不能直接证明优化收益；选定实现后仍按既有正确性、graph 和无 profiler `targeted/checkpoint` 回验，复用有效回执。更新 `optimize/state.yml`、同一优化点 Markdown 和 README 的当前决定/下一步，不另建触发账本、模式或门禁。

#### C0.5 症状驱动的工具选择与退出

这是一张方法分流表，不是固定的“计数→采样→trace→probe”串行清单。协调者先按 C5 复用分析/证据并映射问题覆盖：已有有效分析直接消费到 C2/D8，已有材料足够则仅分析并返回，同问题在途就合并等待；不为走表新增 metrics 或工具预检。只有影响选择的剩余缺口才选相关行，在原总预算与 D0 资源协调下派发。

新增采集/attach 前才按[工具预检](../skills/inference-profiling/references/system-diagnosis-tools.md#preflight)核实实际入口/版本/帮助、输出语义、适用目标身份、权限和扰动。已有离线报告只核其来源、绑定、范围和类型有效性，不以 Linux、活 PID 或连接目标为分析前置；进程采样核 PID/TID/容器，metrics/NIC/设备报告按实际 endpoint/interface/device/窗口等适用身份核验，无关项记不适用。工具名仅是候选，不假定已安装或允许使用；缺工具/权限时采用能回答同问题的低成本替代或返回 unknown，不自动 sudo、安装、放宽权限或重采全套。

| 症状 | 首选最低成本证据与产物 | 何时升级及对应步骤 | 退出与决策返回 |
|---|---|---|---|
| 关键线程忙、提交或输出处理跟不上 | 已有请求/iteration 进度，目标线程 `pidstat` 或 `/proc` CPU 增量、实际 quota/cpuset；产出同窗口线程/角色计数 | 只有关键线程确在消耗 CPU 且热函数会改变方案时，按 [CPU 步骤](../skills/inference-profiling/references/system-diagnosis-tools.md#cpu)选已可用 `py-spy`/`perf` 等做有界热栈采样，按工具语义区分 Python/native 栈与 OS on-CPU 计时；输出栈、样本/丢样与覆盖 | 有效热栈与延迟链支持主机工作候选才进入排名；若主要在等待，转等待行，不反复加深火焰图 |
| CPU 平均低但周期停顿、线程 runnable/阻塞、疑似限流 | 同窗口线程状态、上下文切换、cgroup 节流增量/压力、已有等待栈；不能用累计值或全机平均替代 | 计数不能区分抢占、锁/IPC、I/O 或设备同步且影响选择时，按 [等待/调度步骤](../skills/inference-profiling/references/system-diagnosis-tools.md#waits)补目标范围阻塞/调度证据；已有 host/device 等待关联可直接复用 | 返回实际等待对象/生产者、资源约束或 unknown；不把 `wchan`/单个锁栈当作等待时长或 GIL 证明 |

| 结果漂移、长尾、系统或链路干扰 | 同窗口目标进程资源、`vmstat`/可用系统计数和目标厂商频率/功耗/温度/错误增量；记录其他已知使用者 | 按 [系统状态步骤](../skills/inference-profiling/references/system-diagnosis-tools.md#system)只补关联资源/设备范围；仅剩关键路径歧义再升级相应分支，不自动清场或全机追踪 | 返回可比环境/资源隔离或系统异常假设；不支持的字段留 unknown，不擅自停止无关任务或修改共享配置 |

每行方法的执行者按产物适用范围交付原始报告/计数/栈/trace 或 probe 路径与 SHA、类型有效性和问题覆盖，说明窗口及相关阶段/角色/rank/group、时钟与扰动边界。工具失败、超时或覆盖不足时保留原生状态与可用部分，返回有限 partial/unknown、剩余缺口和重开条件；不自动把其他有效分析、性能结果或全任务判为 Invalid，原正式结果自身的有效性要求不变。共同返回内容沿用 C0.4/C2：支持/反对/unknown、关键路径或争用证据及可消除成本、完整调用新增成本、下一项单变量或有界缺口/停止条件。协调者在同一 C2/D8 规划点明确采纳/降级/暂缓和排名变化；证据已足够或预算/能力边界到达即退出，不能只归档工具输出或自行开新采集循环。

命令细则由上述 runbook 维护；[现有 trace runner 说明](../evaluation/performance/README.md#profiling-与-sglang-诊断)仅承诺已实现的 trace/客户端验证，不提供通用 CPU/off-CPU、rank 工作量或通信链路自动 collector。新增诊断采集/局部 probe 仍由协调者在既有授权内分配，按 C5 复用/去重/限预算；按 D0 隔离或串行资源争用，诊断不改变 quick→完整局部→批次集成→正式验收的边界。

### C1. 两层优化分类与优先级

瓶颈定位可以有请求、调度、通信、内存等多个维度；实施工作按用户指定的两个层面组织：

| 层面 | 子类 | 主要关注点 | 典型候选 |
|---|---|---|---|
| 框架层 `framework` | 不另设算子子类 | 在 vllm-plugin-FL 内改变执行组织、调度和数据流 | 消除主机同步/冗余复制，批处理和 KV 容量调整，graph 覆盖，通信组织 |
| 算子层 `operator` | 接入更好的算子 `replace` | 更换已有实现并接入 Plugin | 对比 FlagGems 与 vendor/native backend；按 Prefill/Decode 和 shape 选择实现 |
| 算子层 `operator` | 优化当前算子 `improve` | 改善当前实现或相邻推理链路的计算、访存与启动效率 | tile/warp/stage 调优，split-K/top-k，访存改造，跨算子融合，特化算法，结合平台 FlagTree/Triton 特性的算子特化，针对热点改进 FlagTree 代码生成 |

分类以收益机制为准，不以修改文件所在目录为准：

- 为新 backend 增加 dispatch 和 fallback 是算子接入的必要步骤，归入 `operator/replace`。
- 减少通用 dispatch、Python 循环或请求组织开销，归入 `framework`。
- 移除框架中不必要的 copy 属于框架层；修改 kernel 支持新 layout 属于算子层。两者共同完成时记录关联实验与依赖。
- 通过重排调用消除中间步骤属于框架层；将现有推理链路中相邻算子的预处理、主体或 epilogue 合并为新的融合 kernel 属于 `operator/improve`；接入已有融合 kernel 属于 `operator/replace`。
- 通信排程、rank 数据组织属于框架层；替换 collective 实现属于算子接入，开发其 kernel 属于当前算子优化。
- 通算融合与 overlap 按 C3.1 的收益机制分类：stream/chunk/microbatch、copy 排程或通信组织为 `framework`；接入已有融合/流水算子实现为 `operator/replace`；新融合 kernel、kernel 内预取/流水为 `operator/improve`。跨层改动保留关联实验、依赖和可回退边界，组合实测且不重复计算同一通信/搬运节省。

默认优先顺序（前提是正确性和测量门禁通过）：

1. **框架层先消除明显浪费。** 检查重复 Prefill、整 cache clone、主机同步、无效循环和运行路径未命中；没有问题则跳过，不做无证据重构。
2. **框架层建立合理工作点。** 小范围扫描并发、KV 预算、batched tokens、Prefill 分块和 graph 覆盖，得到代表性生产 shape；通信已是主瓶颈时提前处理通信组织，不固定排到末尾。
3. **热点算子先比较已有实现。** 在同设备、dtype、shape、layout 和执行模式下比较完整调用成本，通过 Plugin 白名单接入更优实现，保留 fallback。
4. **再优化现有热点算子。** 只有现有实现不满足需求、接入成本不划算，或当前实现的改善机制更明确时，投入 kernel 调优、融合和特化。结合现场证据评估已有 FlagTree/Triton 特性以及私有 FlagTree 的代码生成改进，按 C4 形成候选；记录为何不选择直接替换。
5. **回到框架层复测工作点。** 算子效率变化会改变最优 batch、调度和并行策略；重测后更新候选排名，而不是认为框架优化已经永久结束。

上述顺序是工程默认策略，不是性能定律或当前模型的实测结论。算子热点证据已经充分时，可以直接进入第 3 或第 4 步；跨层方向保持各层局部单变量对照与关联实验，按 D0 统一集成测组合收益，仅决策相关归因或失败定位时按 D3 拆分，不机械逐层整模消融；未证独立端到端贡献保持 unknown，不把单项百分比相加。

### C2. 生成并维护实际候选排名

每个案例维护一张跨两层的统一候选表：

| 排名 | 分类 | 候选 | 目标/阶段与热点证据 | 关键路径与实际覆盖 | 主指标净收益区间 | 证据置信度 | 成本/风险 | 依赖 | 首个证伪实验 | 采纳/暂缓理由 |
|---|---|---|---|---|---|---|---|---|---|---|

主 Agent 在每次选择下一项优化时，自动按以下方法形成/更新短名单；具体分析按第 5.5 节委派，Roofline 与规划 Skill 共享[方法细则](../skills/inference-roofline-analysis/references/roofline.md#热点筛选与净收益排序)：

1. **固定目标与统计单位。** 绑定当前 scenario、候选和稳态窗口，明确优化 TTFT、Decode ITL/TPOT、吞吐、goodput 或其他主指标。分别列 Prefill/Decode/Mixed，不能把平均 step 的节省当作 P99 或容量收益。
2. **先筛选对目标有影响的热点。** 用绑定有效的时间线或 CPU/系统/通信报告等证据判断直接关键路径或资源竞争，记录重复调用与真实 per-rank 工作量/shape 分布，未覆盖贡献保留未知。大累计时间不自动等于大影响；小 kernel 可因高调用频次成为热点。同形状重复层先取代表样本，不逐层逐算子强制采计数器。
3. **自动选择诊断分支与候选机制。** 先按 C0.4 检查 CPU、通信和 rank 偏斜的有效信号与证据状态；足以支持方向时直接比较候选，不足且影响排名时派发限域诊断。按 C3.1 自动评估通算融合、通信/拷贝与计算 overlap、kernel 内预取/流水是否匹配已暴露瓶颈，并让采纳/降级/暂缓影响排名，不等用户点名。只有计算/流量/执行效率判断会改变下一步方案或验证投入时，按 C5 自动调用或复用 Roofline；不要求先给所有热点补齐 Roofline，也不设通用耗时占比/利用率阈值。
4. **建立净收益预算。** 分列原始热点时间、目标窗口与关键路径占比、覆盖口径、局部加速假设、完整调用新增 copy/layout/merge/同步/通信成本，给出目标净收益区间与假设来源。固定 F/Q 的屋顶空间和减少工作量的空间分别评估；有并发时重算依赖路径及新瓶颈，不将累计耗时或扣除重叠后的时间机械乘局部加速比例。已按调用/shape 加权的时间不再乘一次覆盖率；无法可靠换算时写待测。
5. **选择最有价值的下一项实验。** 先比较可兑现净收益区间与跨阶段守护，再结合证据置信度、覆盖、实现/验证/维护成本和正确性/兼容性风险解释排序。区间重叠时优先已有实现可复用、验证成本低、易回退的方案；空间大但证据弱时优先低成本证伪机制，不直接投入完整 kernel/融合实现。没有可信正收益候选时，选择能改变排序的最小诊断或暂缓，不为填榜编造收益。
6. **让结果改变下一轮决策。** 在同一候选表及优化点记录中说明采纳、降级或暂缓依据，选定一个主要变量、成功/停止条件、另一阶段与 Mixed 守护。按既有正确性、graph 和无 profiler 性能流程回验，保留改动后重新核验工作点/关键路径并排序，不把多个候选的独立节省相加。复用/补证仍按 C5，避免因候选排名重复采集或循环调用。

串行时间模型、Amdahl、固定工作量 headroom、改变 F/Q 后的重新建模和重叠算例只支持条件性预测；profiler-on 与无 profiler 测量保持分列，未经绑定与扰动核验不能拼成精确生产收益。P99、动态 batch、排队及 SLO goodput 需要相应样本与无 profiler workload 验证。

对 split、chunk、packing、tile 或调度阈值类候选，候选表同时写明限制资源、理论预算和完整调用新增成本。历史案例中的 S、M 阈值、内存预算和 token 上限只用于形成扫描范围，不能作为新目标的默认值。

设计与兼容性是候选保留约束，不仅是收益相近时的择优项；通用路径特例、隐藏依赖或非目标回归需先修订。收益相近时，优先选择侵入小、已有实现可复用、验证充分和易回退的方案。框架改动并不天然低风险，算子接入也不天然比当前实现更快。候选未命中、精度失败、净收益消失或守护指标越界时停止晋级；每项改动保留后重新测量并排序。

### C3. 从机制选择首个实验

下表由官方设计资料辅助形成候选路径，**不是当前模型/平台已经复现的性能结论**。先确认目标 revision 和平台支持，再把命中条件、保留标准写入候选表；不照抄其他硬件的参数值。

| 触发信号 | 首个单变量实验 | 共同观测与边界 |
|---|---|---|
| 长 prefill 进入时 decode 尾延迟变差 | 固定混合请求序列，小范围扫描 batched token 预算 | TTFT、ITL、排队和实际 batch shape；取舍取决于 SLO。[分块 prefill](https://docs.vllm.ai/en/v0.24.0/configuration/optimization/#chunked-prefill) |
| 长输出期间 KV 压力、重算持续增加 | 保持请求负载，单独降低服务 max-num-seqs | 对比重算成本、完成吞吐和排队；不把抢占恒为零当作普适最优。[Preemption](https://docs.vllm.ai/en/v0.24.0/configuration/optimization/#preemption) |
| 相同输入后续请求显著变快 | 先按 B1/A3 核对编译及实际 cache 状态；只有用户明确研究 prefix cache 时才对照受控冷/热前缀 | 默认性能服务仍关闭 prefix cache；独立缓存契约记录复用比例、实际命中与 prefill 成本，APC 不直接减少新 token 的 decode 计算。[APC 边界](https://docs.vllm.ai/en/v0.10.2/features/automatic_prefix_caching.html#limits) |
| graph 已开启但 launch/padding 仍高 | 只调整实际支持的 capture sizes 或 mode 中的一项 | 实际模式覆盖、capture 成本、内存和 KV 容量；capture 成功不等于全 workload 命中。[Graph 设计](https://docs.vllm.ai/en/v0.24.0/design/cuda_graphs/) |
| 通信占关键路径或 MoE rank 负载偏斜 | 固定设备总预算，比较一个可行的并行布局 | 记录每 rank 形状/路由、通信和副本数；均匀模拟路由仅用于诊断。[Expert parallel](https://docs.vllm.ai/en/v0.24.0/serving/expert_parallel_deployment/) |

这些检查帮助缩小实验范围，不要求为每个任务全跑一遍。Plugin 仍使用已有能力判断与 dispatch 入口；相关版本组合和非目标路径按 D4 复核。

#### C3.1 通算融合与 overlap 候选

在新场景首次选方向、C2 候选排名、每次 D8 复盘以及保留改动后热点/工作点迁移时，自动用已有实际 phase/group/rank/shape、生产者数据就绪与消费者依赖证据检查下表；不要求用户点名，也不因存在异步接口就实施。仅当通信长或跨 rank 等待可能由晚到解释时，先用已有证据按 C0.1–C0.3 区分主机提交慢、rank 工作量倾斜/晚到与通信服务成本；只有影响选择的剩余缺口才按 C5 限域诊断，不能把上游晚到当作网络瓶颈。无关或已足够排除时不新增采集，非通信的预取/copy 候选不强制 CPU/rank 诊断。没有机制匹配或能力/证据不足时在同一候选表记不适用/降级/暂缓和重开条件，不强制新采集、Roofline 或每轮尝试全部机制。

| 机制与分类 | 相关瓶颈信号和需要核对的条件 | 首个有边界的单变量实验 |
|---|---|---|
| 真正通信计算融合：在同一融合实现/设备协作路径中协同生产、通信/归约与消费；已有实现接入为 `operator/replace`，新融合 kernel 为 `operator/improve` | 暴露的通信/同步关键路径，以及可消除的中间 buffer、重复读写、copy 或 launch；实际分块数据就绪、rank 消费关系和可用通信原语支持融合 | 对一个真实 group/shape 比较原完整链路与已有兼容融合实现或最小新融合原型，固定数学语义；仅把两条 stream 同时运行不称为真正融合 |
| Communication–compute overlap：通过 stream、chunk、microbatch 或通信排程使可独立工作重叠，归 `framework`；需新 kernel 的部分另记关联 `operator/improve` | 通信尚在关键路径且存在可提前的独立计算/就绪分块；核对 collective 顺序、异步进展、stream/event 依赖以及计算/HBM/NIC 余量 | 只改变一个排程或分块参数，对比整个关联 step；检查隐藏的等待是否大于新同步/分块开销及并发争抢，不能仅凭双 stream 图认定收益 |
| Copy–compute overlap：通过数据流、缓冲或预取排程重叠搬运与计算，通常归 `framework`；若接入已有融合算子则按接入机制分类 | H2D/D2H/D2D 或 staging copy 暴露，下一块地址/生命周期可知；当前平台确支持相应异步搬运/并发，缓冲及 KV/显存余量足够 | 只对一段搬运/消费链改变排程或缓冲策略，包含 pack、copy、等待、额外 buffer 与启动/排空；搬运与计算同时出现但完整链路不变则降级 |
| Kernel 内 prefetch/pipeline：以已支持的预取/布局/流水原语降低访存等待，新实现归 `operator/improve`，接入已有实现为 `operator/replace` | 算子内存在可流水的访存/计算依赖及等待；按 C4 核对编译器逐原语支持、实际生成代码和寄存器/共享内存成本 | 固定源码其他变量，仅引入一个受支持的预取/流水策略，测完整调用；检查资源占用和同步新增成本，不用“异步”名称推定性能 |

**能力与实现边界。** 在目标平台核对实际 runtime、通信库/backend、编译器版本/构建、设备原语、异步进展与目标 graph 支持，并记录可用范围和实际命中；不能把 CUDA/NCCL 的接口或行为直接推广到其他平台。保持合法数据依赖、各通信组的 collective 顺序、缓冲区所有权/生命周期与可见性，不能靠删除必要同步、提前复用 buffer 或变更 token/专家语义制造收益。按能力/shape/graph guard 在计算开始前选择原路径 fallback；异步计算/collective 开始后不得出错再切后端重试。归约顺序、精度或数值路径变化按既有数值契约与 D6 风险触发验证。

**局部筛选与完整链路。** 沿用 D0：涉及跨 rank 通信的候选，快速 trial 在有代表性的 group/shape 上，以 reference 数值和完整生产→通信/同步→消费链路计时低成本淘汰；入选者再补齐实际适用多 rank、边界/shape/fallback、缓冲复用及目标 graph capture/至少两次变输入 replay。单设备预取/copy 候选按其实际设备完整生产→搬运/同步→消费路径验证，不强造通信或多 rank 覆盖；局部证据不能冒充未测的分布式 graph/服务结果。不为每个 trial 跑整模或强制 profiler。比较以可关联的 iteration/microbatch/collective/step 与 C0.2 时钟误差为界，明确各参与者覆盖和未覆盖结论；分列本地耗时与跨参与者关联，不相加 rank/stream 时长，也不相减未经校准的时间戳。完整成本包括 pack/layout、copy、同步、launch、临时 buffer、流水启动/排空及并发计算/通信/搬运争用；仅主 GEMM 或通信 kernel 变快不足以局部晋级。

入选局部覆盖通过后仅记 pending/“局部通过、整模未验证”，不加入当前组合。协调者按 C2 比较预计可消除的暴露等待/搬运、关键路径贡献、完整调用新增成本、覆盖/置信度与风险，明确采纳/降级/暂缓及首个实验/停止条件；优胜/互补点再批次集成，沿用模型回归、高风险正式精度、Mixed 与另一阶段守护及最终验收。失败限域回退/二分，跨层组合收益不相加，未消融单点贡献保持 unknown。细则见[通算融合与 overlap 实验方法](../skills/key-operator-opt/references/comm-compute-fusion-overlap.md)，共享证据、在途去重与预算仍按 C5，不另建 mode、schema 或门禁。

### C4. 利用平台编译器特性做算子特化

将目标平台已有的 FlagTree/Triton 特性纳入热点算子的优化候选，包括 TLE-Lite 分块表达、已支持的 TLE-Struct/Raw 能力、布局、访存与流水线控制。初次选择算子优化方向和阶段性规划复盘时，都检查这些能力与当前瓶颈是否匹配；不按特性名称提高优先级，不要求迁移所有算子。新写或改写实现归入 `operator/improve`，复用已有特性实现归入 `operator/replace`。

1. **按目标环境核实能力。** 记录芯片架构、FlagTree/Triton 的包版本、revision、真实导入路径、构建选项及厂商 SDK/编译器版本；核对目标版本的后端原语白名单、实现、测试与官方资料。逐项记录所需接口、dtype/shape/layout 和 graph 限制，以及声明支持、编译可用、设备正确性与性能的证据状态。仅能 import、目录中有实现或支持表写有 TLE，不足以证明整个特性族或当前安装包可用。
2. **从瓶颈推导特化。** 绑定当前 `scenario_id`、Prefill/Decode 阶段、真实 shape 分布、调用频次与命中率。说明特性预计减少的成本，例如 gather/布局转换、跨线程交换、中间访存、同步或访存等待，并记录可能新增的寄存器、共享内存和调度成本。异步提示是否生效、静态取块是否减少指令都属于待验证假设，不由 API 名称推定。
3. **比较算子写法时固定编译器。** 保持编译器、SDK、设备、数学语义与测量条件一致，对比普通 Triton 原路径与特性路径；基线应包含合理的普通 Triton 优化，避免只对比低效 gather 或人为串行实现。一次验证一个特性；必要时检查生成的 IR/设备指令及 profiler，确认目标转换和运行路径实际发生。若两条路径生成等价代码或无可测净收益，如实记录，不因采用 TLE 就保留候选。
4. **限定生产启用范围。** 在对应算子库的 vendor 实现和既有公开 API/分发机制中落地，ATen 算子归 FlagGems，vLLM 专用/融合算子归 FlagGems-vllm。按能力、dtype、shape、layout 与 graph 条件建立 guard；未验证或不支持的输入在计算开始前走正确 fallback。保持非目标平台导入与原路径行为；实际执行后的错误不切换后端重试。
5. **按 D0 分层筛选与晋级。** 快速 trial 先以代表 shape 数值与完整调用成本淘汰劣势变体；入选者在目标平台设备补齐适用算子规范、独立 reference 数值/边界与分发测试、适用 graph capture/至少两次变输入 replay，并测包含布局转换、copy、同步、临时内存和 dispatch 的完整调用成本。通过后可局部保留、整模未验证，不要求每个 tile/warp 或局部分支跑整模。优胜/互补候选进入批次集成时，按 D2/D6 执行模型回归、风险精度触发及当前目标 Mixed/另一阶段守护。局部失败或无收益只淘汰/修复相应候选，不以整模测试重复筛选；局部加速不作为端到端收益。
6. **复用现有记录与权限。** 在同一实验的 `change.hypothesis`、`primary_variable`、`engineering_review.design_record` 和对应 Markdown 中保存能力依据、收益机制、边界、原路径/候选/回退结果与未测项，纳入跨层候选排名。修改 FlagTree 本身时按下述方法实验。厂商独立编译器、SDK、驱动及共享安装沿用项目原有授权边界。

能力发现入口：[FlagTree 后端支持表](https://github.com/flagos-ai/FlagTree#multi-backend-support)、[TLE 设计与接口](https://github.com/flagos-ai/FlagTree/wiki/TLE)、[沐曦逐原语支持声明示例](https://github.com/flagos-ai/FlagTree/blob/main/third_party/metax/backend/tle_supported.py)。这些动态入口只辅助检索；实验必须固定实际核对的 revision、路径和日期，不能把在线主线能力当作目标环境事实。本方向由用户于 2026-11-02 指定，尚不构成任何平台或算子的性能通过证据。

#### 修改优化容器内的 FlagTree

当热点 kernel 的 IR、设备指令或资源统计显示一项可消除的成本，例如后端在生成设备代码时引入了重复的布局转换，可将对应的 FlagTree pass、指令选择或流水线策略列为 `operator/improve` 候选。按目标架构和变换的合法条件限定作用范围，对不满足条件的输入沿用原编译路径。

1. **复现原构建。** 从目标 worker 确认实际导入的 Triton/FlagTree、加载的后端与二进制扩展。保存原包或等价恢复副本、版本与内容指纹。候选在优化容器私有位置构建和加载，记录源码 revision 或内容 SHA、补丁、构建命令与产物 SHA。若需从源码重建，先用同一工具链构建未打补丁的版本，与原安装核对代码生成及完整调用表现，再隔离补丁效果。
2. **固定算子，只换编译器。** 保持算子源码、输入、tile/warps/stages 等启动参数、厂商工具链和 workload 一致。用原构建、候选构建、恢复原构建分别编译；隔离各构建的 JIT 和上层已编译图缓存，以同一规则预热。在实际 worker 核对加载路径与构建指纹，将目标 kernel 的 IR 或设备代码变化与完整调用计时对应。若还需改算子，另记一项关联实验，最后实测组合。
3. **验证影响范围并回退。** 除目标 shape 外，覆盖会经过同一编译规则的代表性其他 kernel、边界输入和原路径。局部筛选验证独立数值参考、适用 graph capture 与至少两次变输入 replay、完整调用成本；优胜私有构建按 D0 集成后再以已有精度门禁和无 profiler Mixed 判断服务净收益，不为每个离线编译器候选重启整模。回退时恢复原构建及对应缓存环境；涉及服务时重新加载 worker 并核对实际产物，将构建、验证和回退证据写入同一优化点记录。

### C5. 用 Roofline 连接瓶颈证据与下一步实验

调用独立的 [推理 Roofline 分析技能](../skills/inference-roofline-analysis/SKILL.md)，按其 [Roofline 方法](../skills/inference-roofline-analysis/references/roofline.md)消费现有证据；已有数据待分析交 Profiling `analyze`，确缺采集才按模式条件选择 `capture/reprofile`，不新增验收阶段。适用于当前决策需要区分计算、HBM 带宽、数据搬运或执行效率限制的场景；已有有效证据明确指向排队、主机空隙或通信关键路径时，可先验证相应框架假设，不要求先收全硬件计数器或设备时间线。

**自动触发与决策消费。** 无需用户逐次指定 Skill。主 Agent 在新场景首次选择方向、收到 profiling 结果、保留改动后发现热点/工作点迁移，以及每次规划复盘选择下一项实验前，检查以下条件：

- 计算、HBM 带宽或执行效率归因仍不明确，且不同解释会改变下一项实验；
- 正在依据 FLOPs、流量、利用率或理论上限选择替换/深度调优/融合方案，需要量化可消除成本与验证投入；
- 原 Roofline 结论依赖的候选、shape、batch/KV、精度、执行路径或平台条件已变化，需要重新判断。

满足任一条件时自动安排 `$inference-roofline-analysis`；按第 5.5 节委派具体分析，无需新增确认。已有绑定一致、覆盖充分的有效结果直接复用，缺失计数器可先产出有边界的估算与补证任务。若当前证据明确指向请求/主机/通信等问题且 Roofline 不会改变决策，在既有决策中说明不适用原因并继续，不强制每轮重分析或采集。

分析结果必须回到当前 C2 候选表和规划决策：按阶段关键路径贡献、可消除比例、命中范围、置信度、成本和风险重排；记录哪些方向被采纳、降级或暂缓及其依据，选定下一轮首个单变量证伪实验、守护项和停止条件。证据缺口转成有范围的补证任务；不得只归档 Roofline 图或利用率而沿用未经复核的旧优先级。沿用当前优化点与规划记录，不增加独立触发账本；相同输入的有效结果在 Profiling、算子与规划 Skill 间传递复用，避免循环调用。

去重按决策问题、候选/服务绑定、所需范围与方法、待消除缺口判断，不按任务 ID、文件名、分支名或 Skill 名判断。先核对有效/在途/已知不可用状态，再派发；文件有效与覆盖足以回答问题分别判断，部分有效产物不能冒充完整结论，也不因覆盖缺口把可用部分全部作废。同一 capture/报告可供多个问题复用：先将其实际覆盖映射到各问题，只对会改变选择且仍未覆盖的范围合并最小补证，不按工具、分支或问题各采同一窗口；覆盖不相交或绑定不同的材料仍分别保留，不能拼成伪同窗。

1. **绑定稳态阶段与真实工作量。** 绑定当前 `scenario_id`、服务/代码身份、rank/worker、实际 batch、query/KV 长度、shape、dtype、量化和 graph。分别分析 Prefill、Decode，再核对 Mixed 干扰；共享 batch/kernel 无法可靠切分时保留为 mixed，不按 token 比例伪造两个阶段的流量和 FLOPs。
2. **先现有证据，再聚焦计数器。** 用已有阶段/shape、调用、计时与执行路径证据筛选问题；缺少关键路径证据时保留贡献未知，不强制为可独立分析的原生计时范围或有边界估算新采设备 trace。确需补采时只取同一执行路径上决策相关的代表性 kernel/range FLOPs、HBM 读写与耗时，并核实目标平台工具版本、指标单位和覆盖范围。实际 HBM 流量不同于显存占用、张量逻辑字节数或 L2 流量。算法 FLOPs 与执行 FLOPs 分列，记录 graph padding、重算和量化辅助成本。
3. **建立匹配的屋顶。** 用同范围的 `F`、`Q=HBM读+写`、`t` 计算 `I=F/Q`、`P=F/t`、`BW=Q/t`，再以 `P_roof=min(C_peak, BW_peak×I)` 和 `eta=P/P_roof` 评估距离。峰值须匹配精度、计算单元、稀疏模式、设备分区及运行条件，注明规格或校准来源。kernel 屋顶与包含空隙的阶段效率分列；跨流时间不能直接求和，跨卡看关键 rank 与通信路径。
4. **把判断转成一个可证伪候选。** HBM 接近屋顶时优先检查可消除的实际流量和复用；计算接近屋顶时检查无效计算与更优算法；两者都低时结合时间线、stall 和分层存储指标区分并行度、依赖、launch、同步及通信。按 C1 分类为 `framework`、`operator/replace` 或 `operator/improve`，把预计减少的字节/计算/等待、完整调用新增成本、首个单变量实验和停止条件写入 C2 候选表。不得由“Prefill/Decode”名称直接指定瓶颈，也不以固定利用率阈值代替证据。
5. **按既有流程验证并重排。** 保留原有正确性、精度和目标 graph 门禁，通过性能 Skill 的无 profiler `targeted/checkpoint` 验证当前目标 Mixed 净收益及另一阶段守护项。保留改动后若工作点或热点可能迁移，按需 `reprofile` 并在规划复盘中重新排序；不能以 Roofline 效率提高或局部上限空间替代端到端实测。

计数器不可用、FLOPs 覆盖不全或无法保持真实 graph/cache/concurrency 时，明确记录 `estimated`、未知值与 `incomplete` 的归因范围。允许用已验证 shape、时间线和受控 A/B 继续已授权优化，不把估算写成硬件实测，也不把缺失的 Roofline 数据新增为所有优化的硬门禁。replay、缓存清理、时钟控制及多进程覆盖差异按方法文档留档；未经核对不能混用不同采集运行的流量与时间。

记录沿用当前 `optimize/<experiment-id>.md`、`optimize/state.yml` 的既有证据/假设/下一步字段和 README 索引，最小内容见[实验契约](experiment-contract.md#roofline-诊断记录按需)。不新增模型子目录、强制 YAML schema 或 Roofline 验收器。此流程由用户于 2026-11-12 指定，算例仅说明方法，不构成任何目标平台的性能证据。

## 6. 阶段 D：优化实验循环

### D0. 并行探索、局部筛选与批次集成

**单变量约束属于每项独立对照，不要求全任务串行。** 主 Agent 在资源与依赖检查后，自动派发有限多个有价值且互不冲突的 CPU、通信、框架或算子方向；不为凑并发重复同问题或同时开启无预算的低价值候选。沿用既有实验记录保存执行者、依赖、目标设备/CPU/内存/NIC 预算、源码/运行态/缓存隔离、端口、派发时的基准组合及分支候选身份、预计回收/集成时间和停止条件。并行探索不改变 D7 当前正式目标场景的关闭次序；不同 Host/资源上的实验分别绑定自身基线，不拼接为一个软件收益。

不同方向使用真实私有源码副本/worktree、构建和缓存、独立进程或服务实例/端口，按需要使用容器，不要求每个 tile 新建容器。每个使用的优化容器仍须满足镜像谱系和挂载一致性；共享原目录及当前服务候选不被探索分支修改，不为方便隔离新增不一致挂载。分支内部冻结可比的原路径/reference、shape/dtype/graph 与资源放置；局部 baseline 不冒充整模场景 baseline，跨不同硬件的数字不直接归因软件加速。

同一源码副本写入、同设备测量、同服务启停和依赖步骤串行；即使设备不同，也要核对共享 CPU、NIC、内存/带宽和编译负载是否影响测量。资源无法证明独立时串行相关测量或重新分配隔离，独立分析/开发可继续。新方法先在单台已授权 Host 验证后再在既有授权范围展开；不扫描或扩大 Host 授权。读数据/源码共享不等于允许共享写状态、JIT 缓存或服务热更新。

**回收与集成绑定。** 分支返回时，协调者比较派发时基准组合、分支补丁/依赖与当前主线，核对实际 import/backend、API/数值契约、编译构建/缓存、shape/group/graph 与资源条件。主线已变时先在私有集成副本合并或重基，冻结新的候选批次身份；证明不受影响的局部证据可复用，只补受影响或新增范围，不盲用旧 pending 结论、不因重基全量重跑。冲突/依赖或影响面未知时保持 pending 并限域核验，不能覆盖当前主线或静默丢掉依赖。只有适用服务证据通过后才以 retained 等已有决定更新 `current_combined_candidate`；旧分支服务性能/精度 gate 不随合并转绑，新组合仍核验实际服务身份和对应覆盖。

**已集成点唯一计数。** D6 的低风险 4–5 点以最近有效正式精度的覆盖集合为起点，核对待验证组合实际包含、尚未被该集合覆盖的唯一稳定 experiment ID 及其当前已集成实现身份；同点 trial、重试、重复入批、同批重验或复盘不重复计数，已撤回点不冒充仍在组合。实现/数值契约或依赖变更时更新身份与覆盖、重新评估风险，不能借旧 ID 沿用旧通过；不按离线变体数量扩大计数。计数、依赖与覆盖沿用既有优化点和 gate 记录，不新增字段/账本。预选高风险互补点同批立即正式精度是对冻结组合一次验证，不能解释成每个成员分别跑模型，亦不能让未验高风险继续积压。

局部失败先冻结/淘汰该候选及其依赖，不为局部失败启动整模；独立且绑定可信基线、证据不受影响的分支可继续已授权局部研究。集成组合失败先冻结该组合，按依赖定向回退/二分并复用仍有效的局部证据。模型最小回归或正式精度失败仍按 D6.1 定位并冻结失败服务组合/晋级，不能用局部测试解除正式 gate；若问题涉及共同 baseline 或共享环境，暂停所有受影响分支直至核验。

以下循环用于每项可回退的独立实验，局部筛选与服务集成按 D0 分层选择验证，不是要求每个局部候选都重复整模闭环：

1. 分配稳定 `experiment-id`，在 `optimize/state.yml` 建立结构化条目，并创建同名
   `optimize/<experiment-id>.md`；先写优化方向、瓶颈证据和可证伪假设，再开始改动。
2. 预测主指标、守护指标和可能退化场景。
3. Plugin 修改前按开发规范 v1、算子接入/修改前按算子层开发规范读取综述和适用条款；联动改动取两套规范的适用项。说明符号职责、复用扩展点、公开 API、支持范围和非目标影响；记录 `engineering_review`（算子项写入 `operator_standard`）并保存可重复命令、配置和补丁。
4. 局部候选执行 D0 算子级正确性/graph 检查；批次进入服务集成里程碑才调用精度 Skill 的 `minimal-regression`，按 D6 风险触发完整精度，并更新同一优化点文档。
5. 局部候选测同条件完整调用 microbenchmark；集成候选用冻结的代表性场景测 baseline/candidate 及必要 checkpoint，不要求每个局部调参重复模型测量。
6. 在该优化点文档中记录实际性能数据、变化比例、波动、守护指标和结论边界。
7. 检查失败、显存和服务日志，并在需要时做回退复测以排除环境时间漂移。
8. 决定局部保留/待集成、服务保留、回退、未证实或下一假设，使用既有状态加证据范围说明，只有已验证集成候选才更新当前组合；失败、回退和未完成状态同样保留该 Markdown。
9. 更新 `optimize/README.md` 的多轮总览行和链接，不把单点正文复制进总览。

### D1. 阶段和 shape 分治

- Prefill、Decode 和 Mixed workload 分别统计实际 shape 分布、累计时间/调用次数、主指标、守护指标和热点；每个当前目标场景在确定优化优先级前都要给出三者的证据状态，允许某项为 `unknown/incomplete`，但不能将 Prefill 与 Decode 合并后直接归因。
- 阶段专项 milestone 可以通过单 token/短输出突出 Prefill，或用足够长的输出观察稳态 Decode；它们仍包含未完全消失的其他阶段和调度成本，必须记录 `phase_isolation_method`、残余开销与相对目标场景的 workload 差异，并建立自身同配置 baseline。
- backend/tile/config 的选择键至少考虑阶段、M/序列形状、dtype、拓扑与目标 graph 能力。
- 生产特化使用白名单；未验证 shape 必须走正确 fallback。
- 对 backend、融合或算法替换先冻结数值契约：输入/输出 dtype、cast 与舍入位置、归约或排序顺序、tie 处理、归一化/累计阈值、空输入和边界行为。随机输入误差不能替代这些边界检查。
- split、chunk、packing、tile 和调度阈值按目标环境的限制资源推导扫描范围，并测量 merge、通信、copy、临时内存和 graph 覆盖；不假设参数增大带来单调收益。
- 对 fused op 先展开真实数据流，分别核算 align/gather、GEMM、activation、通信、scatter/reduce，不能只测核心 kernel。

### D2. 分层兑现门禁

候选按以下层级晋级，按 D0 先局部筛选、后批次集成；不是每个离线变体逐一跑到第 4 层：

1. microbenchmark：证明机制和数值语义。
2. 局部路径/graph 证据：证明目标 shape、dispatch/backend 与 capture/replay 命中；kernel profile 仅在机制或路径归因需要时采集，已有证据足够不重复 profile。
3. 服务阶段指标：证明 Prefill/Decode/Mixed 的净收益。
4. 端到端 benchmark：证明 TTFT、TPOT、吞吐、显存和稳定性总体可接受。

前两层通过可局部保留、整模未验证并继续并行探索；优胜/互补小组合到集成里程碑统一执行第 3/4 层和 D6 回归。任一层未命中或新增开销吞噬收益时，不得用上一层数字宣称端到端提升。

Prefill 候选至少以 Decode 指标和 Mixed 端到端结果为守护，Decode 候选至少以 Prefill/TTFT 和 Mixed 端到端结果为守护。调度、KV、通信、graph 或融合改动可能同时影响两个阶段，必须分别报告方向与幅度；单阶段专项通过只允许晋级，不等于当前目标场景完成。

对带 split、packing、融合或 layout 转换的候选，microbenchmark 与 kernel profile 均以完整调用为测量单元；主 kernel 变快但 merge、通信、copy 或隐式 materialization 使服务变慢时，候选不得晋级。

### D3. 调度与算子联动

调度参数会改变生产 shape，算子效率也会改变最优调度点。扫描 `max-num-seqs`、`max-num-batched-tokens`、long-prefill threshold 等参数时，同时记录 KV 抢占、重算 token、batch occupancy、TTFT、TPOT 和目标 kernel shape。容量按完整 Decode 生命周期计算，不按瞬时 Prompt 准入量计算。

诊断性组合 A/B 可临时改变多个开关，但不能凭其混杂结果归因单点。D0 预选、局部通过且可逐项回退的有界集成批次，可按组合实测保留；只在归因会改变选择、组合失败或收益互相抵消时定向拆分/消融，未测单点独立贡献保持 unknown，不机械逐点重跑整模，也不以组合通过掩盖局部语义失败。

### D4. Plugin 与算子设计复核及 PR 准备

本节的完整工程复核面向入选/集成及最终交付候选；快速 trial 按 D0 先低成本筛选，入选后补齐适用覆盖，已验证且不受影响的证据可复用。

量化性能优化按 H10 在固定 workload 下评估端到端收益与加载成本，说明量化、repack、编译和预热的计时范围。加载时间单列，稳态性能仍遵循本项目的预热与准入契约。

Plugin 候选从修改前开始遵循 [开发规范 v1](plugin-development-standard-v1.md)，按 [Plugin 优化设计与 PR 准备](plugin-change-review.md) 完成设计归属、能力/shape 边界、共享调用方与可选依赖检查。新增数值计算落在对应算子库，metadata 与计算混合职责按 A3 拆分；执行前完成选择，执行开始后的错误不得切换后端重试。测试按影响范围覆盖目标、非目标和生命周期；涉及 graph 时按 F3 更新输入、填充独立输出哨兵、重置状态并对照独立 reference，保留至少两次 replay 的证据。复用目标仓库实际 CI 规范；无硬件项目记为未测，不扩大连接范围。

在实验 `engineering_review` 中记录规范版本、适用条款、证据、未测/不适用原因及【应该】条款的偏离理由。最终补丁按相同条款重新复核；硬性条款未满足则标记 `needs_revision`。跨仓库按 D3 先交付公开算子接口及测试再接入并锁定可获取版本，交付文档按 G1/G2 区分长期用户信息与 PR/CI 验证材料。

FlagGems / FlagGems-vllm 候选还须执行 [算子层开发规范](operator-development-standard.md)，即使没有修改 Plugin 也不能省略。**FlagGems 仅提供 ATen 算子能力，vLLM 融合算子由 FlagGems-vllm 提供**；这项用户明确边界优先于来源规范中的宽泛归属描述。先盘点现有公开能力，再确定 schema/overload 或融合 API、实际调用契约与 vendor 落点。历史路径不在无关任务中批量迁移。

验证按算子条款覆盖输入布局/stride/storage offset、dtype/device、数值参数、别名/out/in-place/state、空输入和非法边界；FlagGems 直接公开调用测试与 ATen 注册命中测试分别执行，FlagGems-vllm 验证公开导出、配置、后端与测试选择器。autotune 每个候选恢复受影响的数据和状态；graph 使用新输入、独立输出哨兵和一致初态，保留至少两次 replay 证据。厂商入口日志分别按算子 F5/F6，编译/launcher/调优复用现有机制，不以隐式 PyTorch fallback 冒充目标实现。

用仓库 benchmark 在同设备、同 workload、同步、预热和 graph 条件下报告 baseline/候选延迟、加速比及回归范围，再通过性能评测 Skill 验证稳态端到端收益。算子单测不替代模型精度 gate，模型分数达标也不豁免算子契约缺陷。条款、归属和证据写入 `engineering_review.operator_standard` 及同一优化点 Markdown，交付实现、公开导出/注册、测试、必要 benchmark 与固定依赖；不另存过程目录或自动提交代码。

实验开关、日志和临时 patch 在形成 PR 候选时整理；最终 diff 改变后重新验证实际路径和受影响指标。Plugin、FlagGems-vllm、FlagGems 分别保存补丁与依赖关系。性能结论与 `pr_readiness` 分别记录，可用实验结果不自动等于可合入设计。该复核属于已授权工作，无需新增例行审批。

### D5. 控制波动与调优选择偏差

测量前固定重复数、配置顺序、统计单位、最小有意义改善和停止预算。同进程多轮与重新启动后的独立重复分别记录；按成本选择配对/交错的 baseline、candidate 顺序，并保留回退复测。出现明显进程差异或时间漂移时，先增加相应层级的重复，不能挑一个最慢 baseline 归因给改动。

报告每轮与进程间波动、请求样本数、分位数算法及不确定性。32/64 个请求的 P99 可以作为描述值，不能单凭它证明稳定的尾延迟 SLO；同一进程的大量请求也不等于大量独立实验。多轮分位数的平均值不得命名为全体请求的分位数。

搜索阶段与最终确认分开：用小范围扫描筛选方案，再按事先约定的代表性请求/到达序列验证最终候选。没有新机制、收益落在噪声内或预算耗尽时记为未证实/暂缓；不能不断换 seed、阈值或 workload 直到出现通过结果。

### D6. 精度评测节奏与风险触发

精度验证按 D0 的局部筛选与服务集成分层，降低完整 GPQA 的重复成本不削弱对应层次的正确性护栏：

1. **局部候选先做局部正确性。** 快速 trial 可先用代表 shape 数值和完整调用 microbenchmark 筛选，未完成覆盖者不标局部通过；入选者在目标平台设备补齐独立 reference、数值/语义边界、目标与 fallback shape、完整调用 microbenchmark，以及适用 graph capture 和至少两次变输入 replay；本机 unit/mock 不能代替目标设备证据。局部失败就限域修复/淘汰，不触发整模 smoke、模型最小回归、Mixed/profile 或 GPQA。局部通过可待集成，明确整模未验证且未加入当前组合。
2. **低风险候选在批次集成里程碑做模型回归与分批完整精度。** 先选局部优胜/互补、各自可回退的候选，小组合按依赖逐项应用到隔离的候选服务，统一执行 smoke/C8、模型最小回归与适用服务 graph 验证；不要求各点先分别跑整模。完整 GPQA 默认按 D0 的唯一已集成低风险点累计 4–5 个，并结合风险、待验范围、预算和里程碑提前触发，不重复计 trial、重试或批次。记录批次 experiment ID、依赖、源码/配置/服务身份和 gate；未触发完整精度的已集成候选明确“模型最小回归通过、完整精度待执行”，不能无限积压未验组合。
3. **高风险进入服务候选时立即完整验证。** 改变量化/dtype/舍入、attention 或 KV cache 语义、MoE 路由、top-k/top-p/采样、跨算子融合、算法/backend、广泛 custom-op dispatch、rank 数据布局/通信、graph/fallback 覆盖，或已出现异常输出时，允许先做隔离局部研究；进入服务候选集成批次后立即对该组合做模型最小回归、适用 graph 与正式完整 GPQA，不继续积压未验高风险变更。预先选定、已各自局部通过且可回退的互补点可以同批验证一次，不要求每个离线分支分别跑整模再组合重跑；通过前不向主线晋级或声明服务收益。
4. **组合失败先定位和修复，不继续叠加。** 任一集成组合正式分数低于预冻结阈值时，冻结失败组合并调用精度定位 Skill，按依赖做最小复现、定向回退/二分和路径证明；复用有效局部证据，不机械全量重跑所有分支。修复后重跑受影响最小回归与原正式精度范围，新的 `score >= threshold` gate 生成前不恢复该候选的性能晋级。组合通过只证明绑定组合；未做消融的单点独立端到端贡献保持 unknown，不强制为每点做消融。
5. **最终候选必须有精确绑定的正式验收。** 最终代码与配置冻结后，若最近一次完整 GPQA 的 `score >= threshold` gate 已绑定完全相同的源码、配置与当前服务身份，可直接用于阶段 E；否则必须重跑。其后源码、权重、tokenizer、影响推理的配置或服务实例变化，旧 gate 失效。

“低风险”只决定已集成改动的完整 GPQA 频率，不降低对应层次数值测试、路径与测量要求。尚未集成的私有源码/编译器/局部调参不改变未修改主线的服务身份或 gate；实际进入服务的组合按真实身份重新核验。风险依据正确性影响面判断，不依据代码行数、实现者信心或预期加速比判断。

局部算子验证由对应算子流程承担，不伪造模型精度回执；服务集成的模型最小回归通过 [推理精度评测技能](../skills/inference-accuracy-evaluation/SKILL.md) 的 `minimal-regression` 执行，第 2、3、5 项需要新 gate 时使用 `formal-gate`；已有 gate 在进入正式性能前按 `gate-check`/适用绑定流程核验当前服务事实。中间完整精度产物留在 `optimize/` 的实验记录，只有最终候选结论进入 `acceptance/`。

精度评测按本地 Skill 选择前台进度或 heartbeat。沿用用户已明确的周期要求；其他后台跟进仅在状态变化、完成、失败或需人工处理时通知。多 filter 场景不得用原始行数冒充完成题数，ETA 无可靠依据时保持不可用。评测终态后停用监控；`gate-check` 不创建定时任务。

### D6.1 精度问题定位

下述冻结与停止按 D0 的候选、依赖和基线/环境影响面执行：局部失败只处理该候选/依赖，不触发整模；独立且证据可信的隔离分支可继续已授权局部研究。正式失败组合与晋级仍冻结并遵循原定位/gate，共同 baseline 或共享环境存疑时暂停所有受影响分支；并行不是绕过已知精度阻塞的例外。

继承的上游精度问题统一标记 `inherited-accuracy-blocker`。先核验交付证据，不把它归因为尚未证明有错的
优化点；已确认低于阈值时停止叠加新性能优化，只继续定位及必要复现/修复。最小回归不能解除正式阻塞。
用户明确允许的诊断性探索必须在 `state.yml` 记录指令来源、范围和有效期，不能据此关闭正式场景或验收。
问题修复并按原契约达到阈值后才能正常恢复；不静默降低阈值或修改上游工作区。

同一已通过候选的纯服务重启可以使用 [精度工具 rebind](../evaluation/accuracy/README.md) 核验新实例，
不要求仅因独立性能重复而重复完整 GPQA；这不是放宽代码/配置/环境身份，也不是自动继承旧 gate。精度开启缓存、性能关闭缓存的每个独立实例使用专用 `performance-bind`，直接引用原始精度 gate。

baseline sanity 或必要的最小回归失败、完整 GPQA 分数低于预冻结阈值、或评测身份/产物无效时，冻结失败产物并调用推理精度问题定位 Skill，停止叠加新优化。必须定位精度下降原因并修复或回退，再以相同正式契约重跑；只有新的分数达到阈值后才能恢复性能优化。输出健康异常只是可选诊断观察，在 `score >= threshold` 时不影响候选通过与继续优化。

定位首先区分 `measurement-invalid`、服务/配置漂移、请求/输出健康、真实数值语义回退、graph/并发/rank 执行差异及可控随机性。task、dataset、filter、runner、样本集合、服务身份或比较条件无效时，先恢复同契约可比性，不能把工具问题写成算子精度问题。

从最后一个可信正确状态开始，用同一 prompt/token、生成参数、seed、endpoint、服务配置和输入 shape 建立最小复现，再按改动依赖做单变量二分。优先核对高正确性风险改动、graph capture/replay、C1/C8、目标/fallback shape、短/长上下文、单 rank/分布式、Plugin dispatch/backend 和算子数值边界。撤掉某改动后恢复只能形成嫌疑；重新启用可复现、真实路径命中和机制证据闭合后才能确认根因。

修复后先用精度评测 Skill 的 `minimal-regression` 覆盖复现与边界矩阵；原问题来自正式 GPQA 时必须对固定后的候选重新执行 `formal-gate`。相关重跑复用已有且适用的进度监控，不重复创建。当前定位状态和带稳定 issue ID 的历史摘要写入 `optimize/state.yml`，人可读结论同步到 `optimize/README.md`，不得另建历史目录；只有原失败范围重新通过后才恢复性能优化。

### D7. 性能场景与分层测试频率

当前统一目标场景目录如下，长度单位为 token，负载模式均为 `finite_batch`：

| `scenario_id` | 输入 P | 输出 D | 并发 C | 请求 N |
|---|---:|---:|---:|---:|
| `p1024-d1024-c64-n128` | 1024 | 1024 | 64 | 128 |
| `p4096-d1024-c64-n128` | 4096 | 1024 | 64 | 128 |
| `p16384-d1024-c64-n128` | 16384 | 1024 | 64 | 128 |
| `p32768-d1024-c64-n128` | 32768 | 1024 | 64 | 128 |

这四个场景是最终性能优化目标，不是每一轮优化都必须执行的固定矩阵。最终正式测试必须逐项覆盖；如果某项超出模型声明的上下文、实际可分配 KV 容量或平台能力，将该项记录为 `unsupported/incomplete` 并保留证据，不能静默删除、缩短或用中间 milestone 替代。

每个场景使用上述稳定 `scenario_id`，并补充阶段、endpoint、数据生成、主/守护指标和用途。下列是服务集成后的性能测量层次：D0 的局部 tile/warp/算法候选先用完整调用 microbenchmark 筛选，不因每个局部变体自动触发 targeted、Mixed 或 profiling。集成里程碑按影响面选择代表性 targeted/必要 checkpoint，之后按条件晋级正式场景。

1. **定向诊断（`targeted`）**：每轮只跑能够证伪当前假设的目标场景。大模型可降低请求数、重复轮或只选择一个长度/并发点；baseline 与 candidate 使用完全相同的缩减配置。存在明显外溢风险时增加一个便宜的相邻 shape、fallback 或非目标阶段哨兵。
2. **阶段性检查点（`checkpoint`）**：累计保留多个点、热点迁移、准备组合候选，或改动调度、KV、batch、graph、公共 dispatch、通信等跨场景机制时，运行全部受影响场景。检查点失败后停止叠加，通过拆分或回退定位。
3. **正式测试（`formal`）**：中间 formal 只覆盖当前按顺序选中的一个目标场景；最终 formal 才覆盖全部四场景。两者都完成各自范围内的原路径 anchor baseline/candidate/revert、重复、守护指标和精度绑定要求。任务可以增加额外业务场景，但不能减少最终四项。

**验证去重。** `targeted/checkpoint/formal` 是所需证据的范围与目的，不是每次交接必须重跑一遍的步骤。主 Agent 派发前先核验已有合法原生结果及在途验证：当前候选/服务绑定、scenario/workload、graph/cache、阶段/守护、正确性前提、比较契约与重复要求均须满足本次结论。已有合法 checkpoint/formal 若满足同一批次身份、契约与范围内的代表性 targeted/阶段守护要求，可直接用于该结论，不按 targeted→checkpoint→formal 固定顺序重跑；有效 formal 也可支持覆盖内的更窄检查点。保留原 purpose、身份与回执，targeted 不能追认为 formal，复用同一运行也不能充作新的独立重复。在途 formal/checkpoint 已覆盖需求时等待原执行者，不另启动同场景 workload；未覆盖部分按 D0 分配独立资源或串行处理，不争抢测量资源。只在既有结果失效或需求确未覆盖时补测，不把不同配置或不同实例原始结果拼成新回执。去重不能省略项目要求的正式验收或现场身份/精度绑定核验；只做诊断补证且候选/workload 未变，不单独触发又一轮性能测试。

#### 中间优化 milestone

优化过程中允许建立比最终目标更小、更快的 milestone。milestone 可以是四个目标场景的子集，也可以缩短输入或输出长度、减少请求数或并发、使用 Prefill/Decode 阶段专项、短探针、microbenchmark 或特定热点 shape。阶段专项 milestone 必须明确它突出的是 Prefill 还是 Decode、如何隔离、仍混入哪些成本以及另一个阶段的守护指标。其目的可以是验证路径命中、消除主要瓶颈、达到可测状态或决定是否继续投入，并不要求参数与最终场景完全相同。

每个 milestone 必须记录稳定 `milestone_id`、映射的一个或多个最终 `scenario_id`、相对最终 workload 的缩减项、假设、主/守护指标、成功门槛、停止条件和晋级条件。同一 milestone 内比较 baseline/candidate 时仍保持 workload 和服务条件一致。milestone 达标只表示阶段目标完成；保留的改动按影响面晋级到对应目标场景或 checkpoint 验证。

当 milestone 达到预先定义的“显著提升”条件，或当前场景热点/资源瓶颈发生实质迁移时，可以触发一次中间正式性能测试：核验当前精度 gate，只使用当前目标场景完成同配置 baseline/candidate/revert。显著提升和“当前场景优化充分”的条件由任务在看到结果前定义，不在 SOP 中硬编码。中间 formal 达到场景完成条件后，保留当前组合并按 `P1K → P4K → P16K → P32K` 切换下一个目标场景；否则继续当前场景或回退。全部场景完成后再运行最终四场景 formal，中间结果保存在 `optimize/`，最终组合结果进入 `acceptance/`。

`milestone` 是项目的规划与记录概念，不新增公共性能 Skill 模式。实际无 profiler 测量仍根据覆盖范围调用 `targeted` 或 `checkpoint`；算子 microbenchmark 和静态分析分别按其证据边界记录。

#### 按场景串行优化

按照 `P1K → P4K → P16K → P32K` 从正式目录中每次选取一个目标场景，执行“入口基线 → Prefill/Decode/Mixed 分阶段定位 → 阶段 milestone 与单变量优化 → candidate/revert → Mixed 目标场景验证 → 当前目标场景 formal → 场景完成决策”闭环，然后再进入下一场景。例如：

```text
4k-1k scenario-entry baseline
→ 4k-1k profiling / optimization / targeted comparison
→ 保留或回退 4k-1k 候选
→ 16k-1k scenario-entry baseline（记录是否包含 4k-1k 已保留改动）
→ 16k-1k profiling / optimization / targeted comparison
```

任一场景的入口基线超过预记录诊断预算时，可将该步替换为“未完成 baseline 证据 → 缩减场景测量、静态分析或混合恢复 → milestone 数据 → 晋级当前目标场景”。该分支只改变等待与诊断顺序，不放宽同配置比较、精度回归、单场景 formal 和最终四场景要求。

场景入口基线只支持该场景相对当前代码状态的增量结论。如果新优化修改了全局调度、KV、batch、graph、公共 dispatch、通信或不具备稳定 shape guard 的实现，在保留前用 `checkpoint` 复测已完成的受影响场景。不要求场景特化改动在每轮都重跑全部无关场景。

场景和执行层级在测量前确定。不能在看到结果后删除负优化场景、改变请求数/重复轮后仍沿用原 baseline，或用 targeted 结果宣称完整任务达标。targeted 结果仅支持对应 `scenario_id`；checkpoint 支持列出的受影响集合；只有 full 才支持最终验收范围。

不同场景可以分别优化和保留不同候选。最优实现冲突时，先验证是否能用阶段、shape、dtype、layout 或 graph 能力建立稳定 dispatch guard；若无法安全分派，按预冻结主场景与 SLO 明确取舍并保留各场景结果，不计算一个掩盖回退的无权平均加速比。

以上无 profiler 性能测量通过 [推理性能评测技能](../skills/inference-performance-evaluation/SKILL.md) 执行：B3 使用 `baseline`；单点假设验证使用 `targeted`；累计变更、热点迁移和跨场景影响使用 `checkpoint`；最终验收使用 `formal`。需要 trace 归因时单独调用推理 Profiling Skill；每次结果都写回当前实验，模式不能只作为对话中的临时判断。

### D8. 阶段性优化规划复盘

默认完成 2–3 个有结果的实验后调用推理优化规划复盘 Skill；如果出现组合交互、热点迁移、不同场景结论冲突、连续 `failed/incomplete`，或下一步需要投入高成本算子开发/广泛框架改动，则提前触发。C0.4 的 CPU、通信或 rank 偏斜信号/新诊断结果可能改变方向时，立即按其协议检查并更新规划，不等待实验计数或用户点名。触发计数包含保留、回退和失败实验，避免只总结成功项。

复盘先统一各实验的服务身份、场景、正确性与性能覆盖、变更依赖和当前候选是否实际包含该改动。累计收益以同配置 baseline→当前组合 candidate 的可比测量为准，不能把各轮相对提升直接相加。多个已保留改动尚缺受影响场景的组合证据时，按 D7 验证去重后才派发 `checkpoint`；热点仍不明确时按 C0.4/C5 先复用或分析已有证据；完整精度触发到期时按原生流程核验已有有效 gate/在途评测，缺失部分再交精度 Skill，不因规划复盘重复签发或测量。

每次复盘和选下一实验时，按 C0.4 自动分流、按 C3.1 评估通算融合与各类 overlap/预取流水候选，并按 C5 共享表处理有效、在途、缺失、不可用和失效证据；三类系统诊断不需先做 Roofline。派发及补证回到同一规划点后，复核原始证据，明确结果如何改变 C2 关键路径/净收益/额外成本与置信度、采纳/降级/暂缓和首个实验，不能只归档报告后沿用原排序。无法量化时保留未知与停止/重开条件；局部筛选、pending 与批次集成继续 D0，不因新增候选机制给每个 trial 增加整模、profiler 或 Roofline；集成后沿用正确性、graph、无 profiler Mixed 与另一阶段守护，不把局部/诊断通过当性能通过。

下一轮规划通常形成 1–3 个有价值方向的短名单，按端到端瓶颈贡献、可消除比例、生产命中率、证据强度、实现/验证成本和风险排序；按 D0 在资源/依赖允许时自动并行，而非机械只执行榜首。每方向保留自己的首个单变量实验、执行者、隔离资源与预算，协调者统一回收并选择优胜/互补点集成。每候选注明局部/已集成证据范围、适用边界、支持/反对证据、主/守护指标、依赖、成功/停止条件和回退；集成预算与待验范围达到边界就收敛，不以并行无限扩展候选。当前结果、旧决策摘要和下一次复盘触发条件仍更新同一 `optimize/state.yml`、优化点 Markdown 与 README，不创建新账本或 `optimize/history/`。

## 7. 阶段 E：候选回归与验收

- 调用精度评测 Skill 的 `formal-gate` 或 `gate-check` 模式，取得与最终候选服务身份精确匹配的有效 gate；以下条目是该 Skill 不得省略的正式流程。
- 最终候选的精度 gate 核验通过后调用性能评测 Skill 的 `formal` 模式，设置 `formal_run_lifecycle=final-all-targets`；该生命周期覆盖全部四个目标场景，并完成可比的 baseline/candidate/revert、重复、波动与守护指标检查。中间单场景 formal 不代替本步骤。
- 测试前从 [`evaluation/ACCEPTANCE_TEMPLATE.md`](../evaluation/ACCEPTANCE_TEMPLATE.md) 固定任务、生成参数、metric 和单一 threshold。正式精度的唯一通过条件是 `score >= threshold`，等于阈值通过。
- 验证目标 graph 模式可以启动、capture 和 replay；正式 sanity、精度和性能使用最终候选的同一 graph 配置，不要求另行验证 eager 服务。
- 先运行固定小样本和 8 并发 sanity，逐条检查输出，同时观察明显性能异常。
- 对量化、采样、算子、cache 或图路径改动完成最小数值/行为回归。
- 在目标机器上进入基于 `harbor.baai.ac.cn/flageval/flageval-llmeval:v1` 镜像的评测容器。记录容器名、镜像引用与 image ID/digest，并验证容器内 `python3`、`lm_eval`、GPQA 离线数据集以及到候选服务 `/v1/models` 和 Chat Completions endpoint 的连通性。
- 模型服务继续运行在本次独立优化容器中；评测容器只作为精度客户端。两者的角色、网络路径、服务模型名和实际 endpoint 必须分别记录。
- 使用 [`formal_accuracy.py`](../evaluation/accuracy/formal_accuracy.py) 包装调用原始 [`test/Accuracy_test/llmrun.py`](../test/Accuracy_test/llmrun.py)，先执行 `--preflight-only`，通过后以同一案例专属配置、契约、服务身份及评测容器 inspect 运行完整 `gpqa_diamond_generative_cot`。默认正式路径是单服务 `llmrun.py`、`limit=0`、`expected_samples=198`；`llmrun_parallel.py` 仅在用户明确要求分片方案时使用。
- 核对冻结任务、`results_*.json`、`samples_*.jsonl`、effective config 和服务身份，确认正式 score 属于当前候选。这些是证据有效性检查，不是额外精度门槛。
- 中间分数只用于提前排障；不能代替最终结果。不得在看到分数后更换 metric、筛选样本或放宽门槛。
- 在评测前采集真实 task/数据内容证据并绑定契约，冻结配置/运行身份；结束后检查文件 SHA，由 `acceptance.py issue` 生成正式 gate。输出健康可另存为诊断观察，不参与 gate 判定。
- 精度门禁通过后，用同一候选 graph 配置测正式性能，并对原路径执行可比的 baseline/revert 复测。候选 gate 只关联候选身份，不能为 baseline/revert 伪造该身份；比较测试单独记录范围。任何服务实例、源码、权重、tokenizer 或配置变化使旧 gate 失效，重新核验当前事实。工具与命令统一见 [评测入口](../evaluation/README.md)。
- 重跑短、中、长输入和目标并发区间，覆盖真实或代表性 workload、cache 冷热、混合 batch 和长时间稳定性。
- 长稳在验收前冻结持续时长、负载循环、idle/resume、周期 sanity、错误/重启与资源趋势标准，按改动的生命周期风险选择；未执行保持 `not_run/incomplete`，短测成功不能代替。具体记录见验收模板。
- 多卡或多机方案检查通信、负载均衡和故障表现。
- 确认回退配置或补丁可以恢复原基线。

优化循环允许用短 benchmark 做诊断。若缺少正式精度工具或预先冻结的 metric/threshold，应明确标记“探索性性能验证完成、正式验收未完成”，不能将其升级为最终性能结论。

## 8. 阶段 F：案例复盘与经验沉淀

复盘必须回答：

1. 最初瓶颈判断是否正确？哪些证据最有区分度？
2. 哪些实验无效，为什么当时仍合理？
3. 是否存在客户端、配置、cache、warmup 或 profiler 测量陷阱？
4. 最终收益来自哪个机制，适用边界是什么？
5. 哪些检查可以更早暴露问题？
6. 哪些命令、脚本、测试或分析可被复用？
7. 对关键算子而言，案例开始前的判断是什么，本次确认、细化或反驳了什么？
8. 这项知识差量能让下一次该算子优化更早执行哪个检查、跳过哪个无效方向或提出哪个更深入的实验？

沉淀位置：

- 案例结论、适用边界、关键失败及证据入口写入案例摘要。逐轮测量和回退细节更新同一个模型实验文档，原始脚本、日志、补丁和 trace 归入对应外部案例目录。
- 历史记录保留原 schema 与实际状态，不追认符合新规则；缺失的镜像谱系、挂载 diff 或正式精度按缺口记录。验收配置和未完成状态可保留在 acceptance 以便导航，未达标实验数据仍留 optimize。
- 模型/平台产物固定分为三类：`baseline/` 保存优化前基线，`optimize/` 保存当前优化状态和逐点结论，`acceptance/` 保存最终候选验收状态。三个目录都以供 Agent 读取的 `state.yml` 和供人查看的 `README.md` 为入口；`optimize/README.md` 是多轮总览，每个优化点另有一个直接位于 `optimize/` 的 `<experiment-id>.md`，具体要求见 [模型产物契约](model-artifact-contract.md)。不得在平台根部再建立并列结果目录。
- 某个算子的环境、benchmark、patch、原始回执和逐轮过程文件保存在远程 case 目录或目标源码仓库；模型 `state.yml` 保存 revision、SHA、外部路径、结果和决策，`<experiment-id>.md` 保存该优化点的方向、内容与效果，README 汇总多轮进展，关键算子知识库只建立证据卡。
- 由算子案例改变的诊断检查、适用边界、候选顺序、反例和停止条件：算子 `optimization-map.md`。
- 算子稳定语义、数据流、实现或跨案例性能模型：算子 `README.md`；单个新数字不进入稳定正文。
- 跨案例可复用的工作顺序、门禁或决策标准：本 SOP。
- 通用自动化：`scripts/`、`benchmarks/` 或 `unit_tests/`。`test/` 只保存需要在目标环境中实际执行的评测和性能工具。

案例收尾时清理一次性文件：硬编码 PID/容器名的一次性启动、安装、停止、监控、替换和核验脚本，在其有效结论已写入 `state.yml`、对应 `<experiment-id>.md` 和 README 后从模型目录移除；仍需复现且可跨模型复用的脚本必须参数化并迁入公共工具目录。瞬时机器状态只保留稳定字段和外部产物位置，不保存很快失效的 TXT dump。已完成的性能测试必须在对应优化点文档及 baseline 或 optimize README 中给出实际结果表；未得到数据时必须明确写状态、原因和下一触发条件。

## 9. SOP 更新规则

允许更新 SOP 的条件：

- 新案例证明现有步骤会导致错误结论或明显浪费。
- 新检查能稳定提前发现某类问题。
- 一个优化模式达到 `transferred` 级别且适用边界明确。
- 正确性、安全性或测量有效性要求形成新的 `invariant`。

每次更新必须在下方记录：日期、案例、原规则、变更、证据等级、预期收益和风险。不要仅因为一次实验成功就增加强制步骤。
