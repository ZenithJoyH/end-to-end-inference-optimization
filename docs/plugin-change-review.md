# Plugin 优化设计与 PR 准备

`vllm-plugin-FL` 的优化以框架长期维护为约束：在当前 workload 获得端到端收益，同时保持既有的多模型、多平台抽象、配置契约与默认行为。合理的硬件/shape 特化可以保留，但适用边界必须可解释、可测试，非目标路径不能被意外改变。

本规范是用户指定的工程要求，不是上游维护者已确认的贡献规范。具体目录、接口、风格和检查命令，以目标 Plugin revision 的 README、贡献指南、相邻实现、测试和 CI 配置为准；[本地架构分析](vllm-plugin-FL-analysis.md) 仅用于定位。核对当前代码不意味着自动同步升级或覆盖已有修改。

## 1. 修改前先说明设计归属

每项 Plugin 候选在案例 `optimize/` 的实验记录中，用一小段文字说明：

- 当前调用链、瓶颈及需要改变的语义/执行组织；复用的扩展点和相邻实现。
- 为什么改这一层：配置、OOT/registry、dispatch policy、backend adapter、模型 shim 或 Worker/ModelRunner；为何更窄的改动不足。
- 适用能力、模型结构、shape/dtype/layout、平台及执行模式；受影响的共享调用方和非目标路径。
- 默认选择、兼容/fallback、依赖版本、状态/缓存生命周期，以及用于否证设计的首个测试。

可直接写入已有实验记录，不额外建立审批流程。已有 Plugin/FlagGems 修改授权继续有效。纯配置实验按影响说明即可，不为了填表扩展设计。

## 2. 按框架职责落代码

| 变化 | 默认归属与要求 |
|---|---|
| 实现选择/支持范围 | 复用既有 registry、dispatch policy 和 capability/support 判断，避免在多个调用点复制选择逻辑 |
| 平台实现与可选依赖 | 放在相应 backend/平台适配边界；通用模块导入不能要求其他平台安装该 vendor SDK |
| 模型语义差异 | 放在模型 shim 或显式模型配置边界；仅当语义由架构身份决定时按架构路由 |
| FlagGems kernel 实现/调参 | 修改实际 FlagGems 实现；Plugin 负责必要的契约适配，不复制一份算子只为减少跨仓库修改 |
| 调度、graph、KV 或通信组织 | 使用对应框架扩展点；进入 Worker/ModelRunner 前证明共享路径修改必要，明确所有受影响调用方 |
| 临时兼容 patch | 仅在正式扩展点不足时使用；限制符号/能力/版本范围，幂等、可观测、可回退，并说明未来删除条件 |

沿用目标 revision 的接口和风格；不另造一套 dispatch、配置优先级或设备检测框架。公共调用方表达所需能力，平台 backend 提供实现。避免引入反向依赖或 import cycle。

## 3. 特化必须有边界

- 性能选择优先依据真实能力和工作形状，包括 TP 后每 rank 的有效形状、dtype、stride/layout、设备架构与 eager/graph。不能仅凭 served-model-name、权重路径、Host、端口或容器名选择 kernel。
- 正确性支持条件与性能调优条件分别说明。某个输入能计算，不代表在所有支持输入上都更快；tile、阈值和白名单应记录证据及边界，不将一次最优值升级为全局默认。
- 尽量复用已有配置/策略入口；仅在确有用户可控需求时增加新配置。实验开关不自动成为公共 API，不为每个案例新增永久环境变量。
- 不支持的输入在执行前走既有正确路径，保持原配置优先级、返回值、dtype/device、别名与原地更新语义。已选择实现的执行错误不能被新增的宽泛异常捕获静默吞掉；遵循原有 strict/fallback 语义并证明命中。
- vendor 库按现有项目机制条件加载；依赖缺失时，未选该 backend 的平台仍可导入、注册和使用原路径。选择该能力却不可用时给出明确诊断。
- 不把当前卡数、CUDA 兼容表现或驱动版本当作其他平台的共同能力；使用框架现有能力接口。通用路径不得增加无条件的平台专属初始化或设备同步。
- hook、注册与可变状态遵循原有 worker/fork 生命周期。缓存的 key 和失效条件覆盖实现选择实际依赖的属性，防止先运行的模型或 shape 污染之后的选择。

## 4. 验证按影响范围组织

无需为了局部候选启动全部模型/平台，但必须先识别共享调用方，再选择代表性正例、反例和边界。每项结果标明 `executed_passed`、`executed_failed`、`not_run` 或有理由的 `not_applicable`。

| 范围 | 最低验证内容 |
|---|---|
| 目标路径 | 实际 backend 命中、数值/行为、同条件端到端收益与回退 |
| 同模型的非目标输入 | 支持条件两侧、不同 batch/长度/dtype/layout、空输入及 fallback；按算子契约选择有效组合 |
| 共享调用方/其他模型结构 | 复用同一入口的代表性调用契约测试；改通用状态/调度时增加相应集成回归 |
| 非目标平台/无 vendor 依赖环境 | 导入和注册、能力选择及旧路径保持；可用的 mock/静态测试只证明路由与隔离，不能代表设备运行或性能通过 |
| 执行模式与生命周期 | eager；graph capture 加至少两次 replay；重复注册、worker/fork、缓存重新选择等与改动相关的路径 |
| 工程检查 | 目标 Plugin 仓库实际要求的格式、lint、类型/单元/集成检查；不是只运行本控制项目的 unit_tests |

跨平台硬件暂不可用时，记录未测项、可在本地证明的边界、应交给哪个现有 CI/平台 runner 的测试及剩余风险。不声明“全平台通过”，也不无目标地连接其他 Host。共享默认行为的变更需要更强的共享路径证据；证据不足时缩小作用域、维持原默认或标记待验证。

## 5. 从实验补丁到 PR 候选

实验允许使用小范围诊断开关和命中日志；形成 PR 候选前复核最终 diff：

1. 移除一次性计时、路径/PID、实验专用日志和临时侵入式 patch；保留复现所需的参数化测试、必要诊断及回退机制。避免无关格式化、重命名、重构和依赖升级。
2. 改动大小按清晰职责控制，不能为少几行把平台特例塞进通用路径；也不为未来未出现的需求过度抽象。跨层改动分别说明必要依赖和收益，不简单相加。
3. 实验代码经过整理后，重新核验最终源码内容、导入与命中，并运行受影响的正确性/性能检查。整理前的最佳 benchmark 不能自动证明整理后的 patch。
4. Plugin 与 FlagGems 分别保存基线、最终补丁和测试；说明跨仓库依赖、所需版本/能力及依赖尚未落地时的行为，避免 Plugin 隐含依赖未发布符号。
5. 检查拟提交基线与目标支持的 vLLM/Plugin 版本；只读比较差异即可，不擅自同步、提交、推送或创建 PR。
6. 在最终报告中给出可用于 PR 的问题描述、设计理由、作用范围、验证结果、端到端对比、未测项和回退方法。描述最终代码，不罗列已经放弃的实验过程；完整过程仍保留在案例中。

性能结果和 PR 准备状态分别记录：`pr_readiness=experimental|needs_revision|ready_for_review`。`ready_for_review` 仅表示补丁与证据已整理到可交由维护者评审的程度，不代表上游接受或所有平台实测通过。若收益依赖破坏框架契约的改法，可以保留实验观察，但应修订设计，不能因为当前 benchmark 更快就视为最终 PR 方案。
