# 推理框架插件开发规范v1

本规范适用于 `vllm-plugin-FL` 与 `sglang-plugin-FL` 的模型接入、平台适配及运行时开发。文中的【必须】代表硬性交付要求；【应该】代表默认最佳实践，如确有理由采用其他方案，需在改动说明中写明原因及验证方式。未标注具体项目的条款默认同时适用于两个仓库；标注【项目特例：项目名】的条款仅适用于对应仓库。代码目录结构及项目专属检查项，均以目标仓库的当前约定为准。

**阅读指南：** 建议先通读开发综述，再根据具体任务查阅关键条款。点击综述中的编号链接可直接跳转至完整条款；若直接阅读原始 Markdown，也可通过搜索 `#### A1` 等条款标题进行定位（阅读至下一条款或分组标题即可）。未涉及的专用场景无需全部通读，但触发相关条件或项目特例时，仍需严格按对应条款执行。

## 1\. 开发综述与按需阅读

### 1\.1 职责划分与仓库结构

在整体架构中，推理框架负责组织模型、请求与资源，而算子库负责实现具体的数值计算。通用计算逻辑应归入 `FlagGems`，依赖 vLLM 或 SGLang 特有契约的计算则归入对应的专用算子库。开发前请先核对主线分支与依赖库中的既有能力，再决定是直接复用、扩展还是迁移；具体边界详见 A1、A3、A4。

下表中的 `P` 代表 `vllm_fl` 或 `sglang_fl`。表中路径仅用于说明模块职责；若目标分支已存在等价入口，请直接复用，切勿为了对齐目录形式而另建平行机制。

|层次与落点|核心职责|对应细则|
|---|---|---|
|`P/` 下现有模型模块|模型定义、权重加载、processor、多模态及前向编排；vLLM 通常位于 `models/<model>/`|A2|
|`P/platform.py` 及平台钩子|设备身份识别、能力探测、平台默认值、attention/graph 后端选择|A2、B3、B5|
|`P/dispatch/`（契约、注册、策略、调用桥与配置）|在上游调用点完成实现分发；策略配置沿用现有的 `dispatch/config/` 或等价入口|B1、D4|
|`P/dispatch/backends/`（通用、`vendor/`、`reference/` 后端）|通用 API 接入、真实厂商适配、独立参考实现；厂商 `impl/` 目录仅保留必要的薄适配层|A1、A2、B2|
|模型或平台 patch 入口；厂商的 `patch.py`、`patches/`|集中安装上游补丁，并严格限定其作用范围|C2、C3|
|现有运行时模块|请求元数据、通信、cache、workspace、stream 及生命周期管理|A3、E1、E2、E3、E4|
|现有测试、`examples/`、README 与必要用户文档|验证代码行为，并提供真实可用的用户入口|F1、F2、G1、G2|

新增后端实现的标准调用链路为：**模型或运行时通过既有调用桥进入统一分发层，再由命中的后端调用算子库公开 API 或厂商原生 API。** 模型侧应正常复用现有网络层与公开入口，不得绕过分发策略私自建立选择链路。详见 B1、B2。

### 1\.2 标准改动流程

1. **确认基线与代码归属。** 阅读目标仓库的开发指引，梳理当前实现与上下游调用方，明确代码的合理落点与复用方式。详见 A1、A2、A3、A4。

2. **定义契约并打通入口。** 严格对齐上游行为，补齐分发逻辑与必要补丁；必须在执行前完成实现选择，一旦开始执行，遇到错误应直接向上抛出。详见 B1、B3、B4、C1。

3. **根据影响面开展验证。** 接线测试需检查实际命中的后端，数值测试需对比独立参考实现；若改动涉及计算图、并发、安装构建或 CI，需进一步阅读并落实对应条款。详见 F1、F2、F3、F4、F6。

4. **交付完整可用的结果。** 跨仓库改动需遵循“先交付算子 API，再接入框架并锁定依赖”的顺序；接入新模型或新厂商时，需同步更新 README 支持列表并提供真实可运行的 example，验证结果统一附在 PR 或 CI 中。详见 D3、F5、G1、G2。

## 2\. 关键条款

本节完整保留 A1–G2 的条款编号与约束强度。前文综述仅作快速定位之用，具体的适用条件与执行标准请以以下条款为准。

### A\. 代码归属与架构边界

#### A1【必须】按模块职责选择目标仓库

|代码内容|归属仓库|
|---|---|
|模型结构、配置、权重加载、processor、多模态接线、运行时编排|对应的推理框架插件仓库|
|跨框架的通用基础算子|`FlagGems`|
|面向 vLLM 特定契约的数值算子|`FlagGems-vllm`|
|面向 SGLang 特定契约的数值算子|`FlagGems-sglang`|

凡是新增归一化（Normalization）、激活函数、RoPE、Attention、MoE、量化、FP8 编解码以及 KV 数值读写等具体计算逻辑，均须归入对应的算子库。框架侧仅保留调用与编排逻辑，严禁直接复制 kernel 代码或通过私有文件加载算子实现。

#### A2【必须】模型、平台、分发与厂商代码严格分层

- 模型定义、权重映射、输入处理及模型特有的编排逻辑，应归入模型模块；【项目特例：vllm\-plugin\-FL】通常置于 `vllm_fl/models/<model>/` 目录下。

- 设备能力探测、平台默认值、attention/graph 后端选择应归入平台层；公共 op 契约、注册、策略及调用桥则应置于现有的 `dispatch/` 目录。

- 厂商专属的实现适配与注册应放入现有的 `dispatch/backends/vendor/<vendor>/`；纯参考实现则放入 `dispatch/backends/reference/`。

- 上游补丁应归入对应平台或模型的 patch 入口；厂商专属补丁由该厂商模块负责统一安装。

SGLang 插件请沿用当前仓库既有的模型接入位置。若未找到完全一致的示例目录，应先定位职责相同的现有入口，切勿擅自新建平行架构。

#### A3【必须】职责混合的模块需按符号职责拆分

请求与 token 映射、slot 与 block table、有效索引计算、复制计划生成，以及长期 cache、跨调用状态和图执行 workspace 的分配与生命周期管理，均归属框架侧；而根据映射关系读写实际 KV 数值、执行量化或数据格式转换，则归属算子库。需要明确的是：请求与调度相关的 metadata 处理（哪怕底层使用了 GPU 或 Triton 实现）依然归属框架侧；但基于模型分数的评分、排序或 Top\-k 计算则属于算子计算，不能仅因其输出结果为索引就误归入 metadata。关于资源分配的具体边界详见 E2。

针对 cache、gather/scatter、pool、indexer 等模块，需逐一检查各个函数的实际读写对象；若同一个函数同时承担了上述两类职责，必须将其拆分为“框架侧准备 metadata”与“算子侧消费 metadata”两个独立接口。对于插件内历史遗留的数值计算实现，若与当前任务无关则不强制迁移；若任务明确要求迁移，则必须在保持行为一致的前提下同步迁移相关测试。

#### A4【必须】优先复用已有实现，确有必要再新增

在编写新代码前，必须先检查当前主线与依赖库，逐一比对参数列表、默认值、dtype、stride、mask、状态写入方式以及错误语义。请注意，“函数同名”并不代表“契约相同”。若既有 kernel 已满足契约但缺少公开调用入口，应在算子库中补充薄封装 API；若存在语义差异，则应通过扩展现有实现或新增语义明确的变体来解决。

### B\. 分发与后端选择

#### B1【必须】新增计算入口必须接入统一分发机制

插件内新增或替换的后端实现，必须接入既有的统一分发层，并完整补齐公共 op 契约、算子注册、后端实现、调用桥以及必要配置，确保模型调用入口能够顺畅路由至目标实现。当模型正常复用上游或仓库既有的网络层与公开入口时，请沿用现有调用链；模型代码与厂商适配层严禁私自建立分支选择链路，更不得在 `forward` 函数中绕过分发策略直接调用通用算子库。

#### B2【必须】厂商后端仅允许注册真实的厂商实现

通用算子应统一通过通用后端接入，纯参考实现应归入 reference 后端。厂商后端在实现时可以调用所需的厂商原生 API，但严禁将等价于参考实现的代码副本注册到厂商后端中，以此冒充厂商支持能力。此外，厂商名称必须与现有的设备检测、目录命名及配置映射保持严格一致。

#### B3【必须】在算子执行前完成能力判断与后端选择

平台身份识别必须统一使用项目既有的检测入口；判断具体算子或硬件能力时，需检查实际 API、函数签名、设备属性，或执行无副作用的行为探测。仅仅是“Python 包可成功导入”或“版本号满足条件”，并不能单独作为能力可用的充分证明。此外，必须在明确当前平台与执行路径之后，再去按需加载专属的可选依赖。

#### B4【必须】计算开始执行后产生的错误必须直接向上抛出

只有在计算尚未开始执行、且未产生任何副作用的前提下，才允许按既有策略回退（fallback）至其他支持同一契约的实现，或者直接明确报错。一旦原地写入（in\-place write）、状态更新、异步 kernel 发射或通信原语（collective）已经开始执行，严禁通过捕获异常来切换后端进行重试。

#### B5【必须】接入新芯片厂商时需全面核对平台能力与部署链路

新厂商接入时，需逐项核对设备识别、厂商后端目录与注册、per\-op 分发策略、平台默认参数、通信后端、设备能力特性以及图执行模式；若涉及多卡并行，还需验证实际的 collective 通信后端。同时，需按照仓库现有结构补齐对应的安装依赖、平台测试配置、CI 路由规则及容器镜像配置，绝不能仅注册一个设备名称就视同完成接入。若有部分检查项确实不适用，需在改动说明中明确阐述原因。

### C\. 上游契约与补丁管理

#### C1【必须】逐项对齐上游接口行为与契约

适配或替换实现时，必须全面核对参数列表与默认值、返回值结构、dtype、layout、mask、缩放因子（scale）、舍入模式、原地修改行为、内部状态更新、异常抛出类型以及支持边界。对于尚未实现的参数或参数组合，必须在配置解析或调用入口处显式拦截并报错，严禁在接收参数后静默忽略。

#### C2【必须】上游补丁需严格限域、集中管理且保证幂等

补丁（Patch）应仅在目标平台、目标模型及特定运行条件下生效，确保其他平台与常规模型的原有行为不受干扰。所有补丁必须通过对应的 patch 入口统一安装，且必须保证幂等性（即重复初始化时不会层层叠加 wrapper），同时严禁在导入通用模块时无条件触发厂商补丁的安装。

#### C3【必须】存在相互依赖的补丁必须原子化安装

安装一组相互依赖的补丁时，必须先验证所有必需的 API 与函数签名均符合预期，随后一次性完整构造替换对象并完成挂载。若安装过程中任一环节失败，必须将所有已修改的对象及既有 wrapper 完整回滚至安装前的状态，绝不能遗留“半安装”状态，更不能将安装失败的结果缓存为成功。

#### C4【应该】基于“特性能力”而非“版本号”编写兼容分支

处理上下游兼容逻辑时，分支判断应以具体能力（capability）命名，并保留显式参数传递与原生语义；读取上游状态时应直接访问真实数据源，避免在插件内维护容易失步的状态副本。若上游确实缺乏可靠的公开能力标志，可采用对真实模型状态无副作用的行为探测，但探测结果的缓存必须具备明确的初始化、复用与失效机制。

### D\. 配置、开关与依赖管理

#### D1【必须】新增配置开关前需先回答五个核心问题

在决定引入任何新开关之前，请先核实以下五个问题：

1. 现有的配置项、输入形状（shape）或硬件能力判断，是否已经足以表达该行为？

2. 该开关由谁负责设置？其作用范围涵盖哪些模型与硬件平台？

3. 开关未显式设置时的默认行为是什么？是否会意外改变其他模型的既有行为？

4. 配置项从顶层入口到底层实际读取点的传递链路是否已经打通？多个配置间的优先级是否清晰明确？

5. 是否已同步准备好用户文档，并补齐了“启用、禁用、未设置”三种状态下的测试用例？

凡是能通过现有机制自动推导的内部策略，一律不得新增重复开关；在修改共享配置对象前，必须先进行深/浅拷贝，防止污染其他模型或运行时实例。

#### D2【必须】删除或调整开关时需彻底清理整条调用链

移除或变更开关时，需全面排查代码、测试用例、文档、构建脚本、CI 配置及部署脚本中**实际存在**的所有读取点、默认值定义与环境变量注入点。清理实验性路径时，必须将无用的调用链一并移除，不得采用“重命名开关”或“硬编码为 false”的方式变相保留死代码；清理过程中需确保正常的模型推理与多模态功能不受影响。

#### D3【必须】跨仓库依赖必须使用公开、可获取的固定版本

跨仓协同开发时，必须严格遵循“算子库交付公开接口与测试 → 框架侧接入适配 → 锁定依赖版本”的交付顺序。依赖配置应优先使用正式发布的版本号；若确需锁定特定提交，必须使用团队成员均可访问的公开 Commit SHA，且需保证安装文档与构建配置完全一致，严禁依赖个人私有分支或随时变动的浮动分支。

#### D4【必须】平台配置需保持单一事实来源并明确覆盖语义

平台特有的参数应置于平台专属配置或平台钩子中，严禁直接写入会影响所有平台的全局共享模型配置。当修改算子黑名单（blacklist）、白名单（whitelist）或环境变量覆盖逻辑时，必须清晰定义默认值的来源、配置间的“整体替换”或“增量合并”语义、最终生效值的计算规则及优先级顺序，并针对覆盖前后的行为编写测试；此外，各类诊断或调试开关在默认状态下不得产生写文件等外部副作用。

#### D5【应该】临时性算子黑名单应明确退出条件

因兼容性或数值正确性问题需要临时禁用某个算子或后端时，应在代码注释或配置说明中清晰记录适用的硬件平台、具体触发条件、失败表象以及可追踪的修复任务链接；待问题修复并验证通过后，应及时移除黑名单或收窄其禁用范围。切勿通过不断扩大永久性全局黑名单的方式来掩盖底层问题。

### E\. 状态、内存与图执行（Graph Execution）

#### E1【必须】如实声明张量原地修改（Mutation）与 Cache 契约

在定义函数接口与 PyTorch custom\-op schema 时，必须如实声明所有的原地修改（in\-place mutation）、输出张量别名（aliasing）以及底层存储（storage）共享关系；对 cache 的写入时机、padding 处理、无效 slot 填充规则及返回值结构，均须与上游框架保持完全一致。在 MoE 等复杂结构中，还需严格保持 router 权重计算、残差连接、shared expert 以及通信原语（collective）的执行顺序、调用次数与必要的中间层 dtype。

#### E2【必须】由框架统一管理 Workspace 的所有权与生命周期

框架层全面负责长期 cache、跨调用状态以及图执行（Graph）workspace 的内存分配、显存预算评估、空间复用、资源释放及并发隔离边界。图捕获（capture）所需的显存空间必须在显存预算阶段及捕获开始前准备就绪，并在整个图重放（replay）生命周期内保持内存地址稳定有效。算子 wrapper 仅可根据接口契约分配常规输出张量及单次调用内的临时缓冲区；一旦涉及固定内存地址、跨调用复用或跨 stream 共享，必须由上层调用方明确接管所有权与同步责任，以满足图执行与并发安全的要求。

#### E3【必须】异步执行需建立明确的 Stream 依赖关系

涉及异步算子发射或异步通信时，必须基于当前的实际执行流（current stream）或图捕获流（capture stream）建立显式的依赖关系，确保在下游消费计算结果前完成必要的同步；实现时应优先复用框架既有的 event 与调度机制。注意：在初始化阶段或仅完成 kernel 下发（launch）时打印的日志，严禁表述为“计算已完成”或“数值校验已通过”。

#### E4【应该】复用长生命周期资源并支持异常时的回滚清理

对于 CUDA stream、通信句柄（communicator handle）等开销较大的长生命周期资源，应按设备、进程或实际资源归属进行缓存与复用，避免在逐 token 生成的热路径（hot path）上重复创建，并在生命周期结束时统一释放。当多个有状态组件按顺序依次启动时，若后续步骤发生失败，必须对前面已成功初始化的组件执行回滚与清理，并专门针对此类失败路径补充单元测试。

### F\. 测试、交付与验收

#### F1【必须】全面测试实际分发链路与异常失败路径

测试必须从真实的业务调用入口发起，断言最终命中的后端实现及参数转发的准确性；测试用例需完整覆盖“未命中分发条件”、“缺失可选硬件能力”、“执行中途报错不重试”以及“其他非目标平台不受影响”等边界场景。请注意：使用 mock 或 stub 仅能证明调用链路（接线）畅通，不能作为算子数值计算正确的依据。

#### F2【必须】数值正确性测试需采用独立参考实现并覆盖完整契约

数值测试必须与独立的参考实现（reference）进行比对，并全面覆盖受改动影响的各种 shape、dtype、stride、mask、边界值以及内部状态更新。测试脚本可以导入被测入口，但用于生成期望值（expected）的参考逻辑严禁直接调用被测实现，也不得与被测代码共享任何可能引入相同错误的中间计算过程。开发过程中允许修复编写有误的测试逻辑，但严禁通过毫无依据地放宽误差容忍度（tolerance）、删除核心断言或直接跳过（skip）本应支持的场景来掩盖真实缺陷。

#### F3【必须】涉及图模式的改动需验证真实的 Capture 与 Replay

凡是涉及图执行（Graph Execution）的代码改动，测试中必须执行真实的图捕获（capture）与图重放（replay）；在触发 replay 前需主动更新输入张量，并对独立的输出缓冲区预先填充哨兵值（sentinel values，如 NaN 或特定常数）以防读取残留旧数据。对于包含原地修改、张量别名或内部状态更新的路径，每次验证前必须重置输入与状态，确保独立参考实现与图重放从完全相同的初始状态出发，再比对两者的最终结果。测试需覆盖本次改动所涉及的各类 batch size、并发请求、分布式并行及 cache 读写场景，严禁拿空图、未更新的旧输入或残留的旧输出充当测试通过。

#### F4【必须】提交代码前需完成所有适用检查并如实说明未验证项

提交 PR 前，必须运行与本次改动相关的代码格式化、单元测试、编译构建及真实硬件测试；若改动涉及打包安装，还需验证实际生成的构建产物与依赖入口是否正常。在 PR 描述中，需如实记录本次测试所基于的 Commit、运行环境、实际执行的检查项结果以及受客观条件限制未能验证的范围；当缺乏目标硬件环境时，必须明确注明，严禁将静态语法检查、CPU 模拟、stub 桩测试或历史提交的测试结果包装成“当前代码已通过真实硬件验证”。

#### F5【应该】单个 PR 应聚焦于单一、易于评审的主题

每个 PR 应仅提交与当前主题直接相关的业务代码、依赖变更、算子注册、测试用例及必要的用户文档；提交前需主动清理死代码、重复注册逻辑、临时调试探针、一次性验收日志、废弃的实验性开关以及无关的格式化改动。若确实需要调整公共基础设施，必须在 PR 中明确说明影响范围，并全面验证所有受影响的上下游调用方。

#### F6【必须】CI 门禁必须能够准确拦截“任务未运行”与“配置错误”

当新增硬件平台支持或修改 CI 流水线时，需全面检查平台自动发现、任务路由分发、代码分支检出（checkout）以及前序依赖任务的传递结果；任何配置错误或必跑任务的失败，都必须直接触发 CI 门禁失败（Fail）。若所有硬件测试任务因条件配置不当被意外全部跳过（Skip），CI 门禁绝不能将其判定为通过（Pass）；端到端推理测试不仅要检查进程的退出码（Exit Code），还必须对实际生成的推理输出内容进行校验。此外，在解决分支合并冲突后，必须针对合并后的最新代码重新运行所有受影响的检查项。

#### F7【必须】严格遵守项目的日志规范、版权声明与代码格式要求

源码注释、日志输出及异常报错信息必须统一使用英文编写；运行时输出信息必须使用项目统一的 `logger` 组件，严禁使用 `print` 语句替代正规日志。所有新增或改编自外部项目的源码文件，均须严格遵守目标仓库现行的版权头（Copyright Header）与开源来源声明规范；提交代码前必须运行仓库配置的 formatter、linter 及 pre\-commit 钩子，严禁通过强行跳过格式检查的方式来绕过 CI 门禁。

### G\. README、示例脚本与文档维护

#### G1【必须】完成新模型或新芯片厂商适配时，需同步更新 README 并交付可用示例

完成新模型适配后，必须在仓库 README 的“支持模型列表”中补充模型名称、当前实际支持状态以及对应的 example 脚本链接；完成新芯片厂商适配后，同样需在“支持芯片/厂商列表”中补充厂商名称、实际支持状态及 example 链接。维护时请严格遵循仓库既有的表格格式；若目标仓库尚无对应表格，则应新建结构清晰的列表或等效的导航入口。

表中提供的链接必须指向随本次 PR 一并提交的真实 example 脚本，或是仓库内既有的、经验证确实适用的脚本；必须确保脚本本体能够真实运行，严禁只添加死链接或提交空洞的占位文件。示例脚本应按仓库约定置于 `examples/` 或既有示例目录下，并在脚本或配套说明中清晰给出必需的运行参数、依赖项、启动命令及适用硬件平台；脚本内部严禁硬编码访问密钥、个人本地路径或特定私有环境配置。提交前请务必验证文档链接的有效性及脚本入口的可用性，确保所填写的“支持状态”与实际完成的适配范围完全一致。

#### G2【必须】README 与 `docs/` 目录仅用于承载需要长期维护的用户信息

除 G1 所述的新模型、新厂商适配场景外，仅当发生重大功能演进，或现有用户的安装步骤、配置方式、调用接口、兼容性范围发生实质性改变且确有必要向用户说明时，才允许修改 README 或在 `docs/` 目录下新增、更新文档。更新时应优先在既有文档入口上补充，切勿为了常规的 Bug 修复或单次性能调优而随意新建零散文档。

单次改动的 benchmark 性能数据、临时测试结果、验证过程日志以及阶段性的实验结论，应统一填写在 PR 描述正文或作为 CI 构建产物留存，严禁直接写入 README，也不得作为过程性报告提交至 `docs/` 目录；唯有需要长期向用户公开的功能使用方法与已知限制条件，才应按实际需求沉淀至正式的用户文档中。
