# 20260922-p32k-moe-align-ep-33 P32K MoE align EP 路径特化

- 状态：`experimental_installed_user_e2e_hit_unproven`
- 分类：`operator/improve`
- 父场景：`p32768-d1024-c64-n128`
- 主变量：使 `stage2_padded_vec` 覆盖生产 `expert_map != None` 与 Decode `M=64`

## 动机与边界

历史 small-M 候选在 `M=32/E=288/topk=8/BLOCK_M=16` 的完整 align 调用上为
`3.6292×`，但服务 trace 中新 kernel 命中数为 0，老 stage2 仍执行 2772 次。
生产 EP 路径的 `expert_map` 使原 selector 的 `expert_map is None` 条件不成立；
后续运行时复核还发现，当前 Plugin 的 align 入口根本未接到此 selector。

本实验只改这一个接入边界，并把上限扩到当前 P32K Decode 的 `M=64`。
不改 GEMM、router、EP 映射语义或 MBT。

## 门禁

1. 针对 16 个代表性 EP map，候选与原 4-stage 的 `sorted_ids`、有效
   `expert_ids` 及 `num_tokens_post_pad` 一致。
2. `M=10/16/32/64`、`topk=8`、`E=288`、`BLOCK_M=16` 完成 graph capture 和
   至少两次 replay。
3. `M=64` 完整 align 调用加速不低于 `1.25×`；任一数值/图门禁失败则
   在服务前回退。
4. 进入服务后先用 trace 确认新 kernel 真实命中，再运行同配置
   P32K 缩减 Mixed A/B/R；未命中不得解读吞吐差异。

## 结果

算子门禁通过：16 个代表性 EP map × `M=10/16/32/64` 的有效
`sorted_ids/expert_ids/num_tokens_post_pad` 与原路径精确一致，四个
shape 都完成 graph capture 和两次 replay。完整 align 调用结果：

| M | baseline | candidate | 加速 |
|---:|---:|---:|---:|
| 10 | 0.07122 ms | 0.02282 ms | 3.1209× |
| 16 | 0.07200 ms | 0.02384 ms | 3.0201× |
| 32 | 0.07424 ms | 0.02592 ms | 2.8642× |
| 64 | 0.07482 ms | 0.02636 ms | 2.8384× |

服务门禁不通过。候选在 `max_num_seqs=64 / MBT=32768 / prefix cache off`
下完成了 16-rank 加载、244.55 s 编译和 11 个 Decode graph capture，但第一批
`P1024/D64/C64/N64` 请求后 16 卡利用率降为 0，EngineCore 在 23:55:45 和
23:56:45 连续报告等待 worker 共享内存回执，无任何请求完成，也未生成有效
trace。当时的单 rank graph replay 未覆盖这次 TP16 服务停滞；后续用户测试的
服务走另一条 align 路径，不能据此将停滞归因于本补丁。

按预冻结停止条件，本 Agent 未将候选晋级为正式性能候选，也未进入 P32K
A/B/R。诊断服务停止、8011 关闭后，`moe_align_block_size.py` 和 thead
`fused_moe.py` 曾分别恢复为 `f07fa043...` 和 `f70ff827...`，仓库状态与实验前
一致。

## 2026-09-23 调用链补充确认

只读核对运行容器内的 Plugin、FlagGems 和 FlagGems-vllm 源码：

- `vllm_fl.ops.fused_moe.fused_moe.fused_experts_impl` 在 chunk 内调用
  `CachedOp("moe_align_block_size")`，随后单独调用
  `CachedOp("invoke_fused_moe_triton_kernel")`。Plugin 的
  `FlagGemsBackend.moe_align_block_size` 转到 `moe_align_block_size_flaggems`，
  后者直接导入 `flag_gems.moe_align_block_size_triton`。`TritonExpertsFL`
  另有仅 NVIDIA 可走的 FlagGems 整合 fast path；`PlatformFL.is_cuda()`
  同时要求 `vendor_name == "nvidia"`，因此 T-Head 不走该分支。
- Plugin 中的 FlagGems-vllm 导入仅用于已对齐张量的 GEMM launcher；
  对 Plugin Python 源码搜索未发现 `moe_align_block_size_no_tle` 或
  `flaggems_vllm.fused_experts_impl` 调用。候选
  `moe_align_block_size_stage2_padded_vec` 只在 FlagGems-vllm 的
  `moe_align_block_size_no_tle` 中使用，其 thead `fused_experts_impl` 才会
  根据修复后的 `M=10..64/topk=8/E=288/BM16` selector 打开它。
- 旧服务 trace 的老 `stage2` 2772 次、新 `stage2_padded_vec` 0 次与
  此路径不命中一致。当前启动日志的 16-rank `default.flagos` 是选择记录，
  不是调用计数；当前服务未重新采集候选 trace，故保留“未证明当前服务
  任何请求命中”的严谨表述，而不从启动日志单独断言动态调用次数。

下一步须保持 MBT32768 不变，在 Plugin 窄 dispatch 边界接入 FlagGems-vllm
候选，保留原 FlagGems fallback；先验证生产 shape/EP 数值及 graph、取得
16-rank 服务 kernel 命中，再做同配置 P32K Mixed A/B/R。已运行的服务不因
本次只读确认而中断或修改。
上表 2.84×–3.12× 是 FlagGems-vllm 内部候选与其原 4-stage 实现的对照，
不是当前 Plugin→FlagGems 实际基线的加速比；接入前还须重新做这两条
完整 align 调用的同 shape 对照。
