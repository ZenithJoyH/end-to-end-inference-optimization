# 20260914-mbt4096-scout：max-num-batched-tokens 4096

- experiment-id：`20260914-mbt4096-scout`
- 分类：`framework`
- 状态：`rejected_and_reverted`
- 目标场景：`P4096/D32/C8/N8`

## Hypothesis

At fixed P4096, increasing the scheduler token budget from 2048 to 4096 should
reduce chunked-prefill scheduling overhead and improve end-to-end output
throughput. All other service, cache, workload and client settings remain fixed.

## Scope

- Search workload: `P4096/D32/C8/N8`, one warmup plus two measured rounds.
- Primary metric: output throughput, minimum improvement 5%.
- Guardrails: P99 TTFT, P99 TPOT and total-token throughput.
- This is a P4K scout only. A retained candidate still needs a higher-pressure
  P4K checkpoint before any broader claim.

The candidate reuses the same task-private compile-cache directory as the
baseline. Each role includes a warmup round, so both measured roles consume a
warmed cache while avoiding a cache-location change as a second variable.

## Baseline result

`baseline-2048-p4k-scout-02` completed with two measured rounds. Output
throughput was 0.331100 and 0.331106 tok/s (median 0.331103); total-token
throughput median was 42.7123 tok/s. P99 TTFT/TPOT medians were 764650.05 ms and
21425.45 ms. The maximum relative spread among required metrics was 0.591%.

## Candidate correctness

The candidate service manifest recorded exactly two equivalent representations
of the same change:

- `/launch_config/max_num_batched_tokens`: `2048 -> 4096`
- `/launch_config/launch_args/20`: `2048 -> 4096`

The fixed chat smoke plus C8 minimal regression completed 9/9 requests with
exact expected outputs. The native result is
`/mnt/nfs/users/jinghao/hy4-preview/optimize/20260914-hy4-preview-ppu-e2e/results/candidate-4096-sanity/result.json`
(SHA256 `69d409302cbe53ce93deaf77c226d539dffb14c44f558ea7c4123fb447f5dbfb`).
This is a service correctness guard, not a formal accuracy gate.

## Performance decision

The maintained three-role comparison returned `failed` because the primary
output-throughput improvement was below the frozen 5% threshold:

| Metric | Baseline | Candidate 4096 | Revert 2048 | Candidate vs baseline |
|---|---:|---:|---:|---:|
| Output throughput (tok/s) | 0.331103 | 0.331750 | 0.334935 | +0.195% |
| Total-token throughput (tok/s) | 42.7123 | 42.7957 | 43.2066 | +0.195% |
| P99 TTFT (ms) | 764650.05 | 766507.51 | 755845.95 | -0.243% |
| P99 TPOT (ms) | 21425.45 | 21323.25 | 21189.79 | +0.477% |

The candidate's measured P99 ITL values were 95400.11 and 96840.72 ms, about
twice the baseline median of 48217.89 ms. ITL was not a frozen pass/fail
guardrail, but its return to 47468.93 and 47662.46 ms after revert is additional
evidence against retaining the candidate. The larger scheduler budget also
reduced reported KV-cache capacity from 401,791 to 389,379 tokens.

The authoritative comparison is
`/mnt/nfs/users/jinghao/hy4-preview/optimize/20260914-hy4-preview-ppu-e2e/results/performance/p4k-scout-comparison-v2.json`
(SHA256 `73c64c0b68d13381d086c22bd43c88c87aa1eb5628e49b4d5db8ea57a0192e44`).
The original `p4k-scout-comparison.json` is retained as invalid-tooling
evidence: it was `incomplete` because the comparison utility treated the
`launch_args` array as one path. The utility now reports concrete array indices,
with a regression test; no measurement artifact or frozen contract was edited.

Decision: reject and revert `max_num_batched_tokens=4096`. The optimization
container currently serves the verified 2048 configuration.
