# op-001 Ordinary sigmoid top-k integration

## 优化方向与瓶颈依据

用户要求在独立新容器中将普通 sigmoid+bias 路由由单组 grouped_topk 接入已有 FlagGems-vllm topk_sigmoid。分类 operator/replace，影响共享 MoE 路由；本轮是接口接入，没有性能收益结论。

## 优化内容与适用边界

目标容器 `minimaxM3.1-opt-topk-sigmoid-20261021` 从 `minimaxM3.1-opt-latest-20261020` 无暂停快照创建，镜像谱系、三库及编译器指纹、相同 `/mnt:/mnt` 挂载通过。只修改目标 writable layer 中 `/workspace/vllm-plugin-fl`，现有主线程模型及评测不变。

复用 CachedOp、FlagGems backend 注册和 reference。普通 sigmoid+correction_bias 使用 topk_sigmoid；实际分组、softmax 与无偏置分支保持。选择使用偏置分数，输出为原 sigmoid 权重，按需归一化，routed_scaling_factor 仅乘一次，保留 int32/int64 ids。

库支持条件是二维连续 CUDA 兼容 logits，fp16/bf16/fp32，expert<=256、top-k<=min(32,experts)，可选 FP32 连续偏置；支持范围外调用现有 vLLM native。库开关、可选导出、whitelist/blacklist 仍由现有机制控制，执行错误交给原 dispatch。无模型名/机器名/平台名特判，没有新 kernel 或全局 patch。FlagGems-vllm/FlagGems/Triton 不改。

源码修改：Router、FlagGems backend/注册、reference backend/注册；复用 test_fused_moe_layer.py、test_builtin_ops.py。包名与 canonical 导入路径保持 vllm-plugin-fl、flaggems-vllm。
