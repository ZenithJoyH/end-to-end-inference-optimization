## Completed A/B/revert

The 8000 service on the same cards, source and matched environment started successfully with only `--enforce-eager` added. Six 64-token requests per endpoint (docs 89/140/168, two repeats each) were all healthy and internally exact. Eager 8000 differed from the previous 8000 graph on all three docs. For docs 140 and 168, eager 8000 became byte-identical to untouched 8010 graph for all 64 tokens. For doc 89, eager changed the initial token-4 choice to 8010's choice but diverged from 8010 later at token 20. Adding logprobs did not change any of these three eager trajectories, and repeated outputs were exact.

At the first graph-versus-eager divergence on the same cards, the selected pair remained near-tied: doc 89 token 4 (` chemistry` eager versus ` MC` graph, eager margin 0.125 versus graph tie); doc 140 token 56 (` have` eager versus ` need` graph, margins 0.125 versus 0.25); doc 168 token 12 (` final` eager versus ` produce` graph, both margins 0.125). In doc 89 the eager versus 8010 graph paths first diverged later at token 20, again at near-tied alternatives. This supports an execution-mode effect on small numerical rankings, **not** proof that FULL graph produces incorrect final answers. No full-answer or formal-score comparison was run.

After eager, 8000 was restored to original `FULL_AND_PIECEWISE` with matching library path and original source; the fixed three-doc short probe returned byte-for-byte to the pre-eager graph trajectory for all IDs, two repeats each. The 8010 process remained unchanged (`start_ticks=284523170`).
