## Current-service continuation

Both parallel 60K-budget **near-contract** C1 requests finished with final `C` and `finish_reason=stop`: port 8000 used 11,770 completion tokens and port 8010 used 18,100. The 8010 result exactly repeated the earlier near-contract 8010 C1 response hash and token count. These do not overwrite the formal C64 doc 168 `B` or the 174/198 gate. Their directory labels include the historical word `exact`, but the saved request JSON proves they used `max_tokens` and one stop string. Installed vLLM maps either `max_tokens` or `max_completion_tokens` to the same `TokenizeParams.max_output_tokens`; neither stop literal appears in either completed output. This makes the C1 payload difference unlikely to explain those particular completions, but the requests are still not relabeled byte-identical to formal.

After both endpoints became healthy and idle, a corrected `OpenAIChatCompletion`-field 64-token C1 request on each port returned the same doc 168 reasoning SHA `01977e...` and `Now analyze...` prefix. The corrected C8 probe on untouched 8010 (doc 168 plus frozen docs 0–6; each max64) returned `Need analyze thoroughly maybe complex...` in **both** waves, with no request errors. This moves toward—but does not exactly reproduce—the formal C64 prefix `Need analyze thoroughly maybe simple...`. Under C32 on 8010, three waves produced three different doc 168 prefixes (`Now analyze...`, `Need analyze thoroughly maybe complex...`, `Now analyze thoroughly...`). All 32 responses in each wave were healthy, so the nominal request count alone does not uniquely select a prefix; actual scheduling, graph/shape path and near-tied numeric rankings remain candidates. C32 is the service's configured `--max-num-seqs 32`, but the seven/31 peers and their completion budget differ from formal C64 traffic.

The installed OpenAI protocol forwards `seed=self.seed` to `SamplingParams`; `SamplingParams.sampling_type` selects `RANDOM_SEED` for temperature 1 with non-null seed; the vLLM worker creates a per-request `torch.Generator` seeded from that value, and the native top-k/top-p sampler applies the per-request generator row by row. Thus a single shared global RNG is **not** the straightforward explanation. It does not prove generator offset/order and all execution paths are invariant under batching. A diagnostic `logprobs=true, top_logprobs=5` was neutral for two C1 repeats but changed one of two C8 trajectories, so it cannot be assumed non-perturbing in the batch. At the first divergent doc 168 token (one-based 11), the C1 logprob probe chose ` Now` with a reported exact tie to ` Need` (both -0.70256); C8 logprob wave 1 also chose ` Now` but reported it ahead by 0.125 (-0.64343 versus -0.76843); C8 logprob wave 2 chose ` Need`, ahead by 0.25 (-0.58343 versus -0.83343). The first ten emitted tokens were identical. The varying *reported probabilities*, not just the sampled token, make a numerical/logit path difference directly observable under the diagnostic payload. This service does not set `--logprobs-mode`, so installed vLLM defaults to `raw_logprobs`, computed from model logits before the sampler converts them to float32; this points to a pre-float32-logit boundary rather than a pure random-draw explanation. The quantized 0.125–0.25 margins are near-ties, not evidence that the numerics violate tolerance. This localizes the observable batch-sensitive choice very early in decode; it does **not** prove which upstream operator or graph shape changed those logits or whether that one choice caused a wrong full answer.

To test the latter link, a single C8-started long diagnostic ran on untouched 8010: doc 168 retained the exact formal 60K completion budget, while seven frozen peers terminated after 64 tokens. It returned HTTP 200, `finish_reason=stop`, **17,536 completion tokens and correct final `C`**; all seven peers returned HTTP 200 with no errors. Its request/response paths are `diagnostics/accdiag-008-current-output-replay-20260924/c8-short-targetfull-exact-port8010-wave1/`. The target's initial reasoning followed the formal `Need analyze thoroughly maybe simple...` branch for 90 retokenized reasoning tokens (391 characters) before the first split: formal wrote `choices: discrete/continuous`, C8 wrote `Options: discrete or continuous`. The formal C64 answer later became `B` at 33,320 tokens, while this C8-started answer was `C` at 17,536. Therefore even a formal-matching 90-token prefix and real short batching are **not sufficient** to reproduce the wrong answer. After the seven short peers finish, the request effectively becomes C1; its correct result cannot rule out a sustained C64 mixed-decode effect. Moreover, accdiag-010 recovered formal doc 168 on **8000**, so this 8010 replay is cross-port. No source or service was changed.

The confirmed boundary is pre-sampler near-tied logit/trajectory sensitivity under the current PPU batch/graph execution, plus independently documented long-reasoning non-commitment and semantic mistakes. This experiment does **not** isolate one operator, prove numerics outside expected tolerance, or explain the full 174/198 score gap. Further causal work would need sustained, matched formal-load replay on the **correct port/card group** with scheduler cohorts and first-divergent logits/tensors captured, then a one-variable current-adapter A/B and a fresh 198-item formal gate; the existing gate remains failed.
