## Directly observed failure chain

- The accdiag-011 current-8000 replay started 2026-09-24 13:31:19 +08:00. At 13:33:42 it had nine requests running, no waiting requests; doc 76 was the ninth newly scheduled request. The generated FlagGems `index_linearized_inp_shape_9_13_start_dim_0_indices_len_2_dtype_torch_int32_m_672_n_32.py` cache file has mtime 13:33:42.647, matching the new nine-sequence shape.
- At 13:33:50, Worker_TP1 failed in Qwen3.8-Flash-Next attention-metadata/QSA compressed-slot mapping → FlagGems `ops/index.py` → `LibTuner.run`. Its `SQLPersistantModel.put_benchmark` attempted `CREATE TABLE IF NOT EXISTS` for an `index_linearized` benchmark-v2 table and raised `sqlite3.OperationalError: database is locked`. A second stack from the same worker showed `SQLPersistantModel.get_config` failing a `SELECT` with the same lock error. The benchmark table exists in the database after the incident, consistent with another process eventually creating it, but the surviving table does **not** identify the lock holder.
- The engine then logged no available shared-memory broadcast block in successive minutes; at 13:38:42 `sample_tokens` RPC timed out, EngineCore became fatal, 13 in-flight requests received HTTP 500 and port 8000 exited. Later client dispatches received connection refused. Accdiag-011 target doc 168 was not dispatched. Port 8010 remained healthy/idle, and the shared model container remained up.

The direct mechanism from SQLite exception to worker failure, RPC timeout and service shutdown is **confirmed**. The exact connection/process holding the write or exclusive lock at 13:33:50 was not captured before the process exited; whether an 8000 rank, 8010 rank or another cache client held it is **unconfirmed**.

`LibCache` defaults to one SQLite URL under `config_cache_dir()` when `FLAGGEMS_DB_URL` is unset. The effective file is `/root/.flaggems/config_cache/TunedConfig_thead_triton_3_6.db` inside the shared optimization container, on container `overlayfs` rather than NFS. The live 8010 service has no `FLAGGEMS_DB_URL` or `XDG_CACHE_HOME` override and all eight of its TP worker processes have file descriptors to that same database. The accdiag-006 launch code that created the now-dead 8000 service did not set a cache-isolating override. The database was 13.5 MB with 471 tables when inspected and uses SQLite `journal_mode=delete`, `locking_mode=normal`; its mtime advanced to 13:33:54 after the lock error. These facts establish the shared multi-process cache design; they do not prove which process held the lock at failure time.

`SQLPersistantModel` calls `sqlalchemy.create_engine(db_url)` without an explicit SQLite busy timeout or retry policy. `get_sql_model` guards model metadata with a `threading.Lock`, which is process-local and cannot serialize the eight worker processes (nor the other service). It dynamically creates tables during a previously unseen autotune shape and does not catch SQLite `OperationalError: database is locked`; `RollbackSession.commit` only handles `IntegrityError`. This combination makes concurrent first-use shape tuning a credible trigger. The stack identifies the *index autotune/cache transaction*, not an incorrect tensor value. No numerical/GPQA score causal link is established.
