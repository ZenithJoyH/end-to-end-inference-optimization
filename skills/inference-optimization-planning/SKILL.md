# Inference Optimization Planning

Use this Skill as a periodic planning checkpoint inside the optimization loop. It converts scattered experiment results into a verified current state and a short, falsifiable next cycle with actual execution assignments. The main coordinator owns the review and dispatches concrete analysis, implementation and tests under AGENTS 5.5; this Skill does not run benchmarks, profiling, accuracy evaluation, or operator analysis itself.

## Answer direction progress without a full review

The main coordinator is the single user-facing source for progress across all current directions, including unstarted, queued, failed, stopped and pending-integration work. For a status-only question, use this internal reading/verification/reporting branch, not a new public mode or interface: read the existing case ledger/overview and latest receipts; skip the full evidence-reading/review workflow below. Read only needed direction fields and evidence; do not copy huge raw JSON/logs or treat a truncated case summary as complete. If freshness needs checking, use only authorized task/session, process or artifact-metadata minimal read-only checks under AGENTS 5.5; delegate deeper analysis. Do not rerun benchmarks/profiling, duplicate tasks, restart experiments, change priorities or expand authorization to answer status.

Return each direction using [SOP D0's progress fields](../../docs/performance-optimization-sop.md#d0-并行探索局部筛选与批次集成): goal/current unit, experiment/task/session/owner and parent/current implementation, actual state with verification time/timezone/source, verified results and scope, remaining validation, actual resource/executor placement and parallel validation level, blocker/holder/dependency and release condition, alternatives checked but unused with preparation-cost reasons, next action/owner and recheck/start condition. Distinguish currently verified, last historical confirmation, executor-reported but unreviewed, and unknown/stale. If refresh fails, give the last confirmed time, concrete limitation and next observation arrangement; old running is not current running. Report known branches without waiting for every refresh. Give ETA only as an evidenced estimate, otherwise unknown; a checkpoint is not a completion promise. Do not invent completion percentages.

Task completion, local validation, integrated retention and formal acceptance are different states. Bind performance claims to the actual candidate/workload/phase, correctness and graph coverage; preserve negative results and do not transfer historical evidence to a new identity. Apply D0 event-driven receipt collection: the coordinator verifies then serializes updates to the factual `state.yml`, followed by README numbers/status derived from it, or designates one writer; separate experiment Markdown may remain executor-owned. Delivery alone does not advance business state. Write refreshed facts/limits and next observations there, without a new review ID or separate board/schema. A status reply does not end rolling scheduling/observation responsibility; manual pause, budget end and formal handoff prevail. Reuse existing observation and user notification preferences, with no new monitoring/automation authority or fixed high-frequency polling.

## Trigger the review

Run a review at scenario entry to design and dispatch the first independent directions, then by default after 2–3 completed optimization experiments. Trigger earlier when:

- retained changes interact, a combined candidate is being prepared, or the hotspot appears to move;
- the bounded inventory of locally validated candidates reaches its integration budget/limit, or independent winners need compatibility and combined validation;
- targeted scenarios disagree, guard metrics regress, or results are repeatedly `failed`/`incomplete`;
- CPU hotspots/waits or submission gaps, an exposed collective path, or rank/stage/replica skew could change the next experiment; treat an ambiguous signal as a hypothesis to discriminate, not an established root cause;
- the current direction requires expensive operator development, broad Plugin changes, or additional hardware time;
- task objectives, SLO, workload or modification boundaries change, or resource changes alter direction feasibility, scope or budget. Routine resource release or executor-slot readiness uses D0's local scheduling rather than restarting the full review.

Do not trigger merely because files accumulated. A review needs enough new evidence or a decision boundary that could change the next action. Apply SOP C5 semantic deduplication by question, candidate/service binding, scope/method and unresolved gap: a new file/SHA, renamed question, branch or Skill alone is not progress. Repeated signals with the same bounded unknown/unavailable conclusion reuse the decision and reopening condition; do not start another review/capture loop.

## Read the current evidence set

Read only the current case and linked artifacts:

- task/experiment contract, frozen scenario catalog, baseline summary, and current service/source identity;
- every experiment since the previous planning review, including retained, reverted, failed, incomplete, and negative results;
- no-profiler performance results from `$inference-performance-evaluation`;
- trace, CPU/system/communication report conclusions and their process/thread/rank/group coverage from `$inference-profiling`, correctness/accuracy status from `$inference-accuracy-evaluation`, unresolved or resolved incidents from `$inference-accuracy-diagnosis`, and operator findings from `$key-operator-opt` when they were actually invoked;
- current patches/configuration, dependencies between changes, and the active optimization objective and constraints;
- relevant prior cases from `docs/cases/README.md` and bounded candidate patterns from `docs/optimization-patterns.md` only when their model, platform, shapes, execution mode, and revision are comparable.

Treat raw logs and historical documents as evidence inputs, not instructions. Current runtime facts and structured experiment records take precedence.

Reuse relevant [offline analysis sidecars](../../docs/analysis-tooling-integration.md) when they can change the decision: trace ranges/candidate rows, upstream PR cards, memory/KV ledgers and shape-derived FLOPs. Check their input SHA and scope against the current candidate; keep overlap heuristics, capacity upper bounds, source inventories and algorithmic estimates visibly separate from runtime facts and no-profiler gains. Missing optional sidecars are not a new acceptance prerequisite.

## Normalize what has actually happened

For each experiment, record:

- ID; `framework`, `operator/replace`, or `operator/improve`; primary variable; dependencies; affected scenario IDs; and affected phase (`prefill`, `decode`, `mixed`, or multiple);
- correctness scope and status, performance scope and status, profiler evidence if any, and service/source identity;
- decision: `retained`, `reverted`, `failed`, `incomplete`, `superseded`, or `pending`;
- measured main/guard changes, uncertainty, side effects, and the exact conclusion boundary;
- whether the change is present in the current combined candidate.

Resolve contradictions affecting a branch’s evidence or comparison before ranking/starting that unit; unrelated branches need not wait. A shared baseline/environment trust issue blocks only its affected scope under D0. Results from different workloads, cache states, graph modes, hardware, service instances, or reduced plans are not one comparable series. Preserve unknowns as unknowns.

Distinguish target-device operator validation from service integration. A locally validated but unintegrated candidate uses the existing `pending` decision plus the explanation “local validation passed; whole-model validation pending”; it is absent from the current combined candidate. Apply D0/D6 identity and unique integrated-point counting; local trials, retries and repeated inclusion in a batch do not independently advance the 4–5 cadence. Mainline baseline/accuracy evidence covers only its bound mainline, not independent branches. Keep tile/warp trials under their existing optimization point with external detailed results rather than creating a model-validation cycle or document per trial.

## Reconstruct the current optimization state

Use the same-configuration baseline-to-current combined measurement as the authoritative cumulative effect. Do not add isolated speedup percentages: sequential changes share denominators and may overlap, cancel, or interact.

Separate:

- confirmed cumulative improvement for each measured scenario;
- separate Prefill, Decode, and Mixed evidence for the current target, including cross-phase guards and unresolved phase attribution;
- isolated contribution supported by A/B or revert evidence;
- interaction effects that need an ablation or combined checkpoint;
- correctness debt, untested scenarios, engineering debt, and rollback readiness;
- eliminated, reduced, unchanged, newly exposed, and still-ambiguous bottlenecks.

When Roofline evidence informs the decision, consume the result of [$inference-roofline-analysis](../inference-roofline-analysis/SKILL.md) and check that its phase/rank/shape, FLOPs convention, HBM traffic, timing scope, and ceiling match the current candidate. When inputs change, first check their impact and unaffected bindings; request refreshed analysis only for affected scope whose earlier conclusion no longer supports this decision. Missing collection goes through the coordinator and Profiling. Distinguish hardware measurements from estimates and missing coverage. Compare kernel headroom with timeline gaps, communication, and the target critical path where evidenced; missing critical-path contribution stays unknown rather than forcing a trace for a bounded kernel estimate. A kernel near its roof can still waste bytes or computation. Do not interpret a low FLOP/s percentage alone as poor execution, or assume Prefill is compute-bound and Decode bandwidth-bound by name.

When a baseline is explicitly deferred under SOP baseline-recovery, use verified runtime/source/shape facts for bounded diagnosis and falsification probes; do not force a complete baseline or device trace merely to enter planning. Preserve the missing baseline and acceptance limits, and do not invent cumulative gains.

Use admitted steady-state measurements as the default evidence for bottleneck ranking and cumulative benefit. Cold-start,
first-request, first-batch, and pre-steady anomalies may expose an insufficient warmup contract, but must not redirect the
optimization plan toward startup-only work unless the user explicitly made cold start an objective. Do not repair apparent
instability by dropping the first measured round after seeing it; request a new comparable measurement contract instead.

If several changes have entered the service candidate but the combination lacks coverage of all affected scenarios, apply [SOP D7 validation deduplication](../../docs/performance-optimization-sop.md#d7-性能场景与分层测试频率) before dispatching `$inference-performance-evaluation` in `checkpoint` mode. Reuse valid native results that satisfy the current candidate/service, workload, graph/cache, phase/guards, correctness, comparison and repetition requirements; an eligible formal result can answer a narrower checkpoint question without changing its original purpose or receipt. An old targeted run cannot become formal or count again as an independent repetition. Wait/merge through the owner only when an in-flight formal/checkpoint matches the candidate/service binding, contract and required scope. Do not duplicate that covered workload; a scenario name alone does not deduplicate different candidates or independent experiments. Dispatch uncovered independent work in parallel under D0, queuing only conflicting or dependent units. A diagnosis-only supplement with unchanged candidate/workload does not itself require another performance run. If the new bottleneck is ambiguous, first check evidence, analyses and in-flight tasks under SOP C5; dispatch analysis on valid data before requesting new capture. Route only a decision-relevant remaining gap through `$inference-profiling`, preserving valid artifacts and requesting counters alone when appropriate. If the configured accuracy trigger is due, check existing valid gates/in-flight evaluations before requesting missing work through `$inference-accuracy-evaluation`; retain all required identity and native-gate checks. Keep the planning result `incomplete` only for its required missing scope; optional unavailable diagnosis/counters do not invalidate independently supported decisions or a valid measurement result.

## Automatically route decision-relevant diagnosis

At every review, including one triggered early by a system signal, apply the [SOP C0.4 automatic planning handoff](../../docs/performance-optimization-sop.md#c04-系统诊断自动衔接规划复盘) alongside the [C5 Roofline triggers](../../docs/performance-optimization-sop.md#c5-用-roofline-连接瓶颈证据与下一步实验). Select the relevant [C0 diagnostic branch](../../docs/performance-optimization-sop.md#c0-系统瓶颈分诊与取证) automatically; do not ask the user to name a Skill or choose between CPU, communication and rank diagnosis. Read only the selected branch of the Profiling [system diagnosis reference](../inference-profiling/references/system-bottlenecks.md), or the Roofline method when applicable. For a remaining collection gap, select the cheapest useful method through [SOP C0.5](../../docs/performance-optimization-sop.md#c05-症状驱动的工具选择与退出), which links the executable tool recipe; do not maintain another tool table here. Existing sufficient analysis is consumed directly without tool preflight or new metrics; offline evidence does not require a live PID or target connection.

| Decision-relevant signal | Automatic route and discriminating output |
|---|---|
| CPU hotspot/wait, delayed device submission or output, or one thread busy while average CPU is low | Profiling CPU branch: bind API/tokenizer/scheduler/worker roles and the observed phase/window; distinguish on-CPU work, runnable/quota delay, blocking and downstream device waits. A device gap alone does not prove CPU saturation |
| Collective activity appears to limit the target or scaling | Profiling communication branch: compare the same group/collective/iteration and message scope, separate participant arrival skew from communication service and exposed dependency. If late arrival points upstream, the coordinator routes the remaining question to CPU/rank diagnosis rather than presuming a slow network |
| Rank, PP stage, EP expert or DP replica skew | Profiling load branch: compare appropriate TP/PP/EP/DP roles, logical work, effective/padded tokens and shapes; distinguish workload skew, persistently slow execution and dependency/pipeline waits. Equal request counts or utilization do not establish equal work |
| Compute, HBM traffic or execution-efficiency explanation would change implementation/validation investment | `$inference-roofline-analysis`: bind current phase/rank/shape, timing and measured/estimated counters; request only decision-relevant missing collection through Profiling |

These routes share one evidence-state decision, not a fixed CPU→communication→rank→Roofline sequence:

1. If a current, adequately scoped analysis already answers the question or supplies a reusable bounded unknown/unavailable conclusion, use it directly. If valid matching traces or CPU/system/communication/counter reports exist without analysis, dispatch Profiling `analyze` or the relevant Roofline analysis; no new device trace is required for a CPU/system question. Check the applicable source/binding, workload/window, phase/role/group/shape coverage, units, correlation and clock uncertainty before reuse; PID/TID is relevant to process sampling, while metrics/NIC/device reports use their endpoint/interface/device scope. Map a shared capture/report to all relevant questions under C5 before requesting only the remaining coverage; do not recollect the same window per branch/tool. Artifact validity and sufficiency for this question are separate: retain valid partial evidence while narrowing the conclusion and missing scope.
2. Only an unresolved gap that can change the ranking warrants bounded Profiling `capture`, using C0.5 method selection within the original total budget and D0 resource-conflict coordination. For suspected hotspot migration, use `reprofile` only with comparable previous evidence and capture conditions; otherwise capture just the new missing scope and state the comparison limit. Reuse valid unaffected artifacts after an impact/binding check rather than recollecting everything.
3. Before dispatch, reference semantically matching in-flight work and merge/wait through its owner. For unavailable, failed or budget-exhausted evidence, preserve the native status and valid partial coverage, return bounded partial/unknown for the missing scope without invalidating independent evidence or valid performance results, and retain the gap, attempts and reopening condition; do not retry through another Skill or reset history by renaming the question. Re-entry needs a material change in usable coverage/reliability, mechanism, ranking or next experiment; a known blocker needs its stated tool/permission/scope condition to change. Candidate revision changes alone do not reopen an unchanged unavailable counter. CPU/wait/queue/communication evidence can support a direct experiment without first collecting Roofline counters; record why Roofline would not change that decision.
4. Specify the original decision/question and hypothesis, plausible counter-explanation, existing input artifacts/bindings, exact missing coverage, selected mode/branch, executor and authorized target scope, expected discriminating artifacts/validity, total budget, success/stop conditions and return point in the existing record. For communication/rank questions include logical group/work correlation and timing uncertainty; insufficient coverage remains unknown. This is a scoped task description, not a new schema or collector.

Every analysis/supplement returns to the original coordinator and the same decision point. It does not recursively delegate, call another Skill to open a second optimization loop, or restart the review/budget. The coordinator alone decides any subsequent CPU/rank/communication handoff, operator experiment or validation, carrying the original total budget and attempt history. As each branch has sufficient evidence, proceed to ranking and its smallest supported experiment without waiting for unrelated reports; when it adds no decision-relevant information, select a supported alternative or defer/replan within the original limits, without regenerating the same analysis.

## Rank the next directions

Generate a short ranked list, normally 2–3 independent directions without inventing low-value work, using [SOP C2](../../docs/performance-optimization-sop.md#c2-生成并维护实际候选排名) and the shared [hotspot/net-benefit method](../inference-roofline-analysis/references/roofline.md#热点筛选与净收益排序). Automatically screen for objective-specific critical-path impact or evidenced contention, actual shape/call coverage, and whether further Roofline analysis would change the decision. Reuse the current analysis shortlist; do not require counters or kernel tuning for every operator.

At direction selection, each review and hotspot migration, automatically evaluate [SOP C3.1 communication-compute fusion and overlap](../../docs/performance-optimization-sop.md#c31-通算融合与-overlap-候选) against the current bottleneck; do not wait for the user to name it. Exposed communication/copy, tile/chunk/microbatch readiness or kernel memory stalls can justify a candidate, while communication/rank waits that could reflect CPU/rank arrival skew first use existing evidence to distinguish it; only a remaining decision-relevant gap returns to that diagnostic branch. Distinguish comm-compute fusion, stream/chunk/microbatch overlap, copy-compute overlap and kernel-internal prefetch/pipelining. Read the relevant [operator reference](../key-operator-opt/references/comm-compute-fusion-overlap.md) only when a branch is decision-relevant; no signal or a known unavailable capability warrants a brief deferral/reopening condition, not new collection.

For any shortlisted fusion/overlap direction, bind the actual group/shape/topology, primitive and graph support, legal dependencies, full producer→communication/synchronization→consumer boundary and resource competition. Rank its removable exposed cost against added pack/copy/launch/buffer/synchronization, pipeline fill/drain and smaller-chunk efficiency losses. Record adopted/downgraded/deferred and why in the existing shortlist; simultaneous streams or a shorter isolated kernel is not a gain. Apply D0 quick local screening, completed local validation and bounded pending inventory/batch integration, with existing high-risk model/accuracy triggers at service integration. Only the coordinator assigns decision-relevant missing diagnosis under C5; do not create a fusion→Profiling→Roofline loop or mechanically require traces/counters for each trial.

```text
objective-specific hotspot → removable critical-path cost minus added execution cost
→ net-benefit interval → evidence confidence, engineering/validation cost and risk
→ first falsification experiment and guards
```

Use the serial/Amdahl mapping only for its stated assumptions; for concurrent kernels, collectives or ranks, recompute the changed dependency path and newly exposed bottleneck. Do not simply multiply cumulative kernel time, or overlap-subtracted time, by a kernel speedup fraction. Separate fixed-work roof headroom from reductions in FLOPs/bytes, count coverage once, deduct only additions not already included in candidate full-call timing, and keep profiler and no-profiler timing provenance distinct. Tail percentiles and throughput/goodput require their own workload evidence rather than arithmetic on mean phase latency.

Compare net-benefit intervals first, then explain confidence, production applicability, implementation/validation cost, correctness/compatibility and maintenance risk. Do not numerically subtract dimensionless risk or developer time from milliseconds, invent confidence probabilities, or choose the largest theoretical headroom by itself. When intervals overlap, prefer supported, cheaper-to-validate, reversible alternatives; when upside is large but evidence weak, choose the smallest discriminating probe before deep implementation. If no credible positive net benefit is supported, select a bounded diagnostic or defer explicitly. Re-evaluate the default framework/replace/improve order against this evidence after retained changes; isolated candidate gains are not additive.

For every proposed direction include:

- rank, layer/strategy, target phase and bottleneck, supporting and opposing evidence;
- expected main-metric effect for the target phase and Mixed workload, plus cross-phase and tail guards;
- objective/timing unit, raw hotspot time and window, critical-path share or contention evidence, coverage weighting, fixed-work or work-reduction assumptions, full-call added costs including CPU work, copy/layout, communication, synchronization and queueing, net-benefit interval and its provenance/confidence;
- applicable scenario/shape/dtype/layout/graph/platform boundary;
- dependencies, implementation scope, correctness risk, validation cost, and rollback path;
- the smallest first experiment that can falsify it, including parent `scenario_id`, local versus service-integration scope, applicable performance Skill mode only when service measurement is due, correctness trigger, profiling need, success threshold, and stop condition.

For system- or Roofline-derived directions, state the predicted reduction in CPU work, traffic, computation, or exposed waits, the affected critical-path share, competing explanations, and the measurement that would falsify the mechanism. A shorter collective, a lower CPU percentage or more even ranks alone is not an end-to-end benefit: account for the remaining bottleneck, changed batch/work distribution and added costs. Missing counters reduce confidence without vetoing otherwise supported experiments. After a retained change, reassess batch/KV working point, intensity when relevant and hotspot migration before reusing the old ranking; use `reprofile` only under the routing conditions above. Local operator results remain pending whole-model validation; confirm service-integrated gains with no-profiler Mixed measurements and cross-phase guards.

Explain how each CPU, communication, rank or Roofline result changed or confirmed the next directions: which was adopted, downgraded or deferred and why, then bind each selected direction to its first single-variable experiment, guards and stop conditions. Rejected hypotheses and unresolved alternatives must affect confidence or priority. Do not merely link the analysis while carrying forward an unsupported old priority. If collection is needed, specify its narrow question and scope instead of creating an open-ended profiling loop.

Also list deferred directions and why they are lower priority. Do not present an unmeasured kernel hotspot, historical speedup, or theoretical peak as expected end-to-end gain without discounting and an explicit validation plan.

## Produce a concrete next cycle

At scenario entry and every review, proactively design a bounded set of independent mechanisms or hypotheses, normally 2–3, under [SOP D0](../../docs/performance-optimization-sop.md#d0-并行探索局部筛选与批次集成). When at least two valuable directions have executable work, actually dispatch them; a shortlist is insufficient. Different mechanisms for the same bottleneck and parameter A/B experiments without new code qualify; tile/warp scans, analysis plus review, or stages of one direction do not. If only one supported hypothesis remains, record the evidence and reopening condition rather than manufacture another branch.

Follow the [project assignment rules](../../docs/agent-execution.md#执行前分配与阶段核查). Check C5/D7 for covering evidence and in-flight work before assigning a direction. Group consecutive steps that share the same direction and authorization into one work unit with explicit gates, stop conditions and deliverables. Pass only the required context to a new worker, and send only changed inputs and remaining work when reusing its session. [Observe meaningful events](../../docs/agent-execution.md#按事件观察) and [collect one closeout](../../docs/agent-execution.md#worker-收尾与交接) per work unit.

Where evidence is sufficient, the execution assignment must deliver an implementation or configuration variant and a controlled comparison, not just analysis. Diagnosis may be a prerequisite but must return to implementation/experiment dispatch or an evidenced rejection/deferral.

Apply D0's resource-before-queue order at scenario dispatch, before queuing, and on resource/prerequisite/failure events. Identify the unit's minimum resources/evidence boundary, then minimally inspect compatible alternatives and executor slots within the current task's authorized scope: independent devices/CPU/resource groups on the same Host first, then other already-authorized Hosts. Verify shared CPU/NUMA/NIC/memory/disk/source/cache/compiler contention; containers or ports alone do not establish independence. Do not sweep inventory, expand Host/device authorization, use/terminate other tasks' resources, provision cloud capacity or install tools. Use explainable bounded estimates of verification waiting/completion time and exploration cost, including environment/transfer/control-rebuild overhead. When risk and budget permit and a verified alternative is expected to shorten that unit’s wait/completion or reduce exploration cost, actually dispatch and start independent ready validation units there rather than report resource shortage. This is a scheduling comparison, not proof of model E2E speedup; unknown exact waiting time is not a reason to skip alternative assessment. Use minimal resource/environment checks within existing authorization and budget when needed.

Use idle compatible resources for correctness, graph, complete-call microbenchmarks or reduced milestones without tying every unit to whole-model devices. Preserve actual shapes/reference/guards and scope; an indivisible communication topology cannot be certified on one card. Rebuild comparable baseline/reference and candidate controls for the new placement; do not compute cross-hardware/card-count/topology E2E speedups or transfer local evidence to original-target service/formal acceptance. Apply existing [case isolation/binding rules](../../docs/model-artifact-contract.md): record real Host/device/resources and local controls for bounded external probes; a changed formal target Host/topology/anchor needs a separate case, while each tile/single-card micro does not need a new model directory. Original-target acceptance identity stays unchanged. Keep image/mount/private-import/version/permission/data prerequisites, including no extra mismatched mounts.

Record alternatives checked, verification time and rejection reasons, actual holder/conflict/predecessor/priority and next recheck/release/start condition; revisit alternatives instead of only waiting for the original device. Migrate running work only at safe checkpoints or assign not-yet-started units after verifying old-task state under recovery rules: no replacement writer while unknown, no duplicate covered in-flight validation, no long-measurement interruption for parallelism counts, and no budget reset. A release event can replace an unknown end time. Do not serialize everything without checking, or wait for the first direction's whole-model acceptance before developing another. Async assignments may start their executable units on confirmed resources. Judge readiness per branch/work unit: as its own prerequisites are satisfied, start it without waiting for unrelated diagnosis, trace/Roofline, whole-model baselines or validation. Once multiple units are ready and resources/dependencies are verified independent, start their experiments in parallel. Wait across branches only for real dependencies or the affected scope of a shared baseline/environment trust issue. Development overlap alone is insufficient when controlled comparisons are ready on independent measurement resources; batch submission followed by unjustified direction-by-direction serialization is also insufficient. This does not require concurrent whole-model services or change budgets/stop conditions. On each delivery, diagnosis return, predecessor completion, release or failure, the coordinator locally reassesses ready/queued units and starts or boundedly backfills eligible work within the original budget, without waiting for 2–3 results/all branches or rerunning the whole review/capture. Keep a coordinator owner and next observation/deadline or release event for each queued unit using existing observation mechanisms; respect manual pause, budget end and formal handoff, with no new monitoring/automation authority. Preserve Host/container/mount scope, measurement deduplication and shared-resource isolation.

Verify real task/session identity and execution receipts; a tool call succeeding does not prove work started. Track submission, start, measurement start/end and completion separately, retaining unstarted, queued, failed and unconfirmed states honestly. For ready runnable units, verify a real start receipt or a terminal receipt if already completed. Every unstarted/queued/unconfirmed unit needs concrete blocker/unknown evidence, a coordinator owner and next observation/deadline/prerequisite-completion or release trigger; keep observing/verifying under the recovery rules and original budget rather than ending follow-up with only incomplete or “next”. ## Record the checkpoint

Resolve the active case directory from its current record and [model artifact contract](../../docs/model-artifact-contract.md); new cases use `models/<model>/<platform>/<case-id>/`, while legacy layouts remain readable without automatic migration. Update that case's `optimize/state.yml` with the stable review ID, current candidate, experiment ledger, phase bottlenecks, ranked next directions, immediate experiment, evidence cutoff, next review trigger, and compact summaries of superseded decisions. Verify that every optimization-point ledger entry has a matching `optimize/<experiment-id>.md` covering its direction, content, effect, correctness, decision, and evidence, including reverted, failed, incomplete, and superseded points. Record all D0 directions, including unstarted/queued/failed/stopped/pending integration, with experiment/task/session/owner and parent/current implementation bindings, verified timestamps/sources, outputs/remaining scope and next actions in those same records. The coordinator verifies and serializes factual state updates before synchronizing README, or designates one writer; individual experiment Markdown may remain executor-owned. Collect updates promptly on dispatch/start/checkpoint/validation/failure/release/merge/rollback/stop, without waiting for a full review or user inquiry; heartbeat/log growth/exit 0 alone cannot mark a result verified; on D0 delivery/resource/failure events, update readiness, queue ownership/next observation, actual dispatch and results rather than just list work as next. Synchronize the same case's `optimize/README.md` as the human-readable multi-round overview and link index. Do not create an `optimize/history/`, planning work directory, or per-review file.

Keep raw benchmark, trace, accuracy artifacts, commands, and process scripts at their existing external locations; the structured state links evidence rather than copying it. Only the final frozen result updates `acceptance/state.yml` and `acceptance/README.md`.

Return a compact summary containing: review ID, evidence cutoff, current cumulative state, retained/reverted/incomplete experiments, current bottleneck, next directions and actual assignments/receipts, queued work and release/start conditions, verified parallel scope, required Skill calls, blockers or evidenced single-direction exceptions, updated state/README paths, and next review trigger.
