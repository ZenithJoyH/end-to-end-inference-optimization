# 关键算子分析项目指南

## 1. 项目目标

本项目用于系统分析大模型推理过程中的关键算子。每项分析都应回答以下三个核心问题：

1. 算子是什么，在大模型推理的什么位置、什么场景下使用？
2. 当前主流推理框架和硬件后端如何实现该算子？
3. 当前实现的瓶颈在哪里，如何提出、实现并验证进一步优化？

分析不能只停留在概念介绍或源码复述。最终结论必须尽可能由公式、源码、性能数据或可复现实验支撑。

## 2. 默认工作原则

- 使用中文撰写分析，代码、API、变量名和行业惯用术语保留英文。
- 先明确研究对象和边界，再开展源码与性能分析；不要混淆同名但语义不同的算子。
- 将 `Prefill` 与 `Decode` 分开讨论，因为两者的张量形状、并行度和性能瓶颈通常不同。
- 区分训练与推理实现；除非对理解推理实现有帮助，否则不展开训练特有逻辑。
- 区分算法、框架调度、Kernel 和硬件四个层次，避免把某一层的优化笼统归为“算子优化”。
- 优先使用一手资料：论文、官方文档、正式仓库源码、硬件编程指南和实际性能数据。
- 涉及时效性较强的框架实现时，应记录仓库、分支或 tag、commit、文件路径和分析日期。
- 不预设优化有效。所有优化方案都必须说明适用条件、预期收益、代价和可能退化的场景。
- 保留用户已有改动，不修改与当前算子分析无关的文件。

## 3. 开始分析前需要确认的信息

在信息可以从项目或源码中推断时直接推进；只有关键条件缺失且不同选择会显著改变结论时才向用户确认。

至少明确以下内容：

- 算子名称及其准确语义。
- 目标模型或模型结构，例如 Llama、Qwen、DeepSeek、MoE 等。
- 目标推理阶段：Prefill、Decode，或两者都分析。
- 目标框架及版本，例如 PyTorch、vLLM、SGLang、TensorRT-LLM、Transformers。
- 目标硬件及软件栈，例如 NVIDIA GPU 型号、CUDA、ROCm、Ascend、CPU。
- 数据类型与量化方式，例如 FP32、FP16、BF16、FP8、INT8、INT4。
- 典型输入形状，例如 batch size、sequence length、hidden size、head 数、KV head 数。
- 优化目标：首 token 延迟、单 token 延迟、吞吐、显存占用、功耗或精度。

如果用户没有指定，采用以下默认范围并在报告中明确标注假设：

- 聚焦单机 GPU 推理。
- 同时讨论 Prefill 和 Decode，但分别建模。
- 以 BF16/FP16 为基础精度，并说明量化可能产生的差异。
- 选择一个主流开源推理框架作为源码主线，其他框架用于横向比较。

## 4. 标准分析流程

### 阶段 A：定义与使用场景

1. 给出算子的数学定义、输入输出、张量维度和数据类型。
2. 说明算子在 Transformer 或目标模型计算图中的位置，并列出上游和下游算子。
3. 解释算子在 Prefill 与 Decode 阶段的调用方式和形状差异。
4. 说明是否存在 Dense、MoE、GQA/MQA、量化或分布式场景下的变体。
5. 给出一个足够小、可手算或可运行的示例，验证语义和形状。

### 阶段 B：理论性能建模

1. 推导主要计算量，给出 FLOPs 或等价操作数，并明确计数约定。
2. 估算参数、激活和中间结果的内存读写量；说明缓存命中等假设。
3. 计算或估算 arithmetic intensity，并用 Roofline 思路判断其更可能受计算还是带宽限制。
4. 分析临时显存、峰值显存和数据布局要求。
5. 讨论不同 batch、sequence length、hidden size、并行度和 dtype 下的复杂度变化。

理论模型应提供公式和变量定义，不能只给出 `O(...)` 复杂度。

### 阶段 C：实现与源码调用链

源码追踪应从模型入口一直落到实际执行的 Kernel，推荐按以下层次记录：

```text
模型层 / Module
  -> 推理框架算子或调度逻辑
  -> PyTorch / CUDA Graph / 编译器接口
  -> C++ / CUDA / Triton / CUTLASS 实现
  -> 最终 Kernel 与硬件指令特征
```

对每一层说明：

- 文件路径、类或函数名及关键调用关系。
- 张量形状、stride、layout、dtype 和设备变化。
- Kernel 选择、dispatch 条件及 fallback 路径。
- 是否存在算子融合、量化、缓存、连续批处理或图捕获。
- 关键数据结构及其生命周期，例如 KV Cache、workspace、metadata。
- Prefill 和 Decode 是否进入不同实现分支。

引用源码时只摘录必要片段，并优先用固定 commit 的永久链接。若源码已存在于当前项目中，同时提供本地文件路径和行号。

### 阶段 D：基线实验与性能诊断

先建立正确、稳定、可复现的基线，再提出优化。

基准测试至少记录：

- 硬件型号、显存容量、驱动和功耗状态。
- 操作系统、编译器、CUDA/ROCm 和框架版本。
- 模型配置、输入形状、dtype、量化方式和随机种子。
- warmup 次数、正式迭代次数、同步位置和计时方法。
- 是否启用 CUDA Graph、编译模式、自动调优和缓存。
- 延迟统计，至少包含 median；条件允许时报告 P90/P99。
- 吞吐、有效带宽、有效 FLOPS、显存占用和精度误差。

诊断顺序：

1. 验证输出正确性和 benchmark 计时范围。
2. 观察端到端时间，确认该算子值得优化。
3. 分解 CPU 调度、Kernel launch、通信和 GPU 执行时间。
4. 检查 Kernel 数量、融合机会和不必要的同步或数据搬运。
5. 分析带宽、计算单元利用率、occupancy、warp stall、缓存命中和寄存器压力。
6. 将实测结果与理论上限及性能模型比较，形成有证据的瓶颈判断。

优先使用框架 profiler 和硬件 profiler。NVIDIA 平台可按需使用 PyTorch Profiler、Nsight Systems 和 Nsight Compute；不得只根据单次 wall-clock 计时下结论。

### 阶段 E：提出优化方案

按照投入和风险从低到高组织候选方案：

1. **调用与调度优化**：减少 Python/CPU 开销、同步、重复 dispatch 和 Kernel launch。
2. **算子融合**：减少中间张量、显存流量与 launch 次数。
3. **数据布局优化**：改善连续访问、向量化、coalescing、缓存和共享内存复用。
4. **Kernel 优化**：tiling、并行映射、流水线、异步拷贝、warp specialization、寄存器控制。
5. **精度与量化优化**：采用更低精度，同时控制累加误差、溢出和模型精度损失。
6. **算法优化**：稀疏化、近似计算、减少无效 token 或 KV 访问、改变计算顺序。
7. **系统与并行优化**：continuous batching、并行策略、通信融合和计算通信重叠。

每个候选方案必须填写：

- 当前瓶颈和支持证据。
- 优化原理及将减少的资源开销。
- 适用的形状、dtype、硬件和推理阶段。
- 预期收益及估算依据。
- 正确性、精度、显存、可维护性和可移植性代价。
- 实现步骤与验证方法。

优先实现能够针对已确认瓶颈、易于构建对照实验且不破坏通用路径的方案。

### 阶段 F：实现、验证与结论

1. 使用 reference implementation 或框架原实现作为 correctness oracle。
2. 覆盖典型形状、边界形状、非对齐形状和必要的 dtype。
3. 设置适合 dtype 的 `atol`/`rtol`，报告最大绝对误差和相对误差；量化方案还应评估模型级精度影响。
4. 使用相同环境、输入分布和测量方法比较 baseline 与 optimized。
5. 同时报告收益和退化，不能只选择最优样本。
6. 分析性能变化是否符合理论预期；若不符合，继续定位原因。
7. 明确结论的适用范围，不把单一 GPU、形状或模型上的结果泛化为普遍结论。

优化验收至少满足：

- 正确性测试通过。
- benchmark 可重复运行，并记录完整命令或脚本入口。
- 与可靠基线进行公平比较。
- 报告原始结果、优化结果、加速比和必要的误差指标。
- 说明未解决问题、已知限制和下一步工作。

## 5. 算子知识与实际案例的目录边界

每个算子使用独立知识目录，名称采用小写英文和下划线：

```text
operators/
  <operator_name>/
    README.md              # 稳定语义、数据流、实现路径和性能模型
    optimization-map.md    # 案例提炼出的诊断与优化决策；有真实知识时创建
    case-index.md          # 结构化案例证据卡；有实际案例时创建
    research/              # 论文摘要和固定源码快照
```

完整实验不放在技能目录。环境、命令、实现补丁、correctness、benchmark、profile 摘要、失败过程和最终结果属于 `docs/cases/<case-id>/` 与 `models/<model>/<platform>/`；大体积 profiler、权重和数据集只记录外部位置。

不要预先创建空的 `optimization-map.md` 或 `case-index.md`。首个实际案例产生可复用证据后再创建；后续案例按 [case-to-knowledge.md](case-to-knowledge.md) 写知识差量。

## 6. 稳定算子知识模板

`operators/<operator_name>/README.md` 描述当前稳定理解，不按日期连续追加实际案例。默认结构：

```markdown
# <算子名称> 分析

## 1. 摘要
## 2. 分析范围与环境
## 3. 定义、公式与张量形状
## 4. 大模型推理中的使用场景
## 5. Prefill 与 Decode 特征
## 6. 理论计算量、访存量与性能上限
## 7. 主流实现与源码调用链
## 8. 正确性 oracle 与验证维度
## 9. 性能诊断模型
## 10. 优化方向与取舍
## 11. 结论、限制与开放问题
## 12. 参考资料
```

摘要应直接给出算子的作用、可能瓶颈以及决定路径选择的关键变量。案例中的最优参数和实测收益进入 case index；只有跨案例形成稳定机制后才改写 README 的结论。

实际案例结束时必须回答“本次比开始前新增了什么理解”。按 [case-to-knowledge.md](case-to-knowledge.md) 把证据写入 case index，并在确实改变后续行动时更新 optimization map。单纯增加一个平台性能数字不构成 README 更新理由。

## 7. 数据与图表规范

- 原始 benchmark 数据优先保存为 CSV 或 JSON，图表由脚本生成，避免只保留截图。
- 图表标明单位、硬件、dtype、输入形状和基线定义。
- 加速比统一定义为 `baseline_time / optimized_time`。
- 带宽利用率和计算利用率必须说明所采用的理论峰值。
- 表格中同时展示绝对数值与相对变化。
- 不同实验不可混用 warmup、计时方法或环境配置；若有差异必须显式说明。

## 8. 代码与实验要求

- 优先编写小而独立的 benchmark，避免一开始就用完整模型掩盖算子行为。
- benchmark 必须避免未同步的异步计时、隐式初始化、首次编译和缓存污染。
- 将环境检测、测试、benchmark 和结果生成分离，便于复现和排错。
- 新增优化路径时保留 reference 路径，便于正确性对比和回归测试。
- 对 shape、dtype 或硬件有限制的实现进行显式检查，并提供清晰的 fallback。
- 修改代码后运行与改动风险相匹配的测试；无法运行时说明原因，不宣称已经验证。
- 不伪造硬件测试数据。没有目标硬件时，只能给出理论分析、代码检查结果和待执行实验计划。

## 9. 完成标准

一次完整算子分析只有在以下内容齐备时才视为完成：

- 定义、场景、形状和推理阶段描述清晰。
- 源码调用链可定位到实际 Kernel 或明确说明无法继续追踪的原因。
- 有定量的计算、访存或性能上限分析。
- 有可复现的正确性测试和基线 benchmark。
- 瓶颈结论有 profiler 或实验数据支持。
- 优化方案与瓶颈直接对应，并完成公平对比。
- 结论包含适用范围、代价、限制和后续方向。
- 代码、命令、环境与引用足以让其他人复现主要结果。
- 案例已写出知识差量，并能从算子 case index 追溯到完整证据。
- 若结果改变了未来的首个检查、候选或停止条件，optimization map 已同步；没有变化时明确记录 `knowledge_delta: none`。

若当前工作只完成其中一部分，应将状态标记为“阶段性结果”，并列出尚缺的证据或实验。
